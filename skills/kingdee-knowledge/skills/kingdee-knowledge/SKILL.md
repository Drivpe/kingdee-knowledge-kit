# 金蝶知识库检索(kingdee-knowledge)——kd CLI 流程(v6.3 search-first + 合成在调用方)

金蝶官方知识检索内核(`kd.core`,可 import 的库)的命令行入口 `kd`,
逆向自金蝶云社区公开后端,**纯匿名:零账号、零点数、无澄清、无对话限流**。
默认输出 JSON(stdout=数据,stderr=进度)。**库模式:无服务、无端口、无 HTTP、无本地落盘。**

v6 主轴是**彻底在线**(ADR-0005):模仿人类在论坛解决问题——用时在线搜、搜到即读即查。
ADR-0011 去服务化后,本地落盘缓存(landing / corpus / sqlite)与发版说明库预囤**整体取消**,
`kd ask` 一次调用即把该读的都带回来;**不存在任何本地语料可供 rg**。

v6.2 起**合成权在你手里**(ADR-0008):套件零模型依赖,只产资料包。拿到资料包后由**你**按
ANSWER-SPEC 直接合成——**默认不开子代理**,自己读资料包自己答(2026-09-17 定案:子代理
看不到本对话、无法追问、交付常不完整,为省上下文付出的沟通成本更高)。仅当资料包明显超长
(如回答数极多的长帖、topK 拉满)或一次要合成多份时,才考虑开子代理。

## 产品线默认(2026-09-17 起)

`ask` 的 `product_id` **默认 93(星空旗舰版)**——常规提问不必显式带 `--product`。

- **问句产品词优先于默认**:问句里出现「苍穹」「企业版」等别名时按别名推导并覆盖 93
  (问"苍穹 XX"得到 87,不写则得到 93);
- 要**真正的不过滤**必须**显式**传 `--product 0`——默认 93 已使"不带参数"不再等于不过滤;
- 实测代价(2026-09-17):同一问题不带默认时 `effectiveProductId=null`、GlobalEase 相关
  文档**零命中**;默认 93 后直接命中官方条目。默认值得以存在,是因为不带过滤的召回质量
  在中文语料上显著更差。

## kd 的定位(两级回退)

1. PATH 里的 `kd`(pipx 装到 `~/.local/bin`;Git Bash 下裸名走无扩展名 shim;cmd/PowerShell 走 kd.cmd)
2. 一键脚本兜底路径:Windows `%USERPROFILE%\.kingdee-kit\bin\kd.cmd`;
   Linux/macOS `~/.kingdee-kit/bin/kd`
3. 都没有 → **自己转用仓库启动器,不要停下来让用户去装**:
   `python3 <仓库>/src/kd_run.py ask "问题" --topk 4`
   它自建 `sys.path` bootstrap,无需 PYTHONPATH,与装好的 `kd` 行为等价。仓库位置按序找:
   当前工作目录 → `kingdee-knowledge-kit` 的常见检出位置;找不到再问用户。
   **在此之前不要编造任何金蝶知识内容。**
   (注:机器上可能没装 pipx、`~/.kingdee-kit` 也可能不存在——第 1、2 级落空是常态,
   走第 3 级即可,不要因此判定环境损坏。)

能力清单:`kd --help`(四条子命令与示例)与 `kd health`(内核版本/公开面/预算上限)

⚠️ **永远不要把 stderr 丢弃(禁 `2>/dev/null`)**:stdout=数据,stderr=进度与诊断;命令失败时先看
stderr/错误 JSON(带 hint),据此换调用方式,而不是静默改道 websearch。

## ⭐ 检索流程(三步,不要临场发挥)

### 第 1 步:kd search——常规问题一律此入口(出清单,你挑)

多路拆词检索,**只出标题清单、不返回正文**:内核内置**多路关键词拆解**
(原句路+症状词路+字段/实体名词路+产品词路,≤7 路,规则在包内 `kd/query_routes.json`)→
每路各发一次上游检索(每路 10 条)→ 去重 → **按"命中路数"降序排**(同路数按上游原生序)。

```bash
kd search "应用为禁用状态[网关]" --product 93
# → {total, queries[], results:[{type,id,title,hitRoutes,routes[],…}], routeErrors[], scanNote}
```

- **每条带 `hitRoutes`(命中几路)+ `routes[]`(来自哪几路)**:这是内核给你的**决策依据**,
  比任何融合评分都可解释——多路都命中的通常是泛文,只在原句路命中的往往是精确专文;
- **报错原文直接搜**:用户拿上游报错码/症状描述来时,把原文原样交给 search(如
  `应用为禁用状态[网关]`),内核的原句路负责跨词汇鸿沟召回官方文档;
- **`routeErrors[]` 非空 = 部分路失败、召回不完整**:绝不要把"某路被上游拒绝"读成
  "官方没这类文档",此时应重试或告知用户;
- `budget_exhausted:true` 表示预算耗尽,清单不完整,先消化已获结果;
- `--routes N` 控制最多用几路(默认 7);`--routes 1` 即单路精确检索。

### 第 1.2 步:kd read——从清单挑出 id 再取全文

清单只给标题,**要全文必须显式读**——这一步由你决定读哪几篇,内核不再替你挑:

```bash
kd read <id>                          # type=knowledge → 官方文档全文
kd read <questionId> --kind answer    # type=answer → 问题+全部回答+追问链
kd read <id> --kind article           # type=article → 社区文章全文
# --kind 照抄清单里的 type 字段,零翻译
```

### 第 1.5 步:合成(你的职责,不是 kd 的)

**kd 不合成回答**(ADR-0008,零模型依赖)。拿到资料包后**由你直接合成**——**默认不开子代理**
(2026-09-17 定案)。子代理看不到本对话、不会追问、交付常不完整(实测:只回"已完成"不交正文、
错判置信度),省下的上下文抵不过沟通成本。资料包超长(如长帖、topK 拉满)时才考虑开。

**答案形态(照官方 AI 回答的样子写)**:

- **开头直接给定性结论**,不要元信息、不要 JSON、不要"置信度头";
- 三段式 `## 原因分析` / `## 解决方案` / `## 操作边界`,步骤标题用 `### 1. 动作名`;
- **引用做成可点击角标**:官方文档(knowledge)链接**匿名可访问(实测 HTTP 200)**,
  可直接写 `[标题](https://vip.kingdee.com/knowledge/<id>)`;社区问答(question)链接
  **有 404 失效情况**(帖子被删),只写标题不给链接,或给链接并注明可能失效;
- **正文里不放内部编号**(不要写"源6""[n] n 号文档"这类自用记号);
- **结尾不加审计披露/复盘段**——那是给你自己看的,不是答案;
- 资料不足时(见下「置信度」),像官方那样**反问一句关键的澄清**,而不是堆一段缺口声明。

**合成规范**(你自己照此写,不是传给子代理的提示词):

```text
## 回答格式
结构化 Markdown 三段式:
1. `## 问题原因分析` —— 机制/字段/流程层面的原因;
2. `## 解决方案` —— 编号步骤(### 1. 动作名),每步给可直接执行的菜单路径/字段名/参数值;
3. `## 操作边界` —— 适用版本/前提/不覆盖的情况。
并列信息用 Markdown 表格。
⚠️ 开头直接给定性结论;不要 JSON/置信度头/内部编号("源N")/审计复盘段。

## 引用规则(硬)
- answer(社区问答)引用**只用于症状对齐**;根因解释**必须**引 knowledge 的根因段落,
  只引 answer 不算根因可解释;
- **「官方已修复」类问题优先引官方发版说明的「模块-问题-修复」条目**;社区说法与官方说明冲突时,
  **以官方说明为准**。⚠️ 本套件**没有**本地发版说明库(随去服务化取消)——
  这类问题靠 `kd ask` 召回 + 站外搜索 `site:vip.kingdee.com 发版说明 <关键词>`(见「第 2 步」),
  查不到就按「现有资料未覆盖」如实声明,**不要凭印象断言某版本修复了某问题**。
- **区分权威级**:官方文档确认的结论**直接陈述**;社区问答/文章得出的标注「**来自社区经验**」。
  不要把社区推测写成官方口径,也不要把官方结论降格成"据说"。
- 资料源带 `chunks`(形如 `[chunk#2 【操作步骤】]`)时**优先依据命中段落**,
  不引与结论无关的全文;
- **产品线核对**:引用前核对 `effectiveProductId` 是否等于预期产品线 ID
  (93 旗舰版 / 87 苍穹 / 1 企业版标准版)。**它为 `null` 表示本次未带任何产品过滤**——
  此时不得当作某条产品线的答案引用,正文须标注「本次检索未按产品线筛选」。
  ⚠️ `sources[].products` 装的是上游中文类目名(`["金蝶AI套件"]`),与整数 ID **值域不可比**,
  只能当阅读提示,**不得**拿来判定"产品线不符故排除该源"。
- **网页链接可点性按路径而异**(2026-09-17 实测,更正 ADR-0007 的"一律 302 登录墙"):
  `https://vip.kingdee.com/knowledge/<id>` → **HTTP 200 且含正文,可点**;
  `article/<id>` → 302 到 `knowledge/<新id>`(**路径迁移,最终 200**);
  `question/<id>` → 302 到 `/error/404`(**帖子被删**)。
  故**引用优先用 `knowledge/` 链接**(可点);`question/`、`article/` 的 URL 会因删除/迁移失效,
  只写标题,或给链接并注明可能失效。

## 产品线路由(历史事故记录,规则已于 2026-09-17 撤销)

> **事故(2026-09-06)**:agent 回答「金蝶旗舰版 BOM 维护」时,中途把 `--product 93`
> (旗舰版过滤)变道为 `--product 0`(不过滤),召回了星空企业版内容(ENG_BOM/T_ENG_BOM)
> 且未甄别,把企业版答案当成旗舰版输出(正确答案:旗舰版是 pdm_mftbom)。
>
> 事故后曾立三条硬规则(禁不带 --product、禁变道 0、禁切其他产品线)。**2026-09-17
> 全部撤销**:`ask` 已改默认 93,"不带 --product"不再等于不过滤,第一条失去对象;后两条
> 被判定为可由默认值自然规避。规则见 ADR(已改写)。本节保留事故事实,供未来追溯。

**现行做法**(不是硬规则,是判断):

- 默认 93,问句产品词自动覆盖(见上节);要不过滤需显式 `--product 0`;
- 会话内不要**因为自己检索不顺手**就把 `--product` 切来切去。若问句确实指向其他产品线
  (出现「苍穹」「企业版」等),让产品词推导去做,或先向用户确认;
- `effectiveProductId` 是唯一可读的产品线凭证;**它为 `null` 表示本次未带过滤**,此时
  正文要标注「本次检索未按产品线筛选」;
- ⚠️ `sources[].products` 是上游中文类目名(如 `["金蝶AI套件"]`),与整数 ID **值域不可比**,
  只能当阅读提示,**不得**拿来判定"产品线不符故排除该源"。

## 置信度(内部判断,不输出)

**自己判断,不要把判断过程写进答案**(不要 JSON 头、不要分数、不要"置信度"字样):

- 资料有段落直接说明了机制/字段/步骤 → 正常作答;
- 有相关材料但没覆盖用户问的那一点 → 正文点明「现有资料未覆盖 X」,**不要硬凑步骤**,
  并**反问一句关键澄清**(照官方 AI 的做法);
- 召回与问题不匹配 → 直说没查到,给确认渠道,**绝不编造菜单路径/字段名**。

判断依据(来自 kd 的客观数据,同样不写进答案):

- `budgetExhausted:true` ⇒ 本轮检索不完整,结论应更保守;
- `routeKinds` 只有 `product` 而无症状路/实体路命中 ⇒ 片段路全空,很可能没查到。```

**若确实开了子代理**:要求它把**完整答案正文原样返回**——实测它常只回"已完成"状态摘要
而不交正文,也会错判置信度。追问一次即可拿到。

### 第 2 步:在线兜底——ask 空手或解释不了根因时,站外搜索

`kd ask` 的 sources 空手、或拿到的资料解释不了根因时,才动用 websearch:

```bash
# 站外兜底,回答必须标注「站外语源」
site:vip.kingdee.com 发版说明 <修复项关键词>
site:help.open.kingdee.com <功能名词>
```

诚实边界:部分发版说明不在搜索索引内,搜不到≠不存在;不要因为第三跳也无果就断言「官方没有」,
按 ANSWER-SPEC 写「现有资料未覆盖」。

## 次要入口:kd ask(一站式资料包)

需要**一次拿回全文**而不想自己挑时用它:多路拆解 + RRF 融合 + 深读 topK 全文,
返回 `sources[]`(每源 title/url/products/全文/chunks)+ `synthesisBrief`(召回信号摘要)。

```bash
kd ask "BOM分母27000 MRP运算变成平方" --topk 4
# --kw 可显式指定关键词(跳过自动拆解):kd ask --kw "BOM 分母" --kw "MRP 用量"
```

⚠️ **`ask` 的融合排序会在报错码场景上失手**(实测 `应用为禁用状态[网关]`:目标文档在
`ask --topk 4` 落在第 8 位、读不到,而 `kd search` 清单里可见)。**报错排查、症状描述类问题优先用
`kd search` 出清单自己挑**,`ask` 只在"确定想要一站式全文包"时用。

- 返回体里看 `routes[]` 理解内核拆了哪些路;`budget_exhausted:true` 表示上游预算耗尽,
  先消化已获资料,不要立刻重跑;
- sources 展示排序 answer 优先(症状近似度最高),knowledge 紧随(补根因解释)——两类都要看;
- `synthesisBrief` 是**召回信号摘要**,先读它再决定要不要合成。

## 手动细粒度调试命令(search/read 的参数控制)

`search`/`read` 已是常规入口(见「检索流程」),这里只列参数级控制:

```bash
kd search "信用额度控制" --product 93 --size 10
# → {total,queries[],results:[{type,id,title,hitRoutes,routes[]}],routeErrors[],scanNote,stats}
# --type knowledge|answer|article 可过滤(每路都带该过滤,各路独立跨页扫描)
# --routes N 最多用几路(默认 7);--routes 1 = 单路精确检索
# ⚠️ --page/--size 是**清单分页**(作用于多路去重排序后的清单,不是上游分页)
# --product 93=星空旗舰版(默认)、87=苍穹、1=星空企业版/标准版、0=不过滤
# ⚠️ --product 必须沿用本会话首次检索确定的路由,禁止变道 0(硬规则见下节)

kd read <id>                          # type=knowledge → 官方文档全文
kd read <questionId> --kind answer    # type=answer → 问题+全部回答+追问链
kd read <id> --kind article           # type=article → 社区文章全文
# --kind 照抄 search 结果的 type 字段,零翻译
```

## 回答规范

遵循 `docs/ANSWER-SPEC.md`(单一事实源):结构化 Markdown(原因分析→编号步骤→操作边界)、
表格、`[n]` 编号引用(可细到 `[n](chunk#m)`)、**根因引用规则**(answer 引用用于症状对齐,
根因解释必须引 knowledge 的根因段落;官方发版说明需站外取原文)、资料未覆盖就诚实声明,**不编造菜单路径/字段名/接口名**;
社区内容标注「来自社区经验」;引用一律用资料包 sources 里的原始 url。

## 快捷方式

- `kd search "问题/报错原文"` —— **常规入口**:多路拆词+只出标题清单(带 hitRoutes),你挑完再读
- `kd read <id> --kind <type>` —— 从清单取全文(kind 照抄清单里的 type)
- `kd ask "问题" --topk 4` —— **次要入口**:一站式资料包(多路+RRF 融合+深读 topK+synthesisBrief);
  报错码场景可能漏召回,优先用 search
- 拿到内容后**自己合成**(默认不开子代理;规范见「第 1.5 步」)
- `kd health` —— 内核自检(库模式:确认公开面与路由规则已加载,排查环境问题先跑它)

## 内核或上游异常时

```bash
kd health --help   # 先看用法
kd health          # 正常时回 JSON 自检报告;失败时错误 JSON 的 hint 字段带修复指引
```

仍不行才回退 websearch/webfetch(`site:vip.kingdee.com`、help.open.kingdee.com),并告知用户。

## 禁止事项

- **同一问题会话内禁止把 --product 从已确定的路由变道为 0(不过滤)或其他产品线**;
  产品线切换必须先经用户确认(见「产品线粘性」硬规则)
- **禁止把 `sources[].products` 的中文类目名当作产品线判据**(值域不可比);
  `effectiveProductId` 与预期不符时必须停下报告,禁止带着错误过滤继续作答(见「产品线粘性」硬规则)
- 不要编造端点/字段/参数;内容一律以 kd 返回的 JSON 为准
- 常规问题不要从手动 search/read 起步——一律先 kd ask;也不要在 ask 之外临场编检索词路(多路已内置)
- 不要把检索失败当成"官方没有相关文档"——先走完三步流程,再按「现有资料未覆盖」诚实声明
- 不要高频连续检索(保持人类频率;本地无缓存可复用,每次 ask 都真实消耗上游)
- 不要尝试官方 /aisapi/ai-search 管线——需登录+身份认证,匿名只会得到「未授权操作」
