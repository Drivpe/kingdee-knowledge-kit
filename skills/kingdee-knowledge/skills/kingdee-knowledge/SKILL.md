# 金蝶知识库检索(kingdee-knowledge)——kd CLI 流程(单入口:search → read → 合成)

金蝶官方知识检索内核(`kd.core`,可 import 的库)的命令行入口 `kd`,
逆向自金蝶云社区公开后端,**纯匿名:零账号、零点数、无澄清、无对话限流**。
默认输出 JSON(stdout=数据,stderr=进度)。**库模式:无服务、无端口、无 HTTP、无本地落盘。**

v6 主轴是**彻底在线**(ADR-0005):模仿人类在论坛解决问题——用时在线搜、搜到即读即查。
ADR-0011 去服务化后,本地落盘缓存(landing / corpus / sqlite)与发版说明库预囤**整体取消**,
检索一次即把该拿的清单带回来;**不存在任何本地语料可供 rg**。

## 单入口定案(2026-09-18)

检索链路收敛成**一条**,没有第二条路可选:

1. `kd search` 出**清单**(标题 + 短摘要,不含正文);
2. 你按标题与问题的匹配度**自己挑**;
3. `kd read <id>` 取挑中那条的全文;
4. 你按 ANSWER-SPEC **自己合成**回答(默认**不开子代理**)。

三条定案(不得临场重开):

- **`ask` 已整体删除**——命令不存在(只会得到 argparse 退出码 2),不要尝试调用,
  也不要期待"一站式资料包"/`synthesisBrief`/`chunks` 这些随之删除的东西;
- **内核不做任何算法排分**:金蝶云社区后端用的是**官方综合排序**,我们的每一路检索拿回来的
  结果**本来就是排好序的**;内核唯一做的事是**删除重复内容**(同一条只留一份),
  读哪几篇由你判断。内核里**没有 RRF、没有融合分、没有 rerank、没有 hitRoutes 计分**
  (这些是随 `ask` 删除的历史残留,不要在任何文档里复活它们);
- **合成权在你手里**(ADR-0008):套件零模型依赖。得到全文后由**你**按 ANSWER-SPEC 直接合成
  ——2026-09-17 定案:子代理看不到本对话、无法追问、交付常不完整(实测:只回"已完成"不交正文、
  错判置信度),为省上下文付出的沟通成本更高。仅当单次要合成多份、或某一篇原文确实超长时,才考虑开子代理。

## 产品线默认(2026-09-27 重写:内核不再推导)

`search` 的 `product_id` **默认 93(星空旗舰版)**——常规提问不必显式带 `--product`。

- ⚠️ **内核不做任何字面推导**(决策 D14,2026-09-27):问句里出现「苍穹」**不再**被改写成
  87。旧的别名表 + 裁决规则(`_derive_product_id`)已整体删除。你传什么就是什么;
- 要**真正的不过滤**必须**显式**传 `--product 0`(Python 侧也可传 `product_id=None`,同义);
- **值域三态**(别混):省略参数 → 默认 93;显式 `None` → 不过滤;显式整数(含 0)→ 直通。
  早期把 `None` 一律折成 93,会让 Python 调用方**无法**表达"不过滤"(实测 total 31788 → 6326);
- 实测代价(2026-09-17):同一问题不带默认时 `effectiveProductId=null`、GlobalEase 相关
  文档**零命中**;默认 93 后直接命中官方条目。默认值得以存在,是因为不带过滤的召回质量
  在中文语料上显著更差。

## kd 的定位(三级回退)

1. PATH 里的 `kd`(pipx 装到 `~/.local/bin`;Git Bash 下裸名走无扩展名 shim;cmd/PowerShell 走 kd.cmd)
2. 一键脚本兜底路径:Windows `%USERPROFILE%\.kingdee-kit\bin\kd.cmd`;
   Linux/macOS `~/.kingdee-kit/bin/kd`
3. 都没有 → **自己转用仓库启动器,不要停下来让用户去装**:
   `python3 <仓库>/src/kd_run.py search "问题" --product 93`
   它自建 `sys.path` bootstrap,无需 PYTHONPATH,与装好的 `kd` 行为等价。仓库位置按序找:
   当前工作目录 → `kingdee-knowledge-kit` 的常见检出位置;找不到再问用户。
   **在此之前不要编造任何金蝶知识内容。**
   (注:机器上可能没装 pipx、`~/.kingdee-kit` 也可能不存在——第 1、2 级落空是常态,
   走第 3 级即可,不要因此判定环境损坏。)

能力清单:`kd --help`(三条子命令与示例)与 `kd health`(内核版本/公开面/预算上限)

⚠️ **永远不要把 stderr 丢弃(禁 `2>/dev/null`)**:stdout=数据,stderr=进度与诊断;命令失败时先看
stderr/错误 JSON(带 hint),据此换调用方式,而不是静默改道 websearch。

## ⭐ 检索流程(三步,不要临场发挥)

### 第 1 步:kd search——常规问题一律此入口(出清单,你挑)

多路拆词检索,**只出清单(标题 + 短摘要)、不返回正文**。内核内置**多路关键词拆解**
(稀有数字 token 路 + 原句路 + 症状词路 + 字段/实体名词路 + 产品词路,≤7 路,规则在包内 `kd/query_routes.json`)
→ 每路各发一次上游检索(每路 10 条)→ **去重归并**(唯一的内核加工)→ 出**帖级**清单
(同一帖的多条回答合并为一条,条目 `id` 就是帖子号)。

```bash
kd search "应用为禁用状态[网关]" --product 93
# → {text, keywords, total, queries[], routesPlanned, routesDegraded, effectiveProductId,
#    results:[{type,id,title,url,hitRoutes,routes[],snippet,products,adopted,answersCount,
#              comments,supports,questionBody}],
# ⚠️ url 按链接政策给值:knowledge/article 有值,**question 恒为 null**(不给链接,见第 3 步)
#    routeErrors[], budget_exhausted, scanNote, stats}
# ⚠️ 无 page/pageSize/totalPages(v6.4 删清单分页);无 questionId(帖级化后 id 即帖子号)
```

**清单顺序就是上游相关度顺序**——这是本套件最重要的一条口径:

- 排序键只有 `(路序, 路内上游名次)`:任意两条先比"首次出现在第几路",同路再比"该路内名次",
  **两者都不是内核算出来的**——路序来自拆解规则里固定的路定义顺序,路内名次直接照抄上游返回顺序;
- **第 1 路是"最能收窄候选集"的那一路**(2026-09-28 起):问句里若有稀有数字标识符
  (错误码/单号,≥3 位数字),内核把它单独成路并放在第 1 位,原句路退到第 2 位;
  没有这种 token 时,原句路居首。**原句路恒常参与且保席位,但排位可变**——
  这不是"给 token 打分",是路序(排序键结构没变);
- **`hitRoutes`/`routes[]` 是纯信息字段,不参与排序**:它们只回答"这一条被哪几路撞到"。
  多路命中常意味着**泛文**(每个拆词都沾边的综述),只在原句路命中往往是**精确专文**;
  但这只是阅读提示,不是分数,内核绝不据此重排;
- `routesPlanned`:计划路数(去重前,受 `--max-routes` 截断后)。`routesDegraded:true` 表示
  **路数塌缩**——原句路与产品路拆出**逐字相同的词串**,去重后实际路数少于计划路数
  (`scanNote` 会写"路数塌缩:N→M 路")。它在告诉你:你以为的多路
  交叉验证其实只有少数路在跑,召回面比预期窄,**该换词重搜或补 `--kw`**;
  它是**表达事实,不是评分**。(实测 `kd search "信用额度控制" --product 93` 即落入此情形。)
  注意:本字段只有在**所有计划路都成功返回**时才可靠——若同时 `routeErrors[]` 非空,
  少的那几路可能是**失败**而非塌缩,别把"路没跑成"读成"拆词重复";
- **报错原文直接搜**:用户拿上游报错码/症状描述来时,把原文原样交给 search(如
  `应用为禁用状态[网关]`),内核的原句路负责跨词汇鸿沟召回官方文档;
- **`routeErrors[]` 非空 = 部分路失败、召回不完整**:绝不要把"某路被上游拒绝"读成
  "官方没这类文档",此时应重试或告知用户;
- **`budget_exhausted:true`** 表示上游请求预算耗尽,清单不完整,先消化已获结果,别立刻重跑。

**`--kw`:自己拆词传进去(报错码/中英混写场景的首选)**

内核的自动拆解是**规则**,你比规则懂上下文。当你已经想清楚该用哪几个词去搜时,直接给:

```bash
kd search --kw "BOM 分母" --kw "MRP 用量" --kw "应用为禁用状态[网关]" --product 93
# 也可混用:kd search "BOM 分母 27000" --kw "MRP 用量"
```

- **每个 `--kw` 一路**;路序 = 你给词的顺序。**原句路恒常存在**(2026-09-27 起):
  给了 `text` 就由 `text` 充第 1 路;只给 `--kw` 时**第 1 个 `--kw` 自动充任原句路**
  (故它不再另占一路——路数与 `queries` 逐字不变,只是第 1 路的排序姿态变精确为相关性);
- `text` 与 `--kw` 可并用,推荐并用:`text` 放**整句/完整报错串**(它充任原句路),`--kw` 放你
  拆好的稀有 token 与片段词。两者重复时自动去重,不会出现同词两路;
- 重复词自动去重,超过 `--max-routes` 的尾部词被截掉;
- 只给 `--kw` 时 `text` 回显为 `null`,这不影响原句路的产生(见上,第 1 个 `--kw` 充任);
- 产品过滤对 `--kw` 路同样生效(不会因为用了 `--kw` 就绕过 `--product`)。

**参数速查**

```bash
kd search "<关键词>" [--kw KW]... [--product N] [--type knowledge|question|article]
                     [--max-routes N] [--global] [--budget N]
```

- `--kw KW`:显式关键词,可重复,替代内核自动拆解(见上「`--kw`」小节);
- `--max-routes N`:最多用几路(默认 7);`--max-routes 1` = 单路精确检索;
- `--type knowledge|question|article` 按实体类型过滤(每路都带该过滤,各路独立跨页扫描);
- `--product N`:93=星空旗舰版(默认)、87=苍穹、1=星空企业版/标准版、2=星空侧二开问答专区、0=不过滤(显式指定才生效)——**内核不做字面推导**,你传什么就是什么;
- `--global`:跨全部产品(不按 `--product` 过滤);
- `--budget N`:上游请求硬上限覆盖(默认取包内 `query_routes.json`)。

## 检索策略规范（怎么搜才准）

拆词准不准,不看拆出的词多不多,看**有没有把问句里的稀有标识符单独拎出来一路**。上游是 **OR 语义**:
一路里空格拼接的多个词是"命中任一即召回",所以**拆得越细、词越常见,OR 展开的候选集越大 → 噪音越多**;
反过来,**稀有 token 是区分度的唯一来源**,它能把候选集从数千压到个位数。

实测数据(2026-09-27 复测;金标=官方文档 `646787188905978624`《金蝶AIOpenAPI错误码说明》,产品线 93):

| # | 做法(实际检索路) | 金标位次 | 上游 total |
|---|---|---|---|
| E1 | `text=应用为禁用状态[网关]` + `--kw 2510` → `[原句, 2510]` | 第 5 | 1774 |
| **E2** | `--kw 2510` + `--kw 应用为禁用状态[网关]` → `[2510, 原句]` | **第 1** | 1774 |
| E3 | `text=2510` + `--kw 应用为禁用状态[网关]` → `[2510, 原句]` | 第 1 | 1774 |
| E4 | `应用为禁用状态[网关] 2510` 合并成一路(自动拆解) → `[原句 2510, 应用 禁用状态 网关]` | 第 5 | 4302 |
| E5 | 只给 `--kw 2510` → `[2510]` | 第 1 | 仅 2 |
| E6 | 规则拆词(自动) → `[原句, 应用 禁用状态 网关]` | 第 5 | 4302 |
| E7 | 泛词各自成路 → `[应用, 禁用状态, 网关]` | 掉出前 30 | 11547 |
| E8 | `2510 应用为禁用状态` 合并 → `[原句合并, 应用 禁用状态]` | 掉出前 30 | 15180 |
| E9 | 单路 `应用为禁用状态[网关]` | 第 5 | 1774 |
| E10 | 单路 `应用为禁用状态`(无 `[网关]`) | 掉出前 30 | 15180 / 1751 |

⚠️ `total` 是上游候选集规模,会随语料漂移,**比对检索效果只看金标位次,不看 total**——实测 E10 同一个单路查询(queries 逐字相同)两次跑出 total `15180` 与 `1751`,而位次都掉出前 30。位次本身也有 ±1 的固有抖动。

**关键机制(2026-09-28 对照实验)**:E1 与 E2 用的是**同一组词、同一个上游**,唯一差别是**路序**
——`2510` 在第 1 路得第 1 名,退到第 2 路立刻掉到第 4–5 名。因为排序键第一维就是"首次出现的路序号",
**最能把候选集压窄的那一路必须排在第 1 位**。所以"稀有 token + 原句"这个组合本身不神奇,
神奇的是**稀有 token 排在最前**。

**⚠️ 但"哪个词更收窄"不能靠肉眼判断——已实测证伪**

不要把这条规律推广成"把看起来最像标识符的词放前面"。实测(金标 B = `873372977646105600`,BOM 分母平方案):

| 前置到第 1 路的词 | 上游 total | 金标 B 位次 |
|---|---|---|
| `2510`(纯数字错误码) | 2 | **1**(从第 4 升上来) |
| `生产单位数量`(实体词) | 4506 | 2(未变) |
| `分母变平方`(症状词) | 22038 | 2(未变) |
| **`BOM`**(拉丁缩写,看起来最像标识符) | 1308 | **12**(从第 2 掉下去!) |

即:**"这个词看起来稀有"不等于"它比同问句里的其他路更收窄"**,判断这件事需要语义。故内核
**只把纯数字串前置**,拉丁词与中文词一律不碰。你手工拆词时也照此:**不要把英文缩写想当然地放第 1 位**。

**内核已自动做这件事(2026-09-28 起,T2)**:问句里有 ≥3 位纯数字串时,内核把它单独成路并置于第 1 位,
原句路退到第 2 位。故报错码类的**默认路径**(直接 `kd search "2510 应用为禁用状态[网关]"`)
已能拿到与手工拆词同等的位次:

| 做法 | 实际路序 | 金标位次 |
|---|---|---|
| **默认路径**(内核自动 token 路) | `[2510, 2510 应用为禁用状态[网关], …]` | **第 1** |
| 手工绕开(旧推荐) | `[2510, 应用为禁用状态[网关]]` | 第 1 |
| 改前默认路径(无 token 路) | `[原句, 应用 禁用状态 网关]` | 第 3–5 |

**五条判据(拆词时逐条对照)**

1. **稀有数字 token 单独成路并抢占第 1 路**:错误码 / 单号 / 数字型编码(`2510`、`27000`)
   ——内核已自动处理,**你不用手工做**。手工 `--kw` 时照同一原则:把数字 token 放在**第一个 `--kw`**。
   ⚠️ **拉丁缩写不要放第 1 路**(上表实测:`BOM` 前置会让金标从第 2 掉到第 12);
2. **原句必须保留一路**:完整问句 / 完整报错串原样成路,它有独立价值,不可被片段路替代
   (E9 原句单路得第 4–5,E6 的规则拆词能保住这个位次也是靠这一路)。
   **原句的排位让给稀有数字 token,但绝不能丢**;
3. **常见泛词不要单独成路**:`应用`、`状态`、`网关`、`结果`、`系统` 等被上千篇文档共享的词单用无区分度,
   拆出来只会扩大候选集(E7:三泛词各自成路 → total 11547、金标掉出前 30)。
   这类词的正确位置是**跟在原句路或稀有 token 路里当上下文**,不占独立路;
4. **报错串里的标点/符号别丢**:报错原文的括号、方括号常是区分度的一部分——E9 与 E10 只差一个 `[网关]`,
   total 从 1774 变 15180、位次从第 4–5 掉出前 30。**原样整串传,不要自己清理格式**;
5. **中英混写按扫描提取拉丁 token**:中英之间常无空格(如"分母显示27000"),把串里的拉丁字母与数字
   逐段扫描出来当 token 用(`27000`、`ENG_BOM`、`T_ENG_BOM`),不要整段当一个词去搜。

**固定套路(照做即可)**:报错码类问题**直接把报错原文整串交给 `kd search` 即可**——内核会自动把
数字 token 拎到第 1 路。只有当你想用内核没提取的词(或需要控制多于一路的顺序)时才手工 `--kw`,
写法:`kd search --kw "<数字 token>" --kw "<报错原文整串>" --product 93`。

⚠️ **旧版本曾要求你手工绕开默认路径**(因为改前默认路径会把 token 混在原句里、排到第 2 位之后,
金标只到第 3–5 名)。**该绕行自 2026-09-28 起不再需要**——内核已修正。手工写法仍然可用,
但不再是"必须"。这不是放宽判据,是默认路径已达标。

本节的职责是**选出哪几个词、排成什么顺序**;选好之后怎么传(`--kw` 一路一关键词、原句路的自动产生)见上「`--kw`」小节。

### 第 2 步:kd read——从清单挑出 id 再取全文

清单只给标题与短摘要,**要全文必须显式读**——这一步由你决定读哪几篇,内核不再替你挑:

```bash
kd read <id>                          # type=knowledge → 官方文档全文
kd read <id> --kind question          # type=question → 问题+全部回答+追问链(传帖子号)
kd read <id> --kind article           # type=article → 社区文章全文
# --kind 照抄清单里的 type 字段,零翻译
```

⚠️ **帖级化后无需翻译**:清单条目的 `id` 就是**帖子号**,`kd read <id> --kind question` 直接用
(2026-09-27 起 `questionId` 字段已删除,双 id 空间不存在)。

**挑选判据(2026-09-28 增补;这是纪律,不是内核行为)**

内核**不替你挑**(ADR-0008/ADR-0013:清单是唯一交付物,挑选权在调用方)。判据只存在于本节,
**没有任何代码在执行它**——它的约束对象是**你**。按下列顺序读,别按直觉:

1. **先读清单前 3 条,不要跳读**。清单顺序就是上游相关度顺序(排序键 = 首次出现的路序号 +
   该路内上游名次),**跳过前面的去读第 8 条是无依据的**。实测:金标文档常在 `hitRoutes=2`
   的泛文之后、以 `hitRoutes=1` 出现——**这不代表它更差**,只代表它被更少的路撞到;
2. **读够就停**:先读 2–3 条,不够再回头读第 4、5 条。**不要一次把清单读光**
   (每次都真实消耗上游,且长全文会挤占你的上下文);
3. **`type` 决定它能证明什么**(根因引用规则,见 ANSWER-SPEC 第 7 条):
   - `knowledge`(官方文档)→ **可以**支撑「问题原因分析」的机制/字段/流程结论;
   - `question`(社区问答)→ **只能**用于症状对齐("我遇到的和你一样"),**不足以**当根因;
   - `article`(社区文章)→ 同 `question`,标注「来自社区经验」。
   要答"为什么"而清单里只有 `question`,**必须再搜一次**去拿 knowledge,不得用问答帖的推测充当根因;
4. **标签不是判据,`snippet` 也不能当结论**:`snippet` 只是上游短摘要,
   **具体步骤/菜单路径/字段名必须 read 全文核对**;正文`products` 是中文类目名,值域与产品线 ID 不可比;
5. **要不要补搜,看清单的客观信号而不是"感觉不够"**:
   - `routeErrors[]` 非空 ⇒ 部分路失败,**召回不完整**,应换词重试而不是就此作答;
   - `budget_exhausted:true` ⇒ 预算耗尽,清单不完整;
   - `routesDegraded:true` ⇒ 路数塌缩,覆盖面比预期窄,**该换词重搜或补 `--kw`**;
   - 全清单**没有任何标题**贴近问句 ⇒ 很可能真的没查到(而**不是**"官方没有"),换词再搜一轮;
6. **一次读不到就换词,别改产品线**:检索不顺手时先换检索词(见「检索策略规范」),
   **不要因为检索不顺手就把 `--product` 切来切去**——那是串线事故的形态。

### 第 3 步:合成(你的职责,不是 kd 的)

**kd 不合成回答**(ADR-0008,零模型依赖)。拿到全文后**由你直接合成**——**默认不开子代理**
(2026-09-17 定案)。子代理看不到本对话、不会追问、交付常不完整(实测:只回"已完成"不交正文、
错判置信度),省下的上下文抵不过沟通成本。

**答案形态(照官方 AI 回答的样子写)**:

- **开头直接给定性结论**,不要元信息、不要 JSON、不要"置信度头";
- 三段式 `## 原因分析` / `## 解决方案` / `## 操作边界`,步骤标题用 `### 1. 动作名`;
- **引用:`knowledge`/`article` 给链接,`question` 不给**(2026-09-28 定案,唯一真源 =
  `src/kd/contract.json` 的 `linkPolicy`):`knowledge/` 与 `article/` 匿名复测
  14/14 与 12/12 可点,**照抄条目里的 `url` 字段贴出来**;`question/` 匿名 9/9 不可点
  (最终 URL 恒为 `/error/404`)、用户登录态验证 1 条亦不可点,故**只给标题与出处**
  (标注「来自社区经验」),不贴 URL。
- **正文里不放内部编号**(不要写"源6""[n] n 号文档"这类自用记号);
- **结尾不加审计披露/复盘段**——那是给你自己看的,不是答案;
- 资料不足时(见下「置信度」),像官方那样**反问一句关键的澄清**,而不是堆一段缺口声明。

**合成规范**(你自己照此写,不是传给子代理的提示词):

```text
## 回答格式
结构化 Markdown 三段式:
1. `## 问题原因分析` —— 机制/字段/流程层面的原因;
2. `## 解决方案` —— 编号步骤(### 1. 动作名),每步给可直接执行的菜单路径/字段名/参数值;
3. `## 操作边界` —— 适用版本/前提/不覆盖的情况。
并列信息用 Markdown 表格。
⚠️ 开头直接给定性结论;不要 JSON/置信度头/内部编号("源N")/审计复盘段。

## 引用规则(硬)
- question(社区问答)引用**只用于症状对齐**;根因解释**必须**引 knowledge 的根因段落,
  只引 question 不算根因可解释;
- **「官方已修复」类问题优先引官方发版说明的「模块-问题-修复」条目**;社区说法与官方说明冲突时,
  **以官方说明为准**。⚠️ 本套件**没有**本地发版说明库(随去服务化取消)——
  这类问题靠 `kd search` 召回 + 站外搜索 `site:vip.kingdee.com 发版说明 <关键词>`,
  查不到就按「现有资料未覆盖」如实声明,**不要凭印象断言某版本修复了某问题**。
- **区分权威级**:官方文档确认的结论**直接陈述**;社区问答/文章得出的标注「**来自社区经验**」。
  不要把社区推测写成官方口径,也不要把官方结论降格成"据说"。
- 清单条目的 `snippet` 只是上游短摘要,**具体步骤/菜单路径/字段名必须 read 全文核对**,
  不得只凭 snippet 下结论;
- **引用:`knowledge`/`article` 给链接,`question` 不给**(2026-09-28 定案;取代此前两套
  口径——09-17 的"按路径而异、优先用 knowledge/"与 09-27 的"三路径一律 302、不给链接",
  **那两套都已过期**):
  - `https://vip.kingdee.com/knowledge/<id>` 与 `article/<id>`:**贴**(照抄条目 `url` 字段);
  - `question/<id>`:**不贴**(匿名 9/9、登录态 1 条,方向一致);
  - ⚠️ **判定可点性必须看跟随重定向后的最终 URL(`url_effective`),不得只看状态码**
    ——**两个方向的误判都实际发生过**:`question/` 的最终状态码恰为 200(重定向到 404 页),
    只看状态码会把**失效**链接判成可点;`article/248777993676668672` 首跳 302 但最终
    URL 是 `/knowledge/248777993710223104` 且**可点**(被迁移成知识文档),只看首跳
    状态码会把**可点**链接判成失效。
  - ⚠️ 也**不要**把 `question/` 改写成 `questions/`(复数)试图绕过——实测该路径同样不存在。
  - 唯一真源是 `contract.json` 的 `linkPolicy`(代码真的读它,回归用例对着它断言);
    本节只复述结论。完整证据见 `docs/research/2026-09-28-链接可点性复测.md`
    与本轮匿名复测记录。
```

**若确实开了子代理**:要求它把**完整答案正文原样返回**——实测它常只回"已完成"状态摘要
而不交正文,也会错判置信度。追问一次即可拿到。

## 站外兜底(清单空手或解释不了根因时)

## 产品线路由(历史事故记录,规则已于 2026-09-17 撤销)

> **事故(2026-09-06)**:agent 回答「金蝶旗舰版 BOM 维护」时,中途把 `--product 93`
> (旗舰版过滤)变道为 `--product 0`(不过滤),召回了星空企业版内容(ENG_BOM/T_ENG_BOM)
> 且未甄别,把企业版答案当成旗舰版输出(正确答案:旗舰版是 pdm_mftbom)。
>
> 事故后曾立三条硬规则(禁不带 --product、禁变道 0、禁切其他产品线)。**2026-09-17
> 全部撤销**:默认已改为 93,"不带 --product"不再等于不过滤,第一条失去对象;后两条
> 被判定为可由默认值自然规避。规则见 ADR(已改写)。本节保留事故事实,供未来追溯。

**现行做法**(不是硬规则,是判断):

- 默认 93,要不过滤需显式 `--product 0`(内核不做字面推导,见「产品线默认」);
- 不要**因为自己检索不顺手**就把 `--product` 切来切去。若问句确实指向其他产品线
  (出现「苍穹」「企业版」等),由**你**判定后显式传参,或先向用户确认;切换产品线时在答案里说清楚;
- 想核对本轮产品线,看清单的 `effectiveProductId`——它**恒等于你传入的值**(不传即默认 93),
  内核不做字面推导、也不做过滤声明;**不要把它读成"用户指定了旗舰版"**;
- ⚠️ 清单条目的 `products` 是**上游中文类目名**(如 `["金蝶AI套件"]`),与整数产品线 ID
  **值域不可比**,只能当阅读提示——别拿它去判定"产品线不符故排除该条"。

## ⭐ 产品线语义识别(你的职责,2026-09-27)

**产品线由你判定,内核不再参与判定。**(2026-09-27 起:字面推导整体删除,详见 ADR-0014)

内核只做一件事:**照用你显式传入的值**(不传即默认 93)。问句里出现「苍穹」这类字面
**不会再有任何影响**——这是刻意的:"这句话里有没有产品名"由调用层判断远比规则准,
而判定错误等于拿完全不同的语料作答(实测同问句下 87 与 93 的 top10 **零交集**)。

你要做的:读问题,判意图,显式传 `--product N`。判据如下。

**① 问的是苍穹 → `--product 87`**

问句里出现「苍穹」「星瀚」,或问的是苍穹特有的概念(BOTP、苍穹插件、苍穹开发助手、
`LoginAfterBase`、微服务/容器化部署) → 87。

**② 问的是开发/二开类问题 → 按"开发语境"再分一次**

开发类不是一条线,实测分成两处**不同源的语料**,必须按语境选:

| 开发语境的信号 | 走哪条 | 实测依据(2026-09-28 复测) |
|---|---|---|
| 苍穹侧开发:苍穹插件、Java 插件、`LoginAfterBase`、苍穹二开、开发助手 | `--product 87` | 词「插件开发」下 87 得 889 条,条目类目为 `金蝶AI苍穹` |
| 星空/BOS 侧开发:BOS 设计器、账表开发、设计 BOM、`BOS开发`、星空二开 | `--product 2` | 词「插件开发」下 2 得 73 条,**返回条目 10/10 全部是 `question`**;87 同一词返回 14 条里只有 2 条是问答 |
| 开发类但**分不清哪一侧** | `--product 87` | 87 是开发类的主语料;拿不准时不要猜第二条线 |

`--product 2`(星空侧二开问答专区)的**可执行判据是"返回条目类型恒为问答帖"**,
而不是某一条 total 数值(total 会随语料漂移)。2026-09-28 复测:

| 词 | `--product 87` | `--product 2` |
|---|---|---|
| 插件开发 | total 889,14 条里 knowledge/article/question 混排 | total 73,**10/10 全 question** |
| 账表开发 | total 11104,首条是 knowledge《"账表查询"检查项类型配置指南》 | total 1127,**9/9 全 question**,首条《简单账表如何进行分页呢?》 |

⚠️ 口径提醒:上表数字与早期记录(「插件开发」下 2 得 611 条)不同,原因是那次**没带
`--type` 过滤**、且上游语料在增长。**不要把 total 当判据**,看条目类型构成。

⚠️ `--product 2` 是**实测可用但文档长期未记录**的产品线 ID。它的存在本身就是
"开发类要分语境"这件事的硬证据,不要因为文档没写就不用它。

**③ 意图模糊 / 与产品线无关 → 留空,用默认 93**

- 问的是通用概念、跨产品线机制、或者你判不出属于哪条线 → **不传 `--product`**,默认 93;
- 想跨全部产品线扫一遍 → 传 `--global`(或显式 `--product 0`,两者语义不同:
  `0` = 不过滤,`--global` = 跨全部产品);
- ⚠️ 默认 93 **不等于**"用户指定了旗舰版",别这么写进答案。

**④ 同一问题横跨两条线 → 分两次搜,不要合并**

`--product` 一次只接一个值。开发类问题若确实横跨苍穹与星空两侧,就**分两次 `kd search`**
(一次 87、一次 2),各自挑标题,再合并判断。**不要**用 `--product 0` 图省事把两条线混在一起
——那正是 2026-09-06 串线事故的形态。

**核对**:传了 `--product 87` 后,看清单的 `effectiveProductId` 是否**等于你传的值**。
因为内核不再做任何推导,它**必然相等**——**不等即 bug**,报出来而不是照用。
没显式传参时它是默认 93,此时**不得**在答案里写"用户指定了旗舰版"。

## 置信度(内部判断,不输出)

**自己判断,不要把判断过程写进答案**(不要 JSON 头、不要分数、不要"置信度"字样):

- 读到的全文有段落直接说明了机制/字段/步骤 → 正常作答;
- 有相关材料但没覆盖用户问的那一点 → 正文点明「现有资料未覆盖 X」,**不要硬凑步骤**,
  并**反问一句关键澄清**(照官方 AI 的做法);
- 清单与问题不匹配 → 直说没查到,给确认渠道,**绝不编造菜单路径/字段名**。

判断依据(全部来自 search 清单的客观信号,同样不写进答案):

- `routeErrors[]` 非空 ⇒ 部分路失败,召回不完整,结论应更保守,可换词重试;
- `budget_exhausted:true` ⇒ 上游预算耗尽,清单不完整;
- `routesDegraded:true` ⇒ 路数塌缩,实际只有少数路在跑,覆盖面比预期窄;
- 清单里**没有任何标题**贴近问句 ⇒ 很可能是没查到,而不是"官方没有";
- 单条 `hitRoutes` 高但内容泛 ⇒ 别当作权威依据;精确专文常只在原句路命中。

## 回答规范

遵循 `docs/ANSWER-SPEC.md`(单一事实源):结构化 Markdown(原因分析→编号步骤→操作边界)、
表格、**引用 `knowledge`/`article` 给链接、`question` 只给标题与出处**(详见其第 3 条;
无自用编号、
不要求文末来源列表)、**根因引用规则**(question 引用用于症状对齐,根因解释必须引 knowledge 的
根因段落;官方发版说明需站外取原文)、资料未覆盖就诚实声明,
**不编造菜单路径/字段名/接口名**;社区内容标注「来自社区经验」;
引用一律用清单/全文里的原始 url 字段。

## 快捷方式

- `kd search "问题/报错原文"` —— **唯一入口**:多路拆词 + 只出标题清单,你挑完再读
- `kd search --kw "词1" --kw "词2"` —— 自己拆好词传入(路序=你给的顺序;第 1 个词自动充任原句路)
- `kd read <id> --kind <type>` —— 从清单取全文(kind 照抄清单里的 type;问答档是 `question`,传帖子号)
- 拿到全文后**自己合成**(默认不开子代理;规范见「第 3 步」)
- `kd health` —— 内核自检(库模式:确认公开面与路由规则已加载,排查环境问题先跑它)

## 内核或上游异常时

```bash
kd health --help   # 先看用法

```
