## 与部分轮的口径修正(重要)

| 口径 | 部分轮(20/28 例) | 完整轮(28/28 例) |
|---|---|---|
| usage recall@5 | 0.750(n=8) | **0.671(n=14)** |
| usage recall@10 | 0.750(n=8) | **0.710(n=14)** |
| 全池 recall@5 | 0.314(n=20) | **0.396(n=28)** |
| 硬指标 | 全部跳过 | 1.000(1/1) |

**0.750 不可作为基准。** 部分轮因 `--max-requests 40` 在 20 例处被截断,
usage 层只覆盖了池内前 8 个 usage 用例,剩余 6 例未跑。截断点不是抽样设计,
由此得到的点估计系统性偏向先跑到的用例。

同时须指出:**0.750 与 0.671 在统计上不可区分**。14 例 usage 的 recall@5
样本标准差 0.43,标准误 0.115,95% 置信区间宽达 [0.446, 0.897]。
两个点估计都落在此区间内,既不能据此声称检索"好",也不能声称"变差"。

## 票 #21 裁决依据的复核(推翻)

票 #21 关闭文案称「评测门 ❌ 未通过(词汇鸿沟存活率 1.0→0.0)」,据此关闭技术路线。
复核 `docs/eval-rerank-off.json` / `-on.json` 与服务日志 `logs/ksearch-service.log`,
**该 0.0 是预算耗尽事故,不是 rerank 造成的召回损失**。

证据链:

| 轮次 | JSON `upstreamCalls` | hardRow `upstream` | 服务日志对应行 |
|---|---|---|---|
| rerank-off | used 16 / cap 38 | 14 | `18:13:36 ... upstream 14 / 16 \| exhausted False` |
| rerank-on | used **6** / cap 38 | **4** | `18:18:13 ... upstream 4 / 4 \| exhausted True` |

ON 组实际消耗仅 6(搜索层 1 例 + `/ask` 4),且日志明示 **`exhausted True`**——
服务端单次 ask 预算被压到 4(正常上限 16),`/ask` 编排提前收尾,
gold 文档 `873372977646105600` 因此未进 sources。

**rerank 开关未参与该判定。** 两组运行的搜索层 `r5/r10/mrr` 完全相同
(0.333 / 0.333 / 0.333),OFF 组 pipeline 为 `{}`(默认态),
差异全部落在 `/ask` 层的上游消耗上。

**结论**:票 #21「评测门未通过」的判据不成立。该轮不能支持任何关于 rerank 的结论,
既不能判定其有害,也不能判定其无害。技术路线是否重开需以新评测为准。

## 关键观察

**reference 层低命中是结构性必然,不是检索质量指标。**
`usage` 层 gold = 真实使用问题 + 人工读全文核实;`reference` 层 gold = 官方 AI 的
recallDocuments。官方向量库与匿名搜索接口已知是两套索引,用官方 gold 评匿名检索
必然低命中。报告脚本已注明「reference 仅作参考,不作达标依据」。

**12 个零命中用例**中 9 个来自 reference 层,usage 层 3 个
(`exp-bom-molecule-limit`、`exp-production-unit-qty`、`use-bom-designer-page-2026-09-06`)。

**n=1 的硬指标是池设计缺陷,不是"样本偏小"。**
全池 28 例中仅 `seed-vocab-gap-bom-27000` 带 `hardMetric` 标签。
放宽上游预算**不改变**这两个数字的样本量——`vocabGapN` 与 `rootCauseN` 的
上限由评测集内容决定,与请求预算无关。要提升硬指标置信度**只能扩池**。

## 对「测 M」的判断(修正交接文档 §5)

交接文档称「usage 层 0.750 说明检索侧本来就不弱,故 M 可搁置」。**该前提不成立**:
0.750 的置信区间下界仅 0.446,不足以支撑"检索不弱"。

M 与检索侧优化的关系需重新表述:M 测量的是**官方语料覆盖度**,
而 usage 层 recall@5 测量的是**本方案在已覆盖内容上的检索能力**。
两者是不同维度,当前数据不足以对任一维度下结论。

现有可支撑的唯一结论:**硬指标维度观测点数为 1,任何基于它的技术路线裁决(含票 #21)均不成立。**

## 复跑指引

```bash
# 服务需先起(仓根);v6.1 基线态=rerank 关、cache 关
nohup python3 service/kingdee-ksearch-service.py 4097 &

python3 scripts/run_eval.py --configs baseline --topk 4 \
  --max-requests 120 --sleep 1 \
  --json docs/eval-baseline-v6.1-full.json --out docs/eval-baseline-v6.1-full.md
```

`--max-requests` 是全轮共享预算(搜索评测 + 硬指标共用),按响应
`stats.upstreamCalls` 累加。本轮实测 28 例 + 1 例硬指标 = 72,留 120 有充分余量。
