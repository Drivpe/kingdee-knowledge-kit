# ADR-0008:合成权移交调用方 agent;kd ai 命令删除

日期:2026-09-16 | 状态:已采纳(取代 ADR-0002 kd ai in-tree 的在线合成定位) | 关联:ADR-0002、ADR-0005、docs/ANSWER-SPEC.md

## 背景

`kd ai`(ADR-0002 立项)把「关键词规划 → 检索 → 按 ANSWER-SPEC 合成」三跳全部内置,依赖自接的 OpenAI 兼容端点
(`KAI_BASE`,默认 `http://127.0.0.1:4090`,`KAI_MODEL=glm-5.3-flash`)。该通道:

1. **与调用方无关**——它是独立旁路服务,不是当前对话的模型。同一问题被两个模型各自处理一次,
   而合成用的是其中较弱的一个;
2. **可缺席**——代码因此内建了整套降级机制(`fallback:true` + `_ai_fallback()`),把"通道可能没启动"当作常态;
3. **污染调用方上下文**——资料包(3 源 × 约 6000 字)直接进主对话,挤占调用方的历史上下文。

## 决策

**合成权移交调用方 agent。** 主路固定为:

```
用户 → 当前对话的 agent → kd ask 拿资料包 → 子代理按规范合成 → 返回「答案 + 结构化引用」
```

1. **删除 `kd ai` 命令**(`cmd_ai` / `_chat` / `AI_SPEC_PROMPT` / `_ai_fallback` / `_source_text`)。
2. **废除 `KAI_BASE` / `KAI_MODEL` 环境变量**;`kd` 只剩一个环境变量 `KSEARCH_URL`。
3. **链路上的 LLM 归零**:关键词拆解本就是规则式(`query_routes.json` 外置词表,`plan_routes()` 不走模型),
   删掉 LLM① 后,整个套件 = 纯规则 + 纯 HTTP,**零模型依赖**。套件定位收缩为「检索内核 + 资料包」。
4. **子代理只做合成,不做检索**——拿到 `kd ask` 的资料包后按规范写答案,不自行搜索、不自行读网页。
   返回物 = 完整答案正文 + 结构化引用清单(`n/title/type/entityId`)。
5. **规范交付形态**:`ANSWER-SPEC` 要点、置信度三档、产品线粘性规则**内嵌进 `SKILL.md` 的子代理提示词模板**。
   不得依赖 harness 默认注入——独立子代理看不到主对话,其系统提示词为通用 agent 提示,不含本项目规范。

## 后果

- **成本结构变化**:原为 1 次 LLM 调用(`glm-5.3-flash`);现为 1 个子代理会话(完整 agent 循环,可能多轮工具调用)。
  延迟与 token 均上升,换来合成质量取决于调用方模型(而非套件绑定的弱模型)与上下文隔离。
- **上下文隔离**:资料包长文本不再进主对话,只回传成品与引用。
- **失去确定性合成**:调用方 LLM 每次输出可能不同,不再有"固定模型 + 固定提示词"的可复现性。
  自动化/非 agent 环境若需要确定性合成,自行在调用侧实现。
- **文档自洽性维护**:README 的「AI 合成」与「模型通道」两节、`kd health` 的通道状态、
  `tests/verify_ksearch.py` 的假 OpenAI 端点用例、`install.sh`/`install.ps1` 的相关开关须同步清理,
  否则仓库将出现"文档说有、代码里没有"的矛盾。

## 备选与取舍

- **保留 kd ai 作备用通道**:被否——两条合成路会各自演化,且 `fallback` 常态化的设计本就是把
  "旁路服务可能没起"当成正常态,不是可靠备份。
- **保留 kd ai 但改为调用调用方上下文**:物理上不可行——CLI 无法访问调用方 agent 的上下文。
- **主路仍走 kd ai、置信度写进 cmd_ai**:被否——与"合成权移交"冲突,且要在弱模型上重复实现一遍规范。
