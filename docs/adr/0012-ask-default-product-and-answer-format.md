# ADR-0012:ask 默认产品线 93 + 答案形态改按官方可读优先

日期:2026-09-17 | 状态:已采纳 | 关联:ADR-0008(合成权移交)、ADR-0010(召回置信度三档)、
ADR-0009(原句路)、ADR-0007(引用形态,部分条款本次更正)

## 背景

本 ADR 记录 2026-09-17 三项决策,它们共同改变了「agent 怎么问」与「agent 怎么答」:

**其一:检索默认不带产品线,代价被实证。** `kd search` 的 `--product` 默认 93,
但 **`ask` 的默认是 `None`**(`cli.py` 旧第 206 行),而 `ask` 才是常规入口。实测同一问题:

| 检索轮次 | 命令 | `effectiveProductId` | 召回含目标文档 |
|---|---|---|---|
| 第 1 轮 | 不带 `--product` | `null` | **0 条** |
| 第 2 轮 | `--product 93` | `93` | **2 条**(含官方报错条目) |
| 第 3 轮 | `--product 93` + 精确报错原文 | `93` | 2 条 |

同一份语料,不带过滤时目标文档零命中。默认值缺失不是"更中立",而是**让常规提问落到更差的召回**。

**其二:2026-09-06 串线事故后立的三条硬规则,其前提已在事实上消失。** 事故条款要求
「同一会话内首次 `ask` 确定的 product 路由必须贯穿后续调用;禁止中途变道 `--product 0`、
禁止换用其他产品线、**禁止不带 --product 重新检索**」。其中第三条的语义前提是
"不带 `--product` 等于不过滤"。一旦把 `ask` 默认改为 93,**这个前提不再成立**——
"不带"变成"默认旗舰版",而不再是"不过滤"。

**其三:答案形态偏离了产品的原生形态。** 对照官方 AI 回答(三条真实分享对话)与本套件输出:

| 维度 | 官方 | 本套件(改前) |
|---|---|---|
| 开头 | 直接定性结论 | 一行 JSON `{"confidence":…}` |
| 引用 | 正文内无编号;有配图 | `[n]` + 「源6」两套编号并存 |
| 末尾 | 无 | 审计披露/复盘段 |
| 文档链接 | 可点 | 明文禁止当作可点依据 |

官方的可读性来自**极简**;而本套件的 `ANSWER-SPEC` 第 3 条与 ADR-0007 把
「正文标 `[n]` + 文末 `## 参考来源`」定为硬要求,并把 `kd read <chunkId> --chunk`
当作溯源依赖 —— 后者**从未落地**(官方无「按文档列全部 chunk」端点,`cli.py` 里该命令直接报错)。

## 决策

### 决策 1:`ask` 默认 `product_id=93`,问句产品词优先于默认

- `ask` 签名改为 `product_id=93`(原 `None`),CLI `--product` 同步默认 93;
- **问句里的产品词覆盖默认**:`_plan_routes` 中把 93 视为"用户没说时的兜底"而非
  "覆盖用户所说"——问句含「苍穹」「企业版」等别名时按 `productAliases` 推导并覆盖;
- **要真正的不过滤必须显式传 `--product 0`**。这是本决策的必然代价,已在
  `ask` docstring 与 ANSWER-SPEC 第 8 条写明。

**撤销三条硬规则。** 产品路由粘性的三条硬规则(禁不带 --product、禁变道 0、禁切其他产品线)
全部撤销:
- 第一条因默认值变更而失去对象;
- 后两条被判定可由默认值自然规避。

#### 后续更正(2026-09-27):推导只覆盖默认兜底值,不覆盖显式传入值

本决策的原意是"默认 93 是**用户没说时的兜底**,不是覆盖用户所说"——这句写在决策 1 里。
但实现把推导写成了**无条件覆盖** `product_id`,于是它覆盖的不只是兜底值,连调用方
**明确传入**的值也一并改写:

- 显式 `--product 0`(本决策自己规定的"唯一能拿到不过滤的方式")+ 问句含「苍穹」
  → 被改写成 `87`,该语义**静默消失**;
- 显式 `--product 87` / `1` 同样会被问句字面改写。

根因经 `git log -S "if not product_id"` 核实:本 ADR 之前的 `search()` 默认值是 `None`,
推导覆盖的是"无兜底"语义;**本 ADR 把默认值改成 `93` 后,同一条推导自动变成了覆盖用户的真实输入**
——是默认值的变更让原本无害的写法越了权。

**更正内容**:`_derive_product_id` 只在 `product_id` 为 `None` / `93`(默认兜底)时推导;
任何其他显式值一律尊重调用方。这与本决策原文"93 是兜底而非覆盖用户所说"**方向一致**
(原文只说了"不覆盖用户所说",并未涉及"判定权归谁");
具体到代码,就是把该表述真正贯彻,而非推翻决策。

⚠️ **另有本轮新增的一层约定**(超出本 ADR 原文范围,在此显式登记,不冒充原意):
**产品线判定归调用层(LLM)**——调用方读出意图、显式传 `--product N`,内核不做字面二次改写。
原 ADR 只规定了默认值语义,没有规定"who decides";这条是 2026-09-27 为落地
"用语义替换字面匹配"而新增的,与"收窄推导"配套成立。

**边界与已知缺陷**:推导仍是纯子串匹配(无否定处理),多别名同现的裁决规则与
`sources` 入参契约见 spec 第 2.3 节缺陷 E;显式值不被覆盖见缺陷 F。

**但事故事实保留**——2026-09-06 的串线事故(agent 把 `--product 93` 变道为 0、
召回 ENG_BOM/T_ENG_BOM 并当作旗舰版输出)是历史记录,写入本文档而不抹除;
`ANSWER-SPEC` 第 8 条与 `SKILL.md` 保留事故原文段,供未来追溯"为什么曾经有这条规则、
又为什么撤了"。**规则撤销不等于教训作废**:会话内因检索不顺手就来回切 `--product` 仍是
被明确劝阻的做法,只是不再以"硬规则"形式强制。

### 决策 2:默认不开子代理,由合成方直接作答

`SKILL.md` 原写「长资料包建议**开子代理**隔离上下文」。实测该做法净成本为负:

- 子代理**看不到主对话**,harness 给的是通用 agent 提示,**不含本技能任何规范** ——
  每次都要把整套规范原样复制进提示词;
- 交付常不完整:实测子代理"完成"后**只回状态摘要、不交正文**,追问一次才拿到;
- 会**错判置信度**:实测把一份已有官方专属条目的报错判为 `partial`,理由是"未覆盖触发操作"
  —— 而那份文档当时不在它拿到的资料包里。

**决策**:默认不开子代理,自己读资料包自己答;**仅当资料包明显超长**(长帖、topK 拉满)
或一次要合成多份时才考虑开,且要求它**返回完整正文**。

### 决策 3:答案形态改为可读优先,并更正两条错误表述

- **去掉正文里的元信息**:不输出 JSON 置信度头、「源N」自用编号、文末参考来源节、
  结尾审计披露/复盘段。三档置信度(`answerable`/`partial`/`uncovered`,ADR-0010)
  **保留为内部判断依据**,不再外显;
- **引用改为可点击角标**:`[标题](https://vip.kingdee.com/knowledge/<id>)`。实测该路径
  **匿名可访问**(HTTP 200 且含正文);
- **`partial`/`uncovered` 时反问一句关键澄清**(照官方 AI 做法),而非堆一段缺口声明。

**更正两条实测不成立的表述**:

| 原文 | 实测(2026-09-17) |
|---|---|
| 「vip.kingdee.com 网页路由匿名**一律** 302 登录墙,禁止作为溯源依赖」(ANSWER-SPEC 第 3 条 / ADR-0007) | **按路径而异**:`knowledge/<id>` → **HTTP 200 且含正文**;`article/<id>` → 302 到 **`knowledge/<新id>`**(路径迁移,最终 200);`question/<id>` → 302 到 `/error/404`(**帖子被删**)。三条路径**没有一条是登录墙** |
| 「`kd read <chunkId> --chunk` 匿名调官方溯源端,引用永不 404、离线可重取原文」(同上) | 该端点**从未落地**,`cli.py` 里该命令直接 `_fail` |

**对 ADR-0007 的更正说明(不改写原文,在此声明)**:ADR-0007 记录 2026-09-06 事故为
「agent 引用 4 条 `question\|article/{id}` 链接,用户点击全部 404 —— 实测这些网页路由匿名
一律 302 登录墙,故改用 `entityId+chunkId` 溯源」。本次实测表明:

- 那次事故采样的**全是 `question/` 与 `article/` 路径**,却推广成了"一律"(含 `knowledge/`);
- 这两类路径的 302 真实成因是**帖子被删**(→ `/error/404`)与**路径迁移**(`article` → `knowledge`),
  **不是登录墙**;
- 因而 ADR-0007 决策 3「网页 URL 只作记录、禁止作为溯源依赖」**建立在一个被误诊的前提上**,
  其补偿机制(`entityId+chunkId` + `kd read --chunk`)也因此长期无人能用、最终未落地。

本 ADR 不修改 ADR-0007 原文(保持历史可追溯),但**其决策 3 的适用范围收窄为**:
`question/` 与 `article/` 两类路径的 URL 不可靠(会因删除/迁移失效),`knowledge/` 路径可点。

### 后续更正(2026-09-27):`article/` 路径实测不重定向

上文「更正两条实测不成立的表述」表中记 `article/<id>` → **302 到 `knowledge/<新id>`(路径迁移)**。
2026-09-27 复测**不支持**该断言——本轮实测的 `article/` 样本是**首跳 200、最终 URL 原地不变**:

| 路径 | 样本 | 首跳码 | 最终码 | 最终 URL | 正文字节 |
|---|---|---|---|---|---|
| `article/648135211787498752` | 1 条 | 200 | 200 | **原地**(非 `knowledge/`) | 454237 |

同一轮复测中 `knowledge/` 8/8 仍为 200 原地、`question/` 6/6 仍为 302 → `/error/404`,
两类的判定与上文一致。

**口径修正(以本节为准)**:`article/` 的 URL **不是必然迁移**;是否迁移**逐条判定**,
而判定的唯一可靠方法是**看跟随重定向后的最终 URL(`url_effective`)**,不得只看 HTTP 状态码
——`question/` 的最终状态码恰为 200(成功重定向到 404 页),只看状态码会把失效帖误判为可贴
(六条 `question/` 样本最终字节数**全部为 399522**,即同一张 `/error/404` 页)。

可执行口径已落 `docs/ANSWER-SPEC.md` 第 3 条:引用优先 `knowledge/`,`article/` 可贴,
`question/<questionId>` 不贴链接。**上文"已知偏差"中把 `article` 与 `question` 并列为"URL 不可靠"
的表述据此收窄**:`question/` 是删除(不可贴),`article/` 实测可访问(可贴)。

## 备选(被否)

- **只改文档、不改代码**(把 `--product 93` 写成"惯例"):被否——实测证明默认值缺失
  直接导致目标文档零命中,"惯例"无法约束调用方,且 `ask` 是唯一常规入口,该处默认值才是真缺口。
- **保留三条硬规则,只删第一条**:被否(由决策方明确否决)。保留理由是"后两条才是事故直接原因",
  但决策方判定默认值已使其具备自然规避能力,规则冗余。
- **保留 `[n]` 编号制、只删「源N」口语编号**:被否。决策方要求引用**可点击**;
  编号制不可点击,且其配套的 `entityId+chunkId` 离线重取路径从未落地。
- **把 JSON 置信度头挪到正文末尾**:被否。它无论如何都是元信息,对答案读者无价值;
  三档转为内部判断已足够满足 ADR-0010 的诚实要求。

## 影响

- **对外契约变更**:`ask` 签名的 `product_id` 默认值由 `None` 改为 `93`。
  守卫 `check_core_surface.py` 的 `SIGNATURE_BASELINE` 已同步;
  库调用方不传 `product_id` 时行为改变(原不过滤 → 现旗舰版)。
- **回归基线同步**:`t_product_id_zero` 原本断言「省略 `product_id` 应回显 `None`」,
  该断言建立在"省略=不过滤"的旧前提上,已改写为断言新契约(省略 → 93、显式 0 → 0、
  问句含「苍穹」→ 87)。
- **`ANSWER-SPEC` 第 3、5、8 条与反例节改写**;`SKILL.md` 的合成节、置信度节、
  产品线节、快捷方式节改写。
- **文档链路更正**:`knowledge/` 链接从"禁止当依据"改为"可点击依据"。

## 后续更正(2026-09-18,ADR-0013)

本节记录本轮变更对本 ADR 的影响,**不改写上文原文**(保持历史可追溯)。

**1. 决策 1 的对象 `ask` 已整体删除,但其口径由 `search` 承接。** 本 ADR 把 `ask` 的
`product_id` 默认值由 `None` 改为 `93`,并撤销三条产品线硬规则。ADR-0013 删除 `ask` 后:

| 项 | 原落点(已删除) | 现落点 |
|---|---|---|
| `product_id` 默认 93 | `ask()` 签名 / CLI `ask --product` | **`search()` 签名 `product_id=93`**(`src/kd/_impl/_public.py`)/ **CLI `search --product` 默认 93**(`src/kd/cli.py`) |
| **`effectiveProductId` 顶层键** | `ask` 返回体顶层独有(旧 `search` 无) | **`kd search` 清单返回体顶层**(`src/kd/_impl/_manifest.py`),语义=经 `_plan_routes` 推导后**实际生效**的值 |
| 问句产品词优先于默认 | `_plan_routes` 中把 93 视为兜底 | **2026-09-27 收窄**(见下):推导**只覆盖默认兜底值**(`None`/`93`),不再覆盖调用方的显式传入值 |
| 要真正的不过滤须显式 `--product 0` | `ask docstring` + ANSWER-SPEC 第 8 条 | **不变**,口径改挂在 `search` 上;且显式 `0` 自 2026-09-27 起不再被问句字面改写 |
| 三条硬规则已撤销 | — | **不变**,撤销状态继承 |

> `effectiveProductId` 一行是**执行期由契约走查发现的真实功能回退**:本轮 spec 第 3 节的返回结构设计漏列该键,
> `ask` 删除后调用方将失去唯一可执行的产品线判据(而 ANSWER-SPEC 第 8 条依赖它),
> 已于 2026-09-18 在内核侧补回(spec 第 3.3 节记录裁决与实测三态:默认→93 / 问句含「苍穹」→87 / 显式 0→0)。
> 补回零额外成本——`_plan_routes` 早已算出该值,只是未外露。

**结论**:决策 1 的**内容全部仍然有效**,只是承载命令从 `ask` 换成 `search`——
`search` 本就是 2026-09-17 起的事实常规入口,本次只是把 `ask` 那半边删掉。
`ANSWER-SPEC` 第 8 条与 `CONTEXT.md` 中的 `ask` 表述已同步改为 `search`(v2.4)。

**2. 决策 2(默认不开子代理)仍然有效,且理由未变。** 其论证建立在"子代理看不到主对话、
交付不完整、会错判置信度"三条实测上,**全部与 `ask` 是否存在无关**。`CONTEXT.md` 的
「合成权」词条已据此改写为「默认不开子代理,由合成方直接作答」。原措辞里的
「仅当**资料包**明显超长」应读作「仅当**清单**明显超长或一次要合成多份」。

**3. 决策 3(答案形态可读优先)仍然有效,两处依赖被替换。** 去掉正文元信息、
引用改可点击角标、`partial`/`uncovered` 时反问一句——三条均不变。
但决策 3 的「去掉正文里的元信息」曾把 **`synthesisBrief`** 一并归类为元信息而不外显;
`ask` 删除后 **`synthesisBrief` 与 `_synthesis_brief()` 整体不存在**,
判定依据改由 `kd search` 的清单信号承担(`hitRoutes`/`routeErrors`/`budget_exhausted`/`routesDegraded`),
详见 ADR-0010「后续更正(2026-09-18)」节。
引用可点击角标的「按路径而异」口径(`knowledge/` 200 可点、`question/` 帖子被删)
**原样保留,未变**;`article/` 一项按 2026-09-27 复测更正为"实测 200 原地可贴"(见上「后续更正」节),
判定一律以**最终 URL** 为准。

**4. 「影响」节里的契约变更条目已随 `ask` 删除而失效。** 原文写「`ask` 签名的 `product_id`
默认值由 `None` 改为 `93`」,该签名已不存在;守卫 `check_core_surface.py` 的 `SIGNATURE_BASELINE`
已按新契约(`search` / `read` 两个函数)重写,`ask` 条目移除。原文的
「回归基线同步」提到的 `t_product_id_zero` 亦随之改写为针对 `search` 的用例。

## 未决/残余

- `get(question/<id>)` 路径的 404 是"帖子被删"还是别的成因,只抽样验证了 1 条,未做统计;
  ⚠️ **2026-09-27 补充**:本轮 6 条 `question/` 样本**全部**落到 `/error/404`(最终字节数一致),
  删帖成因而非偶发;**但 `article/` 的迁移成因随之被证伪**——该路径本轮实测 200 原地,
  故上文"路径迁移"的原始归因**仍然缺少可复现样本**(旧记录未留存具体样本 id);
- 「不开子代理」的代价是长资料包占用主对话上下文,该代价在超长帖场景未做量化;
- 三条硬规则撤销后,若未来再现串线事故,需重新评估是否恢复限制——**本 ADR 是其重启依据**。
