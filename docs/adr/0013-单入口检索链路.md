# ADR-0013:单入口检索链路 —— 删 ask、零算法排序、内核拆包

日期:2026-09-18 | 状态:已采纳 | 关联:ADR-0012(ask 默认产品线与答案形态)、ADR-0010(召回置信度三档)、
ADR-0009(原句路)、ADR-0005(多路检索路由)、ADR-0011(去服务化)、
契约输入 `docs/specs/2026-09-18-单入口检索重构.md`

## 背景

2026-09-17 已经把 `search` 升级为「多路拆词 + 只出标题清单」,并作为常规入口公开论证;
但那次改造**只动 search,不动 ask**(spec 裁决⑤原文:「`ask` 的融合路径本轮不动」,
把 ask 的去留标为「应开新票决策」)。于是内核里同时存在两条路径、**两套互相矛盾的排序哲学**:

| | `ask`(旧常规入口) | `search`(2026-09-17 起常规入口) |
|---|---|---|
| 排序 | RRF 融合分 `1/(60+名次)` 求和 | 命中路数降序 + 上游原生序 |
| 交付物 | 资料包:命中 + topK 深读全文 | 清单:标题级条目 |
| 决策者 | 内核(替你挑 topK) | 调用方(给你挑) |

**两条路都不是"零算法排序"**,只是错法不同。RRF 的问题上一轮已实测清楚:

实测对照(检索词 `应用为禁用状态[网关]`,产品线 93,同一时刻):

| 路径 | 目标文档《金蝶AIOpenAPI错误码说明》排名 | 能否读到 |
|---|---|---|
| 上游 `/api/search` 原生排序 | 第 5 | — |
| `kd search` | 第 5 | ✅ |
| `kd ask --topk 4`(RRF 融合后) | **第 8** | ❌ 在 topK 之外 |
| `kd ask --topk 8` | 第 8 | ✅ |

根因在 `_rrf_fuse` 的评分形式:`1/(60+名次)` 求和。它把每一路的**绝对排名**压成一个按名次倒数的
分再加总,**消灭了"哪一路命中的"这个信息**。后果双向:

- **奖励泛泛文档**:一篇被四路各排到第 20 名的文档得 `4 × 1/80 = 0.05`;
  而一篇被原句路精确命中、排第 1 的文档只有 `1/61 ≈ 0.0164` —— 精确的那篇**必然输给四路都不精确的那篇**;
- **惩罚单路精确命中**:目标文档恰好只在原句路命中(这正是**词汇鸿沟**场景的定义),
  它在融合里拿不到任何"多路加成",被压到 topK 之外。

**同一份上游数据,官方的综合排序已经排好了**——`/api/search` 原生把目标放在第 5,
是内核的融合把它推到第 8 并截断掉。用户 2026-09-18 的拍板正是冲着这个事实:

> 「你是用官方的综合排序用不同关键词搜索的,所以结果已经排过序了,因此我们要做的就是删除重复的内容,
> 让 llm 自行判断需要阅读哪篇」

## 决策

### 决策 1:保留 `kd search`,`kd ask` 全删

`ask` 子命令**真删除**,不留 "unsupported" 占位;`ask()` 从 `kd.core` 白名单移除,
`hasattr(kd.core, "ask") is False`,并把 `ask` 加入守卫的 `FORBIDDEN_NAMES`(回归钉子:防它被搬回来)。

链路由两跳收敛为一跳半:

```
用户 → 调用方 agent → kd search 出清单 → 按标题自己挑 → kd read 取全文 → 按 ANSWER-SPEC 合成
```

**为什么是删而不是「ask 内部改为调 search + 深读」**:后者会让"挑哪几篇深读"这个判断
**重新落回内核**——那正是本 ADR 要消灭的东西。深读哪篇是调用方的判断,内核不该有一条
替它决定的路径;留一条,两套哲学就还在。

### 决策 2:**零算法排序**——连「按命中路数排序」也删

> ⚠️ **本决策被 ADR-0016 加强**(2026-09-28,v6.6),两处措辞已失效,读时按下面口径:
> * 「路序来自 `_plan_routes` 的**路定义顺序**」——`_plan_routes` 已**不再定义**任何路,
>   它只把调用方给的词逐字转成路。故路序的**唯一来源**是调用方给词的顺序;
> * 「(原句路恒为第 1 路)」——原句路随 ADR-0009 **整体废止**,该括注作废。
>
> 决策的**实质**(排序键不含任何内核算出的量)不变,且更强了:内核现在连"路"都不生成。

排序键只剩 `(路序, 路内上游名次)`,两者都**不是算出来的**:路序来自 `_plan_routes` 的路定义顺序
(原句路恒为第 1 路),路内名次直接来自上游返回顺序。

`hitRoutes` **降级为纯信息字段**——照旧算、照旧返回、供调用方参考,**不参与排序键**。
旧实现的排序第一维 `-len(hits)` **必须删除**。

**为什么连命中路数排序也要删**(这是本轮最容易被误读的一条,单独论证):

**其一,它同属"算法评分"。** `hitRoutes` 仍然是一个**由本内核算出来的量**。按它排序,
就是在官方综合排序之上**再叠一层我们自己的权重**——与决策 1 要消灭的错误同构。
用户的原话是「只去重,让 llm 自己判断」,**没有给"命中路数"开例外**。

**其二,它的失败已经被实测过。** 2026-09-17 的 spec 附录记录了按路数排序的实际输出:

| # | type | hitRoutes | title |
|---|---|---|---|
| 1–5 | knowledge/answer | **2** | 5 篇泛文(如「预算模板使用状态显示"禁用"是怎么回事?」) |
| **6** | knowledge | **1** | **金蝶AIOpenAPI错误码说明** ← 目标文档 |

**目标文档被 5 篇泛文压在第 6 位** —— 这就是路数排序的实测成绩。

**其三,路数不是独立信号,是窄路位次的冗余编码。** 同 spec 实测:两路 top30 的**交集 = 21/30(70%)**,
因为路 B(泛词路)宽得多(上游 total 4285 vs 路 A 的 1761),路 A 的前部几乎必然落在路 B 的 top30 内。
于是「命中 2 路」实际等价于**「在路 A 靠前 且 没掉出路 B 的 30 名」** —— **路 A 的位次才是决定因素**。

**其四,它把上游的临界抖动放大成整档差。** 路 A 上目标的位次实测在 **第 5–6 位之间摆动**
(连续 4 次:5, 5, 6, 5,`totalElements` 恒为 1761);而每路只取前 10 条。于是「路 A 第 5-6 名」
与「路 A 第 1-5 名」的微小差距,被路数的**二分法**(2 路 vs 1 路)放大成档位差,目标被整体推到 2 路组之后。

**其五,spec 自己立过这条防线。** 2026-09-17 spec 写明:

> ⚠️ **任何加权重方案都要先回答**:本轮废弃 RRF 的核心理由是"加权是黑箱、且奖励泛泛命中"。
> 若新增权重,必须论证它为何不是同一个错误的重犯。**在论证清楚之前,保持零加权。**

路数排序**就是这个错误的重犯**:它同样是黑箱加权,同样**奖励泛泛命中**(四路都泛泛命中的文档
得 `hitRoutes=4`,原句路精确命中的得 1)。它的"可解释"只是把一个黑箱分数换成了一个黑箱计数——
调用方看到 `hitRoutes=2` 并不比看到 `0.05` 更知道该读哪篇。

**去掉它之后,顺序完全继承上游**:上游把目标排第 5,清单里它就是第 5 条(同路内),不再被任何
内核权重挪到第 6。**这是本轮唯一的排序行为变更,也是最关键的一条。**

### 决策 3:`_core_impl.py` 按职责簇拆成 `kd/_impl/` 包

`_core_impl.py` 已长到 **1331 行 / 47 个顶层定义**,一个文件里堆着网络、配置、限速、拆词、
清单编排、详情深读、公开函数七类职责。拆成包,按**职责簇做 seam**:

```
src/kd/_impl/
  __init__.py    # 装配层:汇集公开函数 + 异常 + health 观测口依赖
  _errors.py     # UpstreamError / QueryTooLong / InternalError
  _config.py     # 常量、_route_cfg、预算、_Budget、_RateLimiter、_rate_profile、上游计数
  _net.py        # _get_json、clamp_query
  _text.py       # html2text、_title_of、_is_true
  _upstream.py   # _search_upstream、_norm_item、_URL_OF、ENTITY_KINDS
  _routes.py     # _plan_routes、_salient_chunks
  _manifest.py   # _route_search_once、_search_manifest、_manifest_key/rank/fuse/project
  _detail.py     # _knowledge_article、_question_detail、_article_detail、_detail、_answer_brief
  _public.py     # search()、read()
```

**拆分的性质是「搬家」,不是重写。** 行为等价红线:除本 ADR 决策 1/2 与 spec 第 2.3 节明确列出的
改动外,**上游请求数、请求参数、字段取值逐条不变**。

**命名空间隔离机制不变**:`core.py` 只 import 载体(现为 `kd._impl`),不在自身命名空间留下任何内部名;
`core._impl()` 返回**包对象**;health 经它读的每个内部件必须仍可解析(守卫判据 7)。

## 备选(被否)

- **保留 ask 作为「次要入口」**(2026-09-17 的处置):被否。它把两套排序哲学留在同一内核里,
  且实测已证 ask 在报错码类问题上**读不到目标文档**——一个会静默给出更差结果的次要入口,
  比没有入口更糟(调用方无法区分"官方没有"与"被融合吃掉了")。
- **ask 保留但内部改为「调 search + 深读 topN」**:被否。深读选择权会重新落回内核
  (见决策 1)。
- **保留命中路数排序,只去掉 RRF**:被否。这是上一轮已落地的形态,实测目标排第 6;
  且它同属算法评分(见决策 2 其一至其五)。
- **把命中的窄路(原句路)位次作为主键、路数仅作 tie-breaker**:被否。方向正确但**多此一举**——
  排序键取 `(路序, 路内名次)` 时,原句路恒为第 1 路,原句路命中的条目**已经**天然排在最前,
  等价于"窄路位次作主键",却不需要引入任何按路类型加权的特例。
- **每路取更多条(20 而非 10)以缓解截断**:被否。它治的是路数排序的截断病灶;
  病灶(按路数排序)已删,无需付出双倍请求。
- **保留 `_core_impl.py` 单文件,只删 ask**:被否。删完仍剩约千行、六类职责;
  而本轮的删除动作恰好把文件的职责边界暴露清楚——**趁改动窗口拆,比下次再动一次便宜**。

## 影响

- **对外契约变更**:`kd.core.__all__` 从 6 个公开名缩为 5 个
  (`search` / `read` / `QueryTooLong` / `UpstreamError` / `InternalError`);
  `search` 签名新增 `keywords=None`、`text` 改 `None`、`routes` 改名 `max_routes`、
  删 `rerank`;`read` 删 `refresh`。
- **`search` 返回结构新增顶层键 `effectiveProductId`**(语义见 spec 第 3.3 节):
  该键原为 `ask` 返回体顶层独有,`ask` 删除后若不补,**调用方将失去唯一可执行的产品线判据**
  ——`ANSWER-SPEC` 第 8 条明确要求"引用与合成前核对 `effectiveProductId` 是否等于预期产品线 ID",
  而 `results[].products` 装的是上游中文类目名、值域不可比,无法替代。
  这是**执行期由契约走查发现的真实功能回退**(本轮 spec 第 3 节的返回结构设计漏列该键),已于 2026-09-18 补回:
  值 = 经 `_plan_routes` 推导后**实际生效**的产品过滤(默认 93 / 问句含「苍穹」→ 87 / 显式 0 → 0),
  **不得**回显调用方传入的原始值(否则别名覆盖不可见)。补回零额外成本——`_plan_routes` 早已算出该值。
- **删除清单**(随 ask 一起走,删净不留):`ask()`、`_ask_bundle`、`_synthesis_brief`、
  `_rrf_fuse`、`_select_top`、`_fused_key`、`_knowledge_search`、`_chunk_text`、`_top_chunks`、
  `_rerank_bonus`、`_fresh_bonus`、`_terms`、常量 `RRF_K`、`RERANK_DEFAULT`。
  `query_routes.json` 同步清理:`searchPageSize`、`deepRead`、`displayOrder`、
  `budget.maxUpstreamPerAsk`、`rate.note` 里的 `background` 承诺、`note` 里的 RRF 表述。
  ⚠️ **`effectiveProductId` 是唯一的例外**——它是 ask 返回体的顶层键,但**不随 ask 删除**,
  而是**迁到 `search` 的清单返回体**(见上一条):删的是 ask 这条命令,不是这个判据。
- **文档链路更正**:`CONTEXT.md` 的「资料包」词条改为「清单」、「chunk 切片」标注随 ask 取消、
  「chunk 溯源」的链接禁令改为按路径而异(ADR-0012 实测)、「召回置信度」判定依据改为清单信号;
  `ANSWER-SPEC` v2.3 → v2.4(链路改为清单→挑→read→合成,删 `chunks` 依赖);
  ADR-0010/0012 各追加「后续更正」节,原文不改写。
- **回归基线同步**:`tests/kd_regression.py` 删全部 `t_ask_*` 用例;
  `scripts/check_core_surface.py` 的 `PUBLIC_API` 去 `ask`、签名基线按新契约重写、
  `FORBIDDEN_NAMES` 加 `ask`。
- **请求量下降**:删掉 ask 后,常规链路从「7 路检索 + 多次深读」降为「7 路检索 + 按需 read」——
  **深读次数由调用方决定**,不再由内核按 topK 固定消耗。

## 未决/残余

- **零排序后,清单前部被泛文占据的问题仍在**,只是不再被内核放大。实测路 B(泛词路)是
  OR 语义、上游 total 达 4285,其前 15 名里塞满语义无关文档(`应用`/`状态`/`网关` 单用无区分度)。
  治它要动 `query_routes.json` 的拆词规则(停用词表、单字词不单独成路),**属独立票**,
  本轮只改执行链、不改拆解逻辑。
- **报错类问题的检索词预处理**(提取 `errorCode` 作原句路、中文描述降为辅助)未做,
  是上一轮 spec 就标出的"最高优先级改进方向"。
- **`search` 的 `page` 语义是清单分页**(不是上游分页),该变更是 2026-09-17 引入的,
  本轮未再动;若出现"第 2 页是哪一路的第 2 页"这类误读,需要再澄清一次。
- 拆分后的包内模块间存在**函数级循环依赖风险**(`_routes` 读 `_config` 的配置、
  `_manifest` 调 `_routes` 与 `_upstream`)——当前靠 `_impl/__init__.py` 装配层收口,
  未引入更严格的边界检查;若未来模块数继续增长,需要评估是否加依赖方向守卫。

## 后续更正(2026-09-28)

⚠️ **决策 2 的"零算法排序"契约未变**,但其中一句关于**路序**的表述已过期:

本 ADR 多处写「原句路**恒为第 1 路**」(决策 2 与备选节)。新增**稀有数字 token 路**后,
问句里含 ≥3 位纯数字串时,原句路退到**第 2 位**(`_routes._EXEC_ORDER`:
`token → raw:question → 其余 → product`)。

- **排序键的结构没变**(仍是 `(首次出现的路序号, 该路内上游名次)`),故零算法排序**不受影响**;
  变的只是"第 1 路的**内容**",从未引入任何分数/加权/rerank;
- 「原句路**保席位**」按 `_TRUNC_PRIORITY` 保持,且截断时优先级**高于** token 路
  (见 ADR-0009 的后续更正);
- 因此备选节那句「排序键取 `(路序, 路内名次)` 时,原句路恒为第 1 路,原句路命中的条目**已经**
  天然排在最前」在含数字 token 的问句上不再成立——这是有意的权衡:token 路的收窄能力
  远强于原句路(实测候选集从四位数压到个位数),让它居首带来的收益大于"原句永远第一"。

## 后续更正(2026-09-28,ADR-0016)

| 本 ADR 的决策 | 处置 |
|---|---|
| 决策 1(单入口 `search` → 挑选 → `read`) | **保留,不变** |
| 决策 2(零算法排序:内核只去重、不产生任何评分) | **保留并加强**。ADR-0016 把"路的先后"也收走:内核不再自行生成或排序检索词,路序**逐字等于调用方给词的顺序**。即内核在检索侧的职责进一步收敛为"原样发送 + 去重归并" |
| 决策 3(内核拆包,`kd.core` 公开面 5 名) | 保留,不变 |

⚠️ **对决策 2 的加强不是修订,是同一方向的延伸**:本 ADR 判定的越界形态是"内核产出排序分",
ADR-0016 追加判定"内核替调用方排词序"为同类越界(它同样是在改变召回结构,
只是改的是第一维而非分值)。两份 ADR 合起来构成**内核检索职责的完整边界**:
不生成词、不排词、不评分、不挑选、不合成。
