# ADR-0017:上游频率红线的重新读数 —— 交互链路只有一处数字,并把它上调到 burst 7 / rps 5

日期:2026-09-29 | 状态:已采纳 | 关联:ADR-0004(发现层双轨,**其 1 req/s 与 ≤200 只约束已删除的采集脚本**)、
ADR-0011(去服务化,其决策 5 的跨进程限速**条件不成立**)、ADR-0013(零算法排序,不动)、ADR-0016(检索词生成权移交)
| 承接:2026-09-29 架构审查会话(报告 `.scratch/architecture-review-20260929-115729.html`)+ 同日逐条裁定

## 背景

用户在架构审查后提出一条实际痛点:**「agent 执行这个搜索太慢了」**,并问
**「是不是重新看看红线,能不能提高我的搜索速度」**。

要回答这句话,先把"红线"这个词在仓库里的**全部出处**列出来——它们管着完全不同的东西,
而此前从未有人把适用范围写清:

| 出处 | 原文 | 它实际约束的对象 |
|---|---|---|
| `README.md:19` | 「**保持人类调用频率**,勿高频轰炸;全链路零账号/零 cookie/零点数是红线」 | 交互链路。**但没有数字**,这是本轮争议的总根源 |
| `README.md:221`(改动前为 `:218`) | 「保持人类调用频率,勿高频轰炸」 | 同上,重复表述 |
| `docs/adr/0004:13,22` | 「时间网格 `scripts/discovery_sweep.py`(词表×sortsType=2,手动触发,**1 请求/秒,单轮 ≤200 请求**)」 | **发现层采集脚本**。原文语境即为此,与 `kd search` 无关 |
| `docs/adr/0004:44` | 「红线豁免(一次性):全量快照 1 请求/秒、上限 7,500 请求」 | 同上,已用毕的一次性豁免 |
| `docs/adr/0011:78-80` | 「限速器与预算计数器改为**跨进程共享**(SQLite 存上次请求时间)。理由:采集类脚本(`run_eval.py` 循环用例池)是**自动循环**而非人工逐次触发」 | 防**自动循环**。其唯一生产者 `run_eval.py` 已删除 |
| `docs/specs/2026-09-16-去服务化重构.md:54` | 「`run_eval.py` 全套删除…与 `corpus_fullscan.py`、`discovery_sweep.py` 一起清空 `scripts/` 下的自动循环脚本」 | 上述理由的对象消失 |
| `docs/specs/2026-09-16-去服务化重构.md:113` | 「因此**本轮不实现 SQLite 跨进程共享限速**…**若将来重新引入自动循环脚本**,SQLite 共享限速必须重新评估」 | 已推迟,条件未复现 |
| `docs/specs/2026-09-28-开工清单.md:497` | 「上游为匿名免费链路,所有探测**限速 1.0–1.5 秒/请求**,无并发」 | 该节标题是**「附:实验纪律」**——施工期纪律,不是产品红线 |
| `src/kd/contract.json` 的 `limits.rate.interactive` | `{burst: 3, rps: 2.5, jitterMs: [40, 220]}` | **交互链路唯一的数字**,也是 `_RateLimiter` 实际执行的东西 |

**结论:交互链路的红线数字只有一个,就是 `contract.json` 里那一个。**
「1 请求/秒」与「≤200」从来没有约束过 `kd search`,它们的原文语境全部是发现层的自动循环脚本,
而 `scripts/` 目录已整体删除(`git log --diff-filter=D` 证实:同一次提交删掉了
`corpus_fullscan.py` / `discovery_sweep.py` / `releasenotes_ingest.py` / `releasenotes_probe.py` / `run_eval.py`)。

### 关键实测:慢的根因不是红线,是串行

放宽红线的收益必须先与"改调用方式"的收益对比,否则会调错东西。
实测(典型工作流 = `search` 3 路 + `read` 2 篇,样本 ≥3 次取中位):

| 操作 | 请求数 | 纯网络 | 限速等待 | 总耗时(中位) |
|---|---|---|---|---|
| 单次上游请求 | 1 | 340 ms | 200 ms | **535 ms** |
| `search` 3 路 | 3 | 1191 ms | 383 ms | **1806 ms** |
| `search` 7 路 | 7 | 2631 ms | 3495 ms | **3491 ms** |
| `read question`(5 回答帖) | 6 | 1368 ms | 1011 ms | **2277 ms** |

限速器逐字复刻后确认(`interval = 1/rps = 400 ms`):

- **冷启动、3 路及以内:`delay = 0`** —— 只吃 jitter 40–220 ms,**不是节流**
- 第 4 路起:`delay` = 400 / 800 / 1200 ms 逐路累加
- 热态连续调用:`delay` 直接跳到 1200 / 1600 / 2000 / 2400 ms

即 **`burst=3` 已覆盖典型工作流**(3 路及以内零等待),限速只在 ≥4 路时才成为可见成本。
而 **`_manifest.py` 的路由循环是串行 `for`**,网络往返完全不重叠——串行吃掉 60–70%,
限速只占 20–40%。

### 上游能否扛并发(放宽的前提)

不测这一条就放宽是不负责任的。实测:

| 批次 | 并发数 | 总耗时 | 串行预测 | 加速比 | 200 数 | 429/限流头 |
|---|---|---|---|---|---|---|
| 串行对照 | 1 | 1226 ms | 1226 ms | 1.00x | 3/3 | 无 |
| 并发 | 3 | **395 ms** | 1091 ms | **2.76x** | 3/3 | **无** |
| 并发(真实路径) | 3 | 604 ms | 1040 ms | 2.99x | 3/3 | 无 |
| 并发(真实路径) | 7 | 1675 ms | — | 2.08x | 7/7 | 无 |

判据三条全部满足:(a) `totalElements` 与串行逐条一致(6328 / 1400 / 4208);
(b) 捕获的响应头里无 `Retry-After`、无 `X-RateLimit-*`、无 `RateLimit-*`,`errorCode` 全为 null;
(c) **是真并发不是服务端串行化**——并发 3 路总耗时 395 ms ≈ 单请求 394 ms(`parallelRatio = 1.03`),
而串行预测是 1091 ms。**上游服务端零限流信号,客户端 `_RateLimiter` 是唯一的节流来源。**

⚠️ 未实测边界:并发只测到 7 路(`maxKeywords` 上限)。10+ 路的服务端行为**未实测**,不应外推。
服务端是否存在更长窗口(如分钟级)的限流**没有测到**,这是本决策保留的风险敞口。

## 决策

### 决策 1(主决策):红线的适用面按上表收口,`README.md` 那句补上数字

`README.md:19` 的「保持人类调用频率,勿高频轰炸」改为带数字的明确表述,并注明
**唯一真源是 `contract.json` 的 `limits.rate`**。

理由:本轮争议的全部根源就是这句话没有数字——有人读成"管瞬时并发",
有人读成"只管长期速率",而下一个读 README 的人仍会得出自己的结论。
项目自己有一条纪律叫「**声明必须有消费者,否则'单一来源'是假的**」
(`CONTEXT.md` 契约声明条),并且**点名批评过「名实不符」**。一句没有数字的红线
正是这条纪律的反例:它声明了约束,却不说是多少,于是执行者(限速器)与声明者(README)
可以长期不一致而无人发现。

### 决策 2:阈值由 `burst 3 / rps 2.5` 上调为 `burst 7 / rps 5`

依据三条:

1. **`burst` 对齐"单次操作最大请求数"**。`maxKeywords = 7` 是单次 `search` 的路数上限,
   故 `burst = 7` 表示"一次搜索的全部路数允许在同一起始窗口内发出"。
   此前 `burst = 3` 意味着 7 路搜索必须排两次队,而排队带来的那 1.6 秒**零安全价值**——
   上游在 7 路并发下无任何限流信号(上表)。
2. **`rps` 翻倍仍在"人类手动操作密度"的可解释范围内**。用户是唯一的人工触发者,
   每次 `kd search` 是明确的一次动作。`rps = 5` 意味着连续操作时每 200 ms 放行一个请求,
   相当于"人类连续敲两次搜索"的密度。
3. **放宽只对 ≥4 路生效**,3 路及以下的行为**完全不变**(`delay` 恒为 0)。
   故这是有边界的调整,不是全链路提速。

### 决策 3:`ADR-0011` 决策 5 补条件说明,`spec:113` 的过期陈述一并修

`ADR-0011:78-80` 判决"限速器必须改为跨进程共享",而实现从未这样做,两处口径相反且
**都没有写明前提已消失**。实测机制确认这个缺口是真的:6 进程并发各 6 次调用时,
聚合速率线性放大(1 进程 8.40 req/s → 6 进程 38.40 req/s,名义 2.5 的 15.4 倍),
每个进程各自重新计数。

但 `ADR-0011` 决策 5 的**理由**是"采集类脚本是自动循环",而 `spec:54` 已确认这些脚本
连同 `scripts/` 目录一起删除。故:

- 在 `ADR-0011` 决策 5 补一段「⚠️ 条件说明」:前提(自动循环脚本)已于
  `6afa727` 消失,当前不实现;若重新引入自动循环脚本必须重新评估。**已实施**(2026-09-29)。
- 修 `spec/2026-09-16-去服务化重构.md:113` 的过期陈述——它说"**保留**的人工触发脚本
  (`releasenotes_ingest.py` / `releasenotes_probe.py`)维持既有频率档位",
  而这两个文件**也一起被删了**(实测均不存在)。**已实施**(以更正注形式追加,正文不回改)。

**判定:当前零风险,但文档必须收口。**
唯一让这条变成现实风险的场景是**多进程并发调用**——用户本机的 Agent Teams 模式
(多个 agent 并行跑 `kd search`)就会命中,此时上游看到的是聚合 13+ req/s 而非 2.5。
这一点写进本 ADR 留证,不在本轮实现跨进程限速。

### 决策 4:并发改造与红线放宽解耦,先做零红线代价的那部分

路线分开,理由是**收益归因不同、风险归因不同**:

| 阶段 | 内容 | 红线代价 | 实测收益 |
|---|---|---|---|
| 阶段一 | 路由循环串行 → 并发池;`read` 详情循环并发 | **零**(不动任何数字) | 3 路 search 1806 → **604 ms**;`read question` 2377 → 1557 ms |
| 阶段二 | 应用本 ADR 决策 2 的新阈值 | 数字上调 | 7 路 search 再降到 **~660 ms**;3 路**无额外收益** |

**关键洞察**:决策 2 的收益封顶在网络地板上——`max(净往返) + max(抖动)` 对 3 路是 590 ms、
7 路是 694 ms。放宽红线后已贴到地板,**再无空间**。故调红线是"把最后一段排队时间拿掉",
不是"主要提速手段"。这一点必须写清,否则用户会误以为提速靠放宽红线。

前置条件:**阶段一必须先补 `_RateLimiter` 的并发安全确认**。
现实现 `wait()` 的 `with self._lock` 只包住 `_next` 的计算与更新,sleep 在锁外
——这个结构本身是线程安全的(20 轮 × 7 并发压力测试无异常,`_next` 单调性保持),
但它从未在并发场景下被真正使用过,故阶段一须把它纳入回归。

## 不做的事

- **不实现跨进程共享限速**(SQLite + WAL + `busy_timeout`)。ADR-0011 决策 5 的原案前提
  (自动循环脚本)已消失,当前无消费者。留证:多进程并发时该缺口会真实命中(见决策 3)。
- **不碰 `ADR-0004` 的 `1 请求/秒 / ≤200`**。那组数字约束的是已删除的发现层脚本,
  改它等于给一个不存在的对象改约束。
- **不动 `docs/specs/2026-09-28-开工清单.md:497` 的「无并发」**。它是施工期实验纪律
  (该节标题即「附:实验纪律」),`spec` 是历史记录,不回改;适用范围的澄清以本 ADR 为准。
