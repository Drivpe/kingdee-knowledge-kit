# ADR-0014:清单粒度改帖子级 —— 同帖多回答合并、id 即帖子号

日期:2026-09-27 | 状态:已采纳 | 关联:ADR-0013(单入口检索链路、零算法排序)、
ADR-0009(原句路)、ADR-0005(多路检索路由)、
被推翻的前提:`docs/specs/2026-09-17-search多路清单化.md:139`(去重键论证)

## 背景

自 2026-09-17 起 `search` 的清单单位是**条目**,而去重键定义在
`specs/2026-09-17-search多路清单化.md:139`:

> 去重键 `f"{type}:{id}"`,其中 `answer` 的 `id` 取**回答 id**(`x["id"]`),
> `questionId` 只出现在展示字段里。
> 理由:清单单位是**条目**,而回答是独立条目(一个帖子可以有采纳回答 + 多条普通回答,
> 语义不同、应可分别筛)。`read("answer", ...)` 只认 `questionId` 是**读取路径**的约束,
> 不影响**列表路径**的条目粒度。

这条设计带来一个**结构性口径分裂**,并在真实使用中暴露出来:

| 端点 | 粒度 | 返回的单位 |
|---|---|---|
| `/api/search`(检索) | **回答** | 一个帖子下 3 条回答 → 3 个条目,各带自己的回答 id + 同一个 `questionId` |
| `/api/questions/{帖子号}`(详情) | **帖子** | 问题正文 + 采纳答案 + 全部回答列表 |

后果是**清单给的是回答级 id,而读取只认帖子号**——"回答 id 读不到"这个现象的真相不是
上游不支持,而是**清单那一步给错了号**。为兜住它,内核不得不同时维护两个 id 空间
(`id` = 回答 id、`questionId` = 帖子号),并在 SKILL.md 里教调用方"answer 条目要把
questionId 交给 read"。

用户 2026-09-27 质询时提出:

> 我其实不太理解为什么问题和答案是分开的,我自己人类搜索社区的时候都是在一起的。

这句话指向的是**形态合理性**:人类在社区里搜到的是一个帖子,问题与回答在一起;
而本套件把一个帖子拆成 N 条并列条目,既不贴近人类直觉,又把 id 口径
变成了调用方必须记住的隐性知识。

## 决策

**清单粒度从「回答级」改为「帖子级」**(决策 D4/D6,2026-09-27):

1. **同帖多条回答在清单里合并为一条**;
2. 条目的 **`id` 就是帖子号**(上游的 `questionId`),`questionId` 字段**整体删除**;
3. `read` 三个档一律用 `item["id"]`,`_fetch_for_item` 不再有分支;
4. 双 id 空间随之消失——不存在"该传哪个 id"的问题。

**推翻原文论证**:spec 第 139 行的理由是"同帖多条回答语义不同(采纳的是解、
普通的是旁证),应可分别筛"。用户**明确不接受**该理由:人类搜社区时看到的就是帖子,
"可分别筛"这个能力在清单阶段没有实际消费者——**要分辨哪条回答被采纳,是读了帖之后的
事,不是清单筛选阶段的事**。故该理由连同"清单分条目"一起撤销。

**上游协议不动**:上游两个端点粒度不同是既成事实,内核在 `_norm_item` 一处把
`answer` 翻译成对外的 `question`,并在合并层聚合帖级信号。

## 帖级合并规则(不引入任何排序分)

合并发生在 `_manifest_merge`,遍历同帖条目按下列规则聚合:

| 字段 | 规则 | 理由 |
|---|---|---|
| `title`/`url`/`questionBody`/`type`/`id` | 取首个非空 | 同帖取值本就相同 |
| `snippet` | 取上游给的**第一条非空** | 各条回答的命中片段不同;不拼接——拼接会把不相邻的回答片段伪装成一段连续文本 |
| `products` | 取首个非空列表 | 同上 |
| `adopted` | **任一为真即为真** | 语义由"这条回答被采纳"变为"**这帖里有采纳答案**" |
| `answersCount`/`comments`/`supports` | **取最大值** | 上游各条各自复述同一帖的计数(正常同值),取 max 保证不因某条缺字段丢真值 |

**零算法排序契约不受影响**(ADR-0013 硬契约):排序键仍是
`(首次出现的路序号, 该路内上游名次)`——取该帖最早被哪一路第几名召回。
合并只改变条目**字段内容**,不改变任何顺序。

## 连带变更

- **`type` 与 `read` 的 `kind` 一起改名 `question`**(决策 D5):上游协议里的
  `entity-type` 仍是 `"Answer"`,故 `answer → question` 的映射**只允许出现在
  `_upstream._norm_item` 一处**;此文件之外的代码、文档、CLI 一律用 `question`。
  改为 `question` 的理由:详情端点本来就是帖子级的,叫 `answer` 名实不符。
- **字段增减**(决策 D8–D12):条目字段 16 → 13(砍 `questionId`/`views`/`updatedAt`);
  顶层 16 → 13(砍 `page`/`pageSize`/`totalPages` 与 `--page`/`--size` 参数);
  `questionBody` 保留(零额外上游请求,上游搜索结果本就带帖子 `description`);
  `products` 保留。
- **产品线字面推导整体删除**(决策 D14):`_derive_product_id`(别名表 + 推导源优先级 +
  "先出现优先"裁决规则)全删,`product_id` 直通。`effectiveProductId` 保留但语义变为
  "恒等于调用方传入值",作用是让调用方核对这一轮用了哪条线。详见 ADR 后续或
  `docs/specs/2026-09-18-单入口检索重构.md` 的修订。
- **清单字段集收进 `contract.json`**(决策 D13):代码读它拼返回体,测试从它派生断言,
  文档指向它——治"抄六遍"。

## 已知取舍

- **同帖多条回答不再能分开筛**。这是决策的直接代价,已向上说明;
  回答级信息仍可从 `read(question, 帖子号)` 拿到全文列表(含每条回答的 `adopted`)。
- **`adopted` 的语义变宽**:从"这条回答被采纳"变成"这帖里有采纳答案"。
  调用方读法不变(仍是"这条值不值得点开"的旁证),故未新增字段承担旧语义。
- **上游若将来改为按帖子返回检索结果**,本层的合并逻辑自然退化为恒等映射(无副作用)。

## 后续更正(2026-09-28,晚于本 ADR;优先于以上各处)

1. **「链接可点性」的未决项已收口**:本条原记「三条网页路径一律 302 → /error/404,故当前
   不给链接」——**该结论已被推翻**。匿名复测(24+19 样本):`knowledge/` 14/14、`article/`
   12/12 可点,`question/` 9/9 不可点。原结论的两处根因:(a) 限流窗口内的表现被推广成
   路径级常量;(b) **只看首跳状态码**(而 `question/` 的最终状态码恰为 200,`article/`
   存在"302 但迁移成功"的样本)。现行口径按 kind 分档,**唯一真源是 `contract.json` 的
   `linkPolicy`,且它有生产消费者**(`apply_link_policy`,清单投影与 read 两处调用)。
   证据见 `docs/research/2026-09-28-链接可点性复测.md`。
2. **字段集检查的自环已断**:`contract.json` 的声明曾被"被测代码读、断言也从它派生"两边
   共用,于是删字段与加字段**两个方向都静默通过**(实测)。现改为**冻结基线 + 真实输出 +
   注入自检**三段对账,见 `tests/kd_regression.py` 的 `FROZEN_RESULT_KEYS` 与
   `t_result_keys_vs_real_output`。
3. **「按标题挑」的边界已立**:见 ADR-0015(判据进文档、内核零感知)。
4. **新增稀有数字 token 路(T2)**:问句里的 ≥3 位纯数字串单独成路并抢第 1 路,
   原句路退第 2 位但**截断时仍优先保席位**(ADR-0009 决策 3 未被破坏)。
