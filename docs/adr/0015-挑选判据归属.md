# ADR-0015:「按标题挑」的判据归属 —— 判据入文档、机制不入内核

日期:2026-09-28 | 状态:已采纳 | 关联:ADR-0008(合成权移交调用方)、ADR-0013(单入口检索链路、零算法排序)、
ADR-0014(清单粒度改帖子级) | 承接:`docs/specs/2026-09-28-开工清单.md` 的 T6

## 背景

用户规划的检索链路是 7 步:提问 → LLM 拆词 → 多路搜索 → 标题清单 → **按标题挑** → 读正文
→ 汇总回答 → 附链接。2026-09-28 的架构梳理发现:其中 **6 步都有实现**,
唯独「按标题挑」**步骤存在但没有任何机制** —— 没有判据、没有检查、没有测试面。

这一缺口与 ADR-0008 的边界直接相邻,而 ADR-0008 只说了"合成权在调用方",
没说"**挑选**权在调用方"这件事该如何落成机制。故必须先钉边界,再决定动谁。

## 决策

### 决策 1:挑选判据落进文档(SKILL.md),**不进内核**

用户 2026-09-28 的指示是「在 SKILL.md 里把筛选标准写详细,去限制 LLM」(而非改代码),
本 ADR 确认该方向并把它**写成不可再议的边界**。

判据写在 `SKILL.md` 的「第 2 步:kd read」节,含 6 条(读前 3 条不跳读 / 读够就停 /
`type` 决定能证明什么 / 标签与 `snippet` 不是判据 / 补搜与否看客观信号 / 换词而不是换产品线)。
其中第 3 条是**根因引用规则的下沉**:`knowledge` 才能支撑根因,`question` 只能做症状对齐。

### 决策 2:内核**不得**产出"该读哪篇"的任何形式

明确禁止下列任何一种"把挑选机制塞回内核"的形态:

| 被禁形态 | 为什么它是越界 |
|---|---|
| 给条目**打分 / 排序加权 / rerank** | ADR-0013 决策 2 的零算法排序硬契约,已有回归钉子 |
| 内核**替调用方截断**清单(如只回 top3) | 截断即"替你决定读哪篇",与 ADR-0013 决策 1 同型 |
| 产出"推荐读这几篇"的字段 | 同上,换了个名字不改变性质 |
| 把正文塞进清单(`contentText`) | 有正文就不存在"挑选"这个动作了,已在 `resultForbiddenKeys` 里 |
| 内核里加 LLM 调用做挑选 | 零模型依赖是套件定位(`CONTEXT.md`);LLM 只允许在**调用层** |

**判据的载体只能是文档。** 它约束调用方,不约束内核;内核对其**零感知**。

### 决策 3:「选对词」与「挑对篇」是两件事,分开治

T2(拆词策略)与本 ADR 相邻但**不同源**:

- T2 治的是**路序**(稀缺 token 抢占第 1 路),改在内核的 `_plan_routes`,有测试面;
- 本 ADR 治的是**清单已给出之后,调用方读哪几条**,只在文档,无测试面。

两者不得互相替代:把 T2 修好**不会**让调用方学会挑选;把判据写详细**不会**
让内核产出更好的路序。

## 为什么不给挑选判据建测试面

这是本 ADR 最需要交代的一条,因为它看起来像"少做了"。

**没有可执行的判据,就没有可断言的测试。** 挑选是否恰当取决于调用方的语义判断
(这条标题是否真的回答了用户问的那个点),而这件事:

1. **规则写不出来**——与 T2 的负结果是同一个性质:判断"哪个 token 稀有"需要语义,
   判断"哪篇标题贴题"同样需要语义(实测证据见 T2 的 `tokenRoute.what_is_excluded`);
2. **裁决权已按 ADR-0008 移交调用方**——内核若对"挑得对不对"做断言,等于把裁决权
   又收回来,与本 ADR 决策 2 直接冲突;
3. **能测的部分已经测了**:清单的**客观信号**(`routeErrors` / `budget_exhausted` /
   `routesDegraded` / `hitRoutes` / `type` / `snippet`)全部有回归覆盖,
   文档给的是"**如何读这些信号**",不是"信号是否存在"。

故判据的验收方式是**文档自洽 + 与 ANSWER-SPEC 不冲突**,由 `t_selection_rule_in_docs`
钉住(见「实现落点」),而不是行为断言。

## 后果

- **好处**:缺口被显式填补(从"无判据"变成"有判据且知道它约束谁"),且**不引入任何代码风险**
  ——不碰排序、不碰清单结构、不碰零模型依赖;
- **代价**:约束力仍取决于调用方是否读 SKILL.md。这与票 #24 方案三的自认风险同型
  (「依赖调用方自觉…收益不可测」)。**本 ADR 不假装解决了这个问题**,只把判据写到
  可执行、可引用、有出处;
- **边界变清楚**:此后若有人提议"内核给个推荐顺序",这个 ADR 就是拒绝的依据。

## 备选(被否)

- **内核产出"推荐阅读顺序"**:被否。它就是算法评分(ADR-0013 决策 2),且把挑选权收回来;
- **只在 README 写一句**:被否。README 是给人看的门面,面向调用方的行为纪律必须落在
  它真正会读的地方(SKILL.md 是 agent 的入口);
- **写成一节独立的「挑选规范」文档**:被否。挑选与读取是同一步的两面,
  拆成两份会重现"同一事实抄多遍"的病(与 T1 治的是同一种病);
- **给判据加一个内核侧的"合规检查"**:被否。调用方是否遵守,内核无从观测
  (它看不到调用方的推理),硬加只会得到一个永远绿的检查——那正是 T4 修掉的形态。

## 实现落点

| 文件 | 改动 |
|---|---|
| `skills/kingdee-knowledge/skills/kingdee-knowledge/SKILL.md` | 「第 2 步:kd read」节新增「挑选判据」6 条 + 显式声明"内核不替你挑" |
| `docs/ANSWER-SPEC.md` | 不改:第 7 条(根因引用规则)已是判据第 3 条的来源,本 ADR 只引用不复制 |
| `tests/kd_regression.py` | 新增 `t_selection_rule_in_docs`:判据存在、显式声明挑选权在调用方、且未与 ANSWER-SPEC 第 7 条冲突 |
| 内核代码 | **一行不动**(本 ADR 的核心结论) |

## 未决/残余

- 判据的实际效果**不可测**(同票 #24 方案三的自认风险)。若将来用户反馈"挑错了",
  先分清是**判据不清楚**还是**调用方没读**,再决定是改文档还是改机制;
- `question` 档"只能做症状对齐"这条与 ANSWER-SPEC 第 7 条同源;若该条被改,
  本 ADR 判据第 3 条须同步(已在用例里加交叉检查)。
