# ADR-0016:检索词生成权整体移交调用层 —— 内核不得自行生成任何检索词

日期:2026-09-28 | 状态:已采纳 | 关联:ADR-0008(合成权移交)、ADR-0009(原句路,**本 ADR 整体废止**)、
ADR-0010(召回置信度)、ADR-0013(单入口 + 零算法排序,保留并加强)、ADR-0014(帖级清单)、ADR-0015(挑选判据)
| 承接:2026-09-28 架构审查会话(报告 `/tmp/architecture-review-20260928-210655.html`)+ 同日逐条裁定

## 背景

架构审查列出 10 处差异,用户逐条裁定后暴露出一条共同根源:**内核在做它猜不准的事**。

拆词器用正则 + 两张词表(`symptomCategories` / `entityRules`,合计 2 个症状类 + 2 条实体规则)
猜"这句话该拆成哪几个词",并自行决定路序、自行砍路、自行发一路整句。三处都有实测负结果在案:

| 内核的自行决定 | 实测结果 |
|---|---|
| 把 `BOM`(拉丁缩写)前置到第 1 路 | 金标从第 2 **掉到第 12**(`query_routes.json` 的 `tokenRoute.what_is_excluded`) |
| 把泛词拆成各自一路 | 金标**掉出前 30**(SKILL.md 的 E7) |
| 截断时按"重要性"选路 | 与另一处"直接砍尾巴"的截断实现并存,`--kw` 路径的保席位**靠碰巧**(`_routes.py:140` vs `:251`) |

用户对该方向的表述(本轮原话):**「权重我感觉不能分轻重」**、**「llm 根据 skill 规范的搜法去搜索」**。

同时确认了一件此前含糊的事:原句路当初存在的理由是
**「程序切分的时候全是词搜索导致搜索结果过于宽泛」**——即它是**对抗内核自身拆词缺陷的补丁**。
拆词一旦交给 LLM,这个补丁的对象消失。

## 决策

### 决策 1(主决策):内核不得自行生成任何检索词

检索词**只来自调用方**。内核把收到的词**原样**发往上游,不做拆解、不做去重以外的任何加工、
不扩充、不前置、不排序。`queries[]` 与调用方给的词**逐字、逐序**相同。

这条同时废止 `T2`(2026-09-28 同日落地的"稀有数字 token 抢第 1 路")——它虽然只认纯数字,
但性质仍是"内核代调用方决定哪个词更该排前面",与决策 1 同类。

### 决策 2:路序 = 调用方给词的顺序

排序键第一维仍是"首次出现的路序号"(ADR-0013 决策 2 的零算法排序**不动**),
但**该路序不再由内核决定**——它现在逐字等于调用方传词的顺序。

连带删除:`_EXEC_ORDER`、`_TRUNC_PRIORITY` 两张表,以及两处 `routes.insert(...)`。
"截断优先级"这个概念整体消失:超限就是"按调用方给的顺序取前 N 个"。

### 决策 3:CLI 参数面收敛

| 变更 | 内容 |
|---|---|
| **删位置参数** | `kd search "整句"` 不再成立,改 `kd search --kw "词1" --kw "词2"`。`text` 概念的最后一个特殊性随决策 1 消失 |
| **删顶层 `text` 键** | 与已删的 `page`/`pageSize`/`totalPages` 同处理:契约不挂恒为 `null` 的坑。回显只留 `keywords[]` |
| **删 `--type`** | 调用方从清单条目的 `type` 字段自己看类型 |
| **删 `--max-routes`** | 上限只在声明文件里配一个值;超限行为见决策 4 |
| **删 `--budget` / 预算机制整套** | 跨页扫描删除后每路恒发 1 次请求(实测 7 词 = 7 次),预算**永不可触发**,留着是死机制 |
| **删 `KSEARCH_SEARCH_BUDGET`** | 同上 |
| **删 `--chunk`** | 解析后立刻报错的空参数,连帮助文本一并删(与 `ask` 同处理:「一律真正删除,不留 unsupported 占位」) |
| **`--product` 三态收成两态** | `None` 与不传同义(都是默认);"不过滤"只由显式 `--product 0` 表达 |
| **`--global` 保留** | 实测独立能力:默认 6327 / 不过滤 31802 / 跨全部产品 68649,**三者结果集不同** |
| **`--sort` 不开** | 两种排序姿态里时间倒序"目前没什么用",全部固定相关性排序(0/1) |

### 决策 4:超限按顺序取前 N,并**写明丢了几条**

N = 7(实测:7 个词 = 7 次请求 = 3.33 秒;四维度拆词下 7 个词够用)。

丢词必须在返回体里可见——这是既有纪律("宁可报错也不静默截断",见 `clamp_query`)在多路场景的落地。
**"按顺序取前 N"本身不违规**(路序已等于调用方给的顺序,内核没有选择),违规的是**不说**。

### 决策 5:每路固定取 10 条,删掉跨页扫描整段

跨页扫描(`_MAX_SCAN_PAGES` / `_route_search_once` 的 while 循环)是**为 `--type` 补齐服务的**;
`--type` 删除后,该循环永不执行(实测:不带 `--type` 时第一页就返回 10 条 = 目标条数)。

### 决策 6:清单字段集按类型分三份声明

实测可达性(由独立走查用真实上游 6 组 + 直抓响应体核对得出):

| 字段 | knowledge | question | article | 实测依据 |
|---|---|---|---|---|
| `products` | ✅ | ✅ | ✅ | 9/9、11/11、9/9、14/14、5/5 —— **唯一查询无关恒有值** |
| `questionBody` | ✗ | ✅ | ✗ | 上游 `answer` 专有(10/11 有值,个别 `description` 为空) |
| `answersCount` | ✗ | ✅ | ✗ | 同上 |
| `adopted` | ✗ | ✅ | ✗ | 上游 `isAdopt` 仅 `answer` 携带 |
| `supports` | ✗ | ✗ | ✅ | 上游仅 `article` 携带;knowledge/answer 原始条目**无此键** |
| `comments` | ✅ | ✅ | ✅ | 上游**三类都给**(实测同一响应内 0/2/3),原实现只取 answer 分支=**归一化白丢** |

仍是一个 `results[]` 列表(不改成三个并列数组);字段集按 `type` 分三份声明。
按类型不全的键**直接不出现在该条目上**(而非填 `null`)——"结构性不适用"与"上游没给值"
是两件事,混成 `null` 会让调用方分不清。

### 决策 7:两处静默失败改为可分类

| 位置 | 现状 | 改为 |
|---|---|---|
| `read(question)` 的截断 | 布尔 `truncated: true`,上游故障与翻页上限**同形** | 字符串枚举:`"upstream_error"` / `"answer_limit"` |
| 声明文件读失败 | 只写 stderr,顶层无标志(后果:全部 url 静默变 null) | 顶层显式标注配置来源 |

依据:`truncated` 是召回置信度判定(ADR-0010)的输入之一。把"上游坏了"与"资料就这么多"
压成同一个值,会让判定**在最该保守的时候给出乐观结论**。

### 决策 8:声明缺消费者的病一并治

`contract.json` 的 `topKeys` 与 `resultForbiddenKeys` 在**生产路径零调用**(实测 `rg` 仅剩定义与导出)。
这与 `CONTEXT.md` 已写下的纪律冲突:**「声明必须有消费者,否则"单一来源"是假的」**。

- `topKeys` → 改为**真被生产代码读**(顶层字段也照声明拼,与条目侧同构);
- `resultForbiddenKeys` → **保留为文档记录**(它记着"这些键是刻意删掉的",防后人加回来),
  但**删掉那套冗余断言**——清单字段是白名单拼的,白名单外产不出键,那三条 `check_no_forbidden`
  恒绿,与 T4 修掉的"回声与自回声比"同型。

## 禁止清单(本 ADR 是此后拒绝同类提案的依据)

内核**不得**出现下列任何一种形态:

| 被禁形态 | 为什么它是越界 |
|---|---|
| 自行从问句生成检索词(正则、词表、模板皆同) | 决策 1。判断"哪个词更该搜"需要语义,规则做不到(有负结果在案) |
| 给检索词排优先级 / 抢位 / 前置 | 决策 2。路序即召回顺序,改路序等于替调用方分轻重 |
| 按"重要性"选路截断 | 决策 2。"保席位"概念已整体删除 |
| 自行补发一路整句(原句路) | 决策 1。它是历史补丁,补的是内核拆词的缺陷,缺陷已随拆词移交消失 |
| 自行跨页扫描 / 自行扩充取数深度 | 决策 5。要更深由调用方自己换词或换参数 |
| 在内部持任何形式的"检索策略模型" | 零模型依赖是套件定位;LLM 只允许在**调用层** |

**与 ADR-0013 决策 2 的关系**:本 ADR **加强**它——内核不仅不产生排序分,
现在连"路的先后"也不再产生。内核在检索侧的职责收敛为一句话:
**原样发送调用方给的词,去重归并结果。**

| ADR-0013 决策 1(单入口 search→read) | 保留,不变 |

## 后果

- **好处**:内核行为对调用方完全可预测——给的词就是搜的词,给的顺序就是结果顺序;
  三处实测负结果(拉丁词前置、泛词拆分、双截断实现)不再可能复现;
  字段集与错误类型都变成"看得见的事实"而非"推断出来的意图"。
- **代价 1**:拆词质量**完全**取决于调用方是否遵守 SKILL.md 规范。这与 ADR-0015 的自认风险同型
  (「依赖调用方自觉…收益不可测」)。本 ADR 不假装解决它,只把规范写到可执行、可引用、有出处。
- **代价 2**:CLI 调用形态发生**破坏性变更**(位置参数与四个开关删除),
  所有既有文档、示例、技能全文、回归用例的写法都要改。版本须抬高。
- **代价 3**:`--type` 删除后,"只要官方文档"这类需求要靠调用方从清单里自己筛,
  且 `upstream_type_of` 与 `_UPSTREAM_TYPE_OF` 变成死代码(一并删)。

## 未决/残余

- **`_type` 过滤能力是否需要以另一种形式回来**:若将来实测发现"跨类型混排导致清单噪声过大",
  应按决策 1 的同源逻辑处理(由调用方表达意图),而不是在内核加回隐式扫描。
- **注入点形状**:`_manifest._resolve()` 的字符串查表(为让测试替换生效而存在)拟删除,
  测试注入点改到网络出口。属施工细节,见同批施工规格。
- **SKILL.md 的拆词规范效果不可测**(同 ADR-0015 的自认风险):
  若将来反馈"拆词质量下降",先分清是**规范不清楚**还是**调用方没读**,再决定改文档还是改机制。
