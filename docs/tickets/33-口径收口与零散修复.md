## 项一:丢词提示撤销(执行用户口径)

**用户原话**:「**重复的就不要提示了,非重复的超上限的提示**」。

现状实测:

| 输入 | 发出 | `keywordsDropped` | `routesDegraded` | `scanNote` |
|---|---|---|---|---|
| `A B A`(3 词 1 重复) | 2 | 0 | **True** | 报「路数塌缩:3→2 路(调用方给了重复词)」 |
| `A…G A`(8 词 1 重复) | 7 | 0 | **False** | **只字不提** |
| `A…H A`(9 词 1 重复) | 7 | **1** | False | 「收到 **8** 个词,只发前 7 个」 |
| `A…I`(9 词全唯一) | 7 | 2 | False | 「收到 9 个词,只发前 7 个」 |

**症状**:重复词造成的路数减少**报得不一致** —— 同一原因时而报时而不报。

**落实**:

- `keywordsDropped` 的现有算法(去重后词数 − 上限,下界 0)**恰好符合用户口径**,**保留不动**;
- **撤掉"重复词那一支的提示"**:`routesDegraded` 顶层键、`degraded` 计算、
  `scanNote` 的「路数塌缩」句、CLI stderr 的对应句。
  **删除而非置恒 false** —— 留一个恒 false 的键是"死机制",与本仓"不留占位、
  不承诺不存在的能力"冲突;
- **去重本身保留** —— 不得对同一 query 发两次上游请求。

⚠️ **`scanNote` 的第二条症状**(在**去重后**的列表上数,9 词含 1 重复时报"收到 8 个词"
而调用方给的是 9 个)按用户口径同样归入"重复的不提示",随本项一并收口。

⚠️ **上一版报告在此处报错方向**:架构审查报告把「8 词含重复 → `dropped=0`」列为"少报",
**那个判断方向错了** —— 按用户口径它就是对的。复核文档 §2.2 末尾有更正,别沿用错的。

⚠️ **`topKeys` 声明面须同步**:删 `routesDegraded` 要动 `contract.json` 的 `topKeys`
与 `_FALLBACK_TOP_KEYS`,以及投影响应。`routesPlanned` 不在裁定范围,保留。

**影响**:明文钉「同词重复必须报塌缩」的那条用例须改;`ADR-0016` 决策 4 的措辞须更新。

## 项二:排序去伪(删除恒等的 `sorted` 与 `rank`)

`_manifest_rank` 是**恒等函数**:200 组随机构造下 `sorted(order, key=rank) == order`
**恒成立**;500 次试验 `first_seen` 取值**恒不相交**(单射,无 tie-break)。
把 `sorted(...)` 换成 `keys = list(order)` 行为**不变**。

**用户裁定**:删掉 `sorted` 与 `rank`,**直接保序**。

**落实**:

- 删除 `_manifest_rank` 与那句 `sorted`;
- **`_manifest_fuse` 的返回契约要同步**(它也返回 `first_seen`,须一并清理或改注释);
- `_manifest_rank` 若有导出/用例引用,**同步清理**(不保留恒等兼容层)。

⚠️ **真正的顺序契约不在这段代码里**,而在一个**未命名的隐式不变量**上:
`order.append` 与 `first_seen[...]` 被**同处写入**。
删 `rank` 时**必须把这条不变量写成注释**,否则下一个人会以为"顺序不重要"。
既有用例断言的是**签名**而非行为,故这条不变量必须落到注释 + 一条行为断言上。

**红线不变**:`ADR-0013` 的零算法排序契约一字不改 —— 只是把"排完等于没排"
变成"明确不排"。

## 项三:两处零散修复

### 3.1 导入期快照跟随声明

`_public` 的 `_DEFAULT_PRODUCT_ID = default_product_id()` 在 import 期求值。
注入 `productIds.default=87` 后:`default_product_id()` → 87,但
`_public._DEFAULT_PRODUCT_ID` → 93、`core.search` 签名默认 → 93、上游收到 **93**。

**"改 `contract.json` 不生效"不成立** —— 重启进程后三者一致(全 87),
而生产路径**从不重读声明**(实测 `core.search` 执行期间 `default_product_id()` 被调用 **0 次**)。
真问题只有一条:**`default_product_id()` 现在零运行时消费者**。

**修法**:`_public` 的 `None` 分支改为 `return default_product_id()`(一行),
让"显式 None"跟随声明。

⚠️ **签名默认值不能改成动态** —— 回归断言
`sig.parameters["product_id"].default == DEFAULT_PRODUCT_ID`。

### 3.2 子模块被遮蔽改名

`vars(kd._impl)` 里撞车名 9 个,只有 **1 个是真遮蔽**:

| 撞车名 | 包属性实际是 | 真遮蔽? |
|---|---|---|
| `_config` `_errors` `_manifest` `_net` `_public` `_routes` `_text` `_upstream` | 就是子模块对象 | ❌ |
| `_detail` | **function**(被 `from ._detail import _detail` 覆盖) | ✅ |

```python
import kd._impl._net as m       -> module    (可用)
import kd._impl._detail as m    -> function  (不是模块)
kd._impl._detail._get_json      -> AttributeError
```

**已有真实代价**:回归测试专门写了 `_upstream_mod()` 与 `_detail_mod()` 两个 helper
**绕道 `sys.modules`**,注释写明"不能写 `import kd._impl._upstream as m`"。
生产代码未踩(全仓 `_impl.<子模块>` 形式的属性访问零处)。

**修法**:把 `_impl/__init__.py` 的 `_detail` 导出改名为 `_detail_fn` 或删除该导出
(它不是 `cmd_health` 的依赖,也无测试引用包属性形态)。

⚠️ **改完须能直接 `import kd._impl._detail as m`**,并删除那两个绕道 helper。
