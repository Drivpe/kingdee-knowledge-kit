## 问题

`_plan_routes` 的规则拆解**按词法切分,不判区分度**。`_salient_chunks` 只做一件事:把 CJK 连续段按 `stopwords` 切开、留 ≥2 字片段。切出来的片段是不是"上千篇文档都在用的泛词",它无从知道。

后果不是一个词拆错了,而是**整条路的候选集被撑爆**:上游是 **OR 语义**,`product` 路一支 `应用 禁用状态 网关`,等价于"含其中任一即召回",于是泛文塞满前排,精确专文被挤到后面。

同时,反向的错误同样存在:`2510` 这类**纯数字稀有 token** 在 `_plan_routes` 里被归入 `numeric`,**从不产生独立路**——只在「症状类别 i==0 有命中」时才被塞进症状路(`src/kd/_impl/_routes.py:102-103`),而在 `product` 泛词路里**被完全丢弃**(本票定票时本地实跑 JSON 输入,`product` 路产出 `errorCode messagecn 应用`,数字桶不参与)。它恰恰是把候选集从千级压到个位数的那个 token,却**没有任何一路在有意承载它**。

一句话:**内核当前的拆解既不知道哪些词该丢,也不知道哪个 token 必须留。**

读法(照此读,否则会定出错误方案):

- **E1 与 E2 是同一组词、同一个上游,唯一差别是路序**:`2510` 在第 1 路 → 第 1 名;退到第 2 路 → 立刻第 5。排序键第一维是"首次出现的路序号"(`_manifest_rank`),所以**收窄能力最强的那一路必须抢占第 1 路**,这与"命中几路"无关。
- 因此本票方案二的正确定性是:**稀有 token 不只"要有独立路",还要"有路序优先级"**——否则修出独立路、却让它排在第 2 位,E1 的结果(第 5)照样发生。`_PINNED_KINDS` 目前只做"截断时保席位",**不保证排在第 1 路**,这是方案二要额外覆盖的口径。
- **E1 vs E4**:把 token 与原句合并在同一路(E4,与本票「问题」节所述现状同形态)→ 第 5;独立且排第 1(E2)→ 第 1。**合并是实打实的损失**,不只是"稀释"。
- **E6 vs E7**:只差报错串里的 `[网关]` 方括号,位次从第 5 掉出前 30。**报错原文的标点/符号是区分度的一部分**,规则拆解/清洗时不得剥掉。

读法(**必须照此读,否则会读出错误结论**):

- **`total` 会漂移,不得当作判据**。同一检索词在不同时刻 `totalElements` 不同(上游语料在长)。**只有「位次」是可比量**。上表位次与 spec 旧表的差异(旧表 `应用为禁用状态[网关]` 记 total 1761、第 6 位)源于取样时刻不同,不是行为变化。
- **泛词成路 = 候选集爆炸**。`应用 禁用状态 网关` 一路把候选集从 1774 撑到 11547(6.5 倍),目标从此**掉出前 30**,连清单一页都够不着。这正是本票要治的主症。
- **稀有 token 是唯一有效的收窄手段**。`2510` 把候选集压到 **仅 2 条**,目标第 1。而当前的拆解**从不给它一路**——它只是碰巧被原句路带着走,泛词路里则被丢弃。这是"用户拿报错原文来搜,内核把最该用的词降级成搭便车"。
- **原句路本身是好的**。原句单路 total 1774、目标第 5;`2510` + 原句把目标提到**第 1**。所以修法不是"废掉拆词",是"**别让泛词路污染原句路,别丢稀有 token**"。

## 候选方案

### 方案一(推荐):`query_routes.json` 增「泛词/高共享词」黑名单

在 `query_routes.json` 新增 `lowValueCjk` 词表(数据,不是代码)。`_salient_chunks` 产出的片段若命中该表,**不进 `product` 路**(即不单独成路、也不参与 OR 拼接);词表命中同时在 `scanNote` 留痕(说明"本次丢弃了 N 个低区分度片段")。

**入口已实测钉死**(本票定票时本地实跑):

```python
_salient_chunks("应用为禁用状态[网关]", stopwords)  # → ['应用', '禁用状态', '网关']
```

这三个片段**逐字**就是实证里 total 11547 / 掉出前 30 的那一路的词源。黑名单只要覆盖它们,该路即消失——改动点极小、可证伪性强,这是方案一被推荐的技术理由。

- **做什么**:`query_routes.json` 加 `lowValueCjk: ["应用", "禁用状态", "状态", "网关", ...]`;`_routes.py` 的 `_plan_routes` 在 `leftover_cjk` 计算处过滤(约 3 行);`scanNote` 增一行说明。
- **代价**:新词表需人工沉淀,且**只能靠实测扩充**——语料变、泛词也变。每次扩充都是一次 `query_routes.json` 改动。
- **风险**:
  - **误杀**。`状态` 在「单据状态」类问题里可能是有效词。黑名单是**全局**的,没有按场景消歧能力。缓解:词表只收**单用无区分度**的词(≥3 字优先),并保留原句路兜底——原句路永远带着完整输入,误杀片段不等于丢召回。
  - **路数下降 → 请求数下降**,但 `routesPlanned` 变化会撞上现有断言(见「契约约束」),必须同步改测试。
  - 不解决**稀有 token 没有独立路**的问题(那是方案二)。黑名单只做**减法**(不让泛词成路),不做**加法**(不让稀有 token 成路)。

### 方案二:稀有 token(拉丁/数字/下划线标识符)提升为独立路并保席位

`_plan_routes` 现在把 `latin` token 一律塞进 `leftover_lat → product` 路;纯数字更惨,只有症状类别命中时才被用。改为:匹配 `[A-Za-z0-9][A-Za-z0-9._/-]*` 的 **token 若未命中 `stopwords` 且长度 ≥ 2**,产出**独立路**(建议 `kind: "token"`,`why`:稀有标识符强收窄),并把 `"token"` 加进 `_PINNED_KINDS`(与现有 `_PINNED_KINDS = ("product", "raw:question", "raw")` 同机制),使其在 `max_routes` 截断时**保席位**。

- **做什么**:`_routes.py` 新增 token 路产出段;`_PINNED_KINDS` 加 `"token"`;**并保证 token 路占据第 1 路**(见下);`_plan_routes` 尾部 `routes.sort(key=...)` 的路序映射同步。
- **代价**:每多一路 = 多一次上游请求。`budget.maxUpstreamPerSearch` 默认 **24**,`maxRoutes` 默认 **7**——7 路已占满,新增 token 路会**挤掉别的路**(`_PINNED_KINDS` 保席位意味着挤掉的只能是片段路)。要么接受挤占,要么调 `maxRoutes`(那是产品决策,不在本票)。
- ⚠️ **仅"给独立路 + 保席位"不够,必须同时定路序(2026-09-27 对照实验实证)**:`_PINNED_KINDS` 只保证截断时不丢,不保证排在第 1 路。实测 E1(原句第 1、`2510` 第 2)= 第 5 名,E2(`2510` 第 1、原句第 2)= 第 1 名——同一组词仅换路序。故本方案的验收必须**同时**断言 `queries()[0]` 是 token 路,否则修完仍是 E1 的结果。
- **风险**:
  - **路序变了 = 排序键第一维变了 = 清单顺序整体重排**。当前排序键是 `(首次出现的路序号, 路内上游名次)`(ADR-0013 判据,不得引入任何分数)。token 路插在第几路,直接决定清单里所有 token 命中条目的位置。**实测过的顺序(原句第 1、其余按拆解顺序)会被打乱**,须用金标位次重新验收——本票「实证依据」节的 E1–E7 表就是现成的对照基线:E2/E3 为达标态(第 1),E1/E4/E6 为对照态(第 5)。
  - 误伤:普通英文词(`BOM`、`MRP`)会各自成路,可能反而稀释。缓解:与症状类别/实体规则的命中词去重(现有 `used` 集合机制已具备),或限定"纯数字 + 含 `.`/`_`/`-`/全大写"子集。
  - 与方案一冲突:方案一砍路、方案二加路,两者对 `routesPlanned` 的作用方向相反,必须一起定,不能各改各的。
  - **token 抢第 1 路会挤掉原句路的位置**。E2 里原句退到第 2 路仍保住第 1 名(该案原句本身也命中目标),但原句是 ADR-0009 定案的"恒常参与"路,把它从第 1 路挪走属于规格变更,须在 spec 落字后再改——不得只改代码。

### 方案三:不动内核,只在 `SKILL.md` 规范调用方用 `--kw` 自己拆

`--kw` 入口已存在(`keywords` 显式关键词 → 每词一路、跳过全部自动拆解,`_routes.py:49-60`)。`SKILL.md` 已有一节「`--kw`:自己拆词传进去」,但**没有把"泛词不要单独成路""稀有 token 优先"写成硬规则**。改为:明确规定报错类问题**优先把 `errorCode` 作为一路 `--kw`**,禁止把 `应用`/`状态`/`网关` 这类泛词单独作为 `--kw`;并把本节实证表(泛词路 total 11547 掉出前 30 vs `2510` total 仅 2 第 1)抄进 SKILL.md 作为依据。

- **做什么**:改 `skills/kingdee-knowledge/skills/kingdee-knowledge/SKILL.md`;按 spec「技能文档三处同步」纪律,`md5sum` 核对三处一致。
- **代价**:**零**——不碰内核、不碰拆解规则、零回归风险、零守卫改动。
- **风险**:
  - **依赖调用方自觉**。调用方不读 SKILL.md、或读了临场发挥,内核仍然会拆泛词路。spec 自己承认这是"成本最低、收益最高的一步",但**收益不可测**。
  - **不解决"用户直接搜报错原文"这个默认路径**。用户/调用方直接把 `应用为禁用状态[网关]` 交给 `search` 时,`_plan_routes` 照样拆出泛词路——方案三对此完全无感。
  - 三处副本同步若漏,则"仓库对、装机不对",与票 #19 遗留问题同型。

### 建议执行顺序

**先做方案三(零风险,立刻可交付),再做方案一(治主症,风险可控),方案二单独立项**。理由:方案一与方案二同时上会互相掩盖效果,无法归因;方案二动的是**路序**,而路序是排序键的第一维,一旦改错整个清单顺序都错,应有独立验收。若用户要求"本轮只动一处",选**方案一**(它直接对应实证里最刺眼的那一行:泛词路 11547 掉出前 30)。

## 契约约束(必须遵守,勿重开)

1. **零算法排序(ADR-0013 决策 2,不得引入任何分数/加权/RRF)**。排序键**只能**是 `(首次出现的路序号, 路内上游名次)`——见 `docs/specs/2026-09-18-单入口检索重构.md` 第 3.2 节第 2、4 条原文:「路间:按**路序**」「**排序键绝不包含** `hitRoutes` 长度、任何分数、任何时间衰减、任何 views 权重」。
   - **本票的任何方案都不得给"泛词"或"稀有 token"打分**。删路是**集合操作**(在不在),不是**权重操作**(多重要)。方案二里 token 路的"重要"只体现为**路序靠前**,不体现为任何系数。
   - `hitRoutes` / `routes[]` 保持**纯信息字段**,不参与排序。
2. **`search` 顶层键集有硬计数断言 `len(ks) == 16`**。位置:`tests/kd_regression.py` 的 `t_search_contract()`(第 816-817 行 `ok(len(ks) == 16, ...)`),白名单常量 `SEARCH_KEYS` 在同文件第 73-75 行(当前 16 键:`ok, text, keywords, total, queries, routesPlanned, routesDegraded, effectiveProductId, page, pageSize, totalPages, results, routeErrors, budget_exhausted, scanNote, stats`)。

## 验收标准(可执行、可证伪)

以下每条都能被一条命令或一个断言证伪,不得用"看起来更好了"替代。

1. **金标位次不劣于第 5**(本票的核心判据):
   ```bash
   python3 src/kd_run.py search "应用为禁用状态[网关]" --product 93 --size 30
   ```
   取 `results` 中 `id == 646787188905978624` 的下标 +1 → 必须 **≤ 5**。
   ⚠️ **不得用 `total` 作判据**(total 会漂移,见「实证依据」读法)。
2. **泛词不再单独成路**(方案一专属,可证伪的集合断言):
   ```bash
   python3 src/kd_run.py search "应用为禁用状态[网关]" --product 93
   ```
   `queries[]` 中**不得存在**恰好等于 `应用` 或 `禁用状态` 或 `网关` 的整路 terms;且 `routesPlanned` 相较改前**下降**(该输入改前拆 2 路:原句 + 泛词路)。
3. **纯数字稀有 token 不再被丢弃**(方案二专属,可证伪):
   ```bash
   python3 src/kd_run.py search "2510 应用为禁用状态[网关]" --product 93
   ```
   `queries[]` 中**必须存在一路的 terms 恰为 `2510`**(方案二的 token 独立路)。
   改前基线(本票定票时本地实跑 `_plan_routes` 复现,`planned=2`,`degraded=False`):
   ```
   IN : 2510 应用为禁用状态[网关]
     routes: [('raw:question', '2510 应用为禁用状态[网关]'), ('product', '应用 禁用状态 网关')]
   IN : {"errorCode":"2510","messagecn":"应用为禁用状态[网关]"}
     routes: [('raw:question', '{"errorCode":"2510",...}'), ('product', 'errorCode messagecn 应用')]
   ```
   **读法(勿误读)**:`2510` 并未在字面上被删除——它仍被**原句路**带着走。问题在于:
   (a) 它**从不产生独立路**,只在 `i == 0` 的症状类别命中时才被塞进症状路(`src/kd/_impl/_routes.py:102-103`);
   (b) 在 `product` 路(混合输入的泛词路)里,`2510` **被丢弃**——JSON 输入的 `product` 路是 `errorCode messagecn 应用`,数字桶不参与。
   所以"稀有 token 提供强区分度"这件事**没有任何一路在有意承载**;`2510` + 原句能到第 1,靠的是原句路的**偶然兜底**,不是设计。本票要把它变成**有意**的路。
   进一步断言:改后目标文档位次**不劣于改前**。
4. **`routesPlanned` 的变化被测试钉住**(防静默漂移):
   - `tests/kd_regression.py` 的 `t_routes_degraded()`(第 662 行起)依赖 `PROBE_DEGRADED` 拆出 **≥2 路**、`PROBE_MULTI_ROUTE` **不塌缩**——改拆解规则后这两个探针词的拆解结果**必须复核**;若探针失效,换探针并写明新实测值,不得放宽断言。探针常量在同文件第 118-119 行(`PROBE_DEGRADED = "信用额度控制"`、`PROBE_MULTI_ROUTE = "BOM 分母变平方"`),**改前实测基线**(本票定票时本地实跑 `_plan_routes`):
     ```
     信用额度控制      | planned=2 | degraded=True   | raw:question='信用额度控制' 、product='信用额度控制'   ← 塌缩
     BOM 分母变平方    | planned=6 | degraded=False  | raw:question / symptom:quantity-error / entity:bom-denominator-square ×3 / product='BOM'
     ```
     即:`信用额度控制` 的路全靠"原句路与 product 路逐字同串"这一巧合成立——**方案一把 `信用额度控制` 加进黑名单就会让 `product` 路消失,塌缩不再发生,该用例会 FAIL**。这是刻意保留的互锁:改黑名单必须同步处理"塌缩用例靠什么成立",不得静默放宽。

     同理,`BOM 分母变平方` 的 `planned=6` 里 `product` 路只承载 `BOM` 一个 token——**方案二会让 `BOM` 脱离 `product` 路自成 token 路,`planned` 与路序双变**。此探针是方案二的主要受害者,实施方案二前必须先重定该探针。
   - `t_keywords_entry()`(第 595 行起)断言 `routesPlanned == 2`——**`keywords` 显式入口走的是 `_routes.py:49-60` 的分支,完全绕开规则拆解,本票不得让它变化**。这是防止"改规则时顺手把 `--kw` 路径也改了"的钉子。
5. **在线金标用例必须仍 PASS**:`t_gold_error_code_case()`(`tests/kd_regression.py:1164`)——断言目标文档在清单前 30 条内且标题非空、含「错误码」。本票改完该用例**恒须 PASS**。
6. **三件套 + 守卫**:
   ```bash
   python3 tests/kd_regression.py            # 离线 21/21,EXIT=0(当前实测基线 21 通过 / 0 失败)
   python3 scripts/check_core_surface.py     # 10 判据全 PASS,EXIT=0
   python3 tests/kd_regression.py --online   # 联网组(真实上游,人类频率)
   ```
   守卫 10 判据(当前实测名):`no_leaked_names` / `no_missing_names` / `no_dead_names` / `__all__ matches baseline` / `forbidden names absent` / `signatures unchanged` / `exception identity consistent` / `health impl deps resolvable` / `version single source` / `kind set consistent`。
7. **新增回归用例(至少一条)**:把「实证依据」表里的**至少一行**钉成固定用例。建议钉**泛词路**,因为它是本票的主症:
   - 断言 `search("应用为禁用状态[网关]", product_id=93)` 的 `queries[]` 不含整路泛词(离线可用 monkeypatch 抓参,不必打上游);
   - 或断言 `search("2510 应用为禁用状态[网关]", product_id=93)` 的 `queries[]` 有一路含 `2510`。
   **没有新增用例的改动不算完成**——否则下次有人改回拆解规则,没人会发现。
8. **`scanNote` 必须反映丢弃事实**(方案一):若发生低价值片段被丢,`scanNote` 里须有可读说明(沿用现有 `scanNote` 拼接风格,不新增字段)。
