# 方案：把金蝶文档配图纳入回答（在 `kd` 之外的接入设计）

> 前置事实见 `2026-09-17-金蝶知识库配图链路实测.md`（链路已逐环实证完毕）。
> 本文件回答的是：**这个能力该长在哪一层、怎么接、代价是什么**。

## 边界判断：不进 `kd` 内核

**结论：图片能力不写进 `kd`，落在调用层（技能 / Agent 流程）。**

三条理由：

1. **依赖性质冲突**。`kd` 的硬纪律是「纯标准库、零外部依赖」（`CONTEXT.md` 与去服务化 spec 均确认）。而图片理解必须依赖一个 **vision LLM endpoint**——这是外部网络服务 + 凭据。把它塞进内核会让 `kd` 的依赖面从 0 变成 1，并引入凭据管理。
2. **职责冲突**。`kd` 是**检索内核**，输出的是「清单 + 全文」。判断"这张图值不值得看、要问它什么"是**语义决策**，属于调用方（LLM/Agent），不属于检索。内核替调用方决定该不该读图，与本轮 `search` 改造「别替我决定」的同一原则直接冲突。
3. **去服务化刚拆掉的负担不该从侧门加回来**。ADR-0011 刚把后台服务、缓存、ONNX 运行时全部移除，理由是"代价没换来收益"。视觉 endpoint 配置、图缓存、失败重试如果进内核，是在重建被判定为负资产的那类东西。

**所以本方案不产出 `kd` 代码改动，只产出 Agent 侧的操作流程。**

## 能力来源：`describe_image`（已装未配）

DSH 侧已有 `@linxin666/dsh-tool-describe-image` v0.3.23（`~/.dsh/profiles/web/node_modules/@linxin666/`），其设计目标就是「给纯文本模型图像理解能力」。

**它满足本需求的关键特性**：
- 直接吃 **http(s) URL** → 金蝶 CDN 图可直接传，**无需先下载**
- 返回**纯文本**，图像不进上下文 → 上下文成本可控
- 支持显式 `prompt` → 可问"转录图中所有文字并说明操作路径"，而非泛泛描述
- 多 endpoint 轮换 + 语义缓存 + 失败降级

**前置**：需要配置一个 OpenAI 兼容的 vision endpoint（`baseURL` / `model` / `apiKey`）。未配置时工具不可用（本会话即此状态）。

配置入口：DSH 设置 → 插件配置 → "Image understanding" 分组（由其 `DESCRIBE_IMAGE_SETTINGS_NAMESPACE` 提供）。挂载命令见其 `cordis.patch.yml` 注释：
```
dsh plugin --profile web add link:<repo>/packages/dsh-tool-describe-image
```

## 流程图

```
用户提问（报错码 / 操作类）
      │
      ▼
kd search "<原文>"            ← 多路清单（票 #22 产出）
      │  标题清单，LLM 目视筛选
      ▼
kd read <id> --kind knowledge      ← 取全文（HTML）
      │
      ├─→ 文本：直接进回答
      │
      └─→ 正则抽 <img src>          ← 归一化为绝对 URL
              │
              ▼
        describe_image(image=URL,
                       prompt="转录图中所有文字；说明这张截图对应的界面路径")
              │
              ▼
        文本结果并入回答（可标注"据文档配图第 N 张"）
```

## 抽图规则（必须处理的三件事）

从 `kd read` 的 `contentText` 抽 `<img>` 时：

1. **相对路径要补前缀**。HTML 里 `/download/xxx.png` 与 `https://vip.kingdee.com/download/xxx.png` **混用**（实测 5 张里 2 张是相对路径）。统一补 `https://vip.kingdee.com`。
2. **双域名都要接受**。实测有图落在 `vip-admin.kingdee.com`（不是 `vip.kingdee.com`）。抽取器不能硬编码单域名。两个域名都 `302` 到 `cdn-vip.kingdee.com`。
3. **用标签匹配，不要 `str.count("<img")`**。字符串计数会重复计入，实测得 10 而实际只有 5 张。用 `re.finditer(r'<img[^>]*>')`。

## 成本与降级

**成本**：每张图一次 VLM 调用。金蝶一篇文档实测有 5 张图，全读即 5 次调用。所以**不应对所有图无脑读**。

**建议策略**（按优先级）：
1. **只读与问题直接相关的图**。由 Agent 看图的**位置上下文**（图的 `alt`、前后文字）决定——这正是抽图时应**保留偏移量**的原因。
2. **先读文本，判断是否需要图**。若 `contentText` 已足够回答，跳过图。
3. **失败降级**：VLM 不可用/超时/无 endpoint → 回答仍基于文本产出，并**显式标注**"本文档含 N 张配图（操作截图），未纳入本次回答"。**不许静默丢弃**——用户需要知道信息不完整。

**超宽图注意**：实测有 `3268 × 662` 的横条截图（典型的界面路径指示图），文字可能很小。这是待实测项。

**`read_image` 的降采样语义有误导性（已从源码确认）**：

- 工具**描述**（`@deepseek-ai/dsh-tool-fs/lib/index.js:1043`）写着 "Harness validates and downscales large supported images before the next model request"——听上去超限会被自动救回。
- **实际行为**（同文件 `1089-1091`）：`saveImage()` 超限直接抛 `AttachmentError`，工具把它转成错误消息，要求**调用方自己降采样**（原文 "downscale the image and read the smaller copy"）。
- 真正的降采样发生在 `1009` 行（`downscaled from ... px`）——那是**通过入库校验之后**、把图片规范化进模型上下文的环节，**不是**"超限自动救回"。

**结论：入库校验是硬的，超限即拒。** 若要走 `read_image` 路线，必须自己先把图压到限制内（单边 / 像素 / 字节三个上限）。而走 `describe_image` 路线则绕开这整套限制——这也是推荐后者的理由之一。

## 待办（按依赖排序）

1. **配 vision endpoint** —— 决定该能力是否可用。用户手上资源决定。
2. **实测 `describe_image` 吃金蝶 CDN URL** —— 链路最后一环（CDN 无防盗链已证，剩下是工具侧接受度）。
3. **实测超宽图（3268×662）的文字可读性** —— 决定是否需要预处理。
4. **把流程写进技能文档** —— 与 `SKILL.md` 的检索流程衔接（注意三处同步纪律）。
5. **（可选）在技能层加一个薄脚本**：输入 `knowledgeId`，输出该文档的图片 URL 清单（含位置偏移），供 Agent 挑选。**这个脚本属于技能层，不属于 `kd` 内核。**

## 不做

- 不做图片 OCR 兜底（引入 tesseract 等外部依赖，与零依赖纪律冲突；VLM 路线已够）。
- 不做图片本地持久缓存（除非实测发现 VLM 重复拉取成本高；`describe_image` 自带语义缓存已覆盖短时重读）。
- 不把图下载到 `kd` 的工作目录（`kd` 不落盘的纪律）。
