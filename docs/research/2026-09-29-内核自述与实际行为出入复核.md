## 1. 成立且是真缺陷(2 条)

### 1.1 网络出口分裂 —— 离线测试真的会发上游请求

**症状**:模块 docstring 声称"唯一网络出口",但实际有两个独立入口,而**没有单一注入点
能拦住全部请求**。

```
up._get_json  is net._get_json -> True      # 导入期快照,替换 net 的无效
det._get_json is net._get_json -> True      # 同上
替换 net._get_json → 未被拦住(真请求成功, totalElements=6329)
替换 up._get_json  → 被拦住(BLOCKED)
```

| 文件:行 | 形态 | 可打补丁? |
|---|---|---|
| `_upstream.py:21` | `from ._net import _get_json` | ❌ 快照 |
| `_detail.py:14` | `from ._net import _get_json` | ❌ 快照 |
| `_manifest.py:62` | `_upstream._search_upstream(...)` | ✅ 属性访问 |

`_net.py:33` 的 `_get_json` 调用点共 6 处,分属 `_upstream.py:118` 与
`_detail.py:20,78,97,114,134`。`_net._RATE is cfg._RATE -> True` —— **限速器同样是快照**。

**决定性实测(本轮独立抓到)**:用 `sitecustomize.py` 钩住 `urllib.request.urlopen`,
跑完整的 48 条离线用例:

```
通过 48 / 失败 0
=== 期间漏出到真实上游的请求 ===
URLOPEN https://vip.kingdee.com/api/search?text=%E4%BF%A1%E7%94%A8%E9%A2%9D%E5%BA%A6%E6%8E%A7%E5%88%B6...
  src/kd/_impl/_public.py:129  in search
  src/kd/_impl/_manifest.py:297 in _search_manifest
  src/kd/_impl/_manifest.py:62  in _route_search_once
  src/kd/_impl/_upstream.py:118 in _search_upstream
  src/kd/_impl/_net.py:38       in _get_json
```

**漏出 1 次,48/48 全绿。** 源头是 `tests/kd_regression.py:586`:
```python
code, d, err = cli("search", "--kw", PROBE_DEGRADED)
```
`cli()`(`tests/kd_regression.py:197`)用 `subprocess.run` 起**新进程**,
进程内的桩不继承,故这条用例绕过所有打桩点真发请求。而它只断言
`effectiveProductId == 93`,拿到真实结果也照样绿。

**「CI 会打外网」不成立**:仓库无任何 CI 配置(无 `.github/`、无 `.gitlab-ci.yml`;
`git ls-files | grep -i workflow` 零命中)。真正跑这条离线组的是装机自检
`install.sh:150` 与 `install.ps1:207` —— **在用户机器上跑,并且会真发一次请求**。
无网络时它仍然全绿(把代理指向死端口 `127.0.0.1:1`,48/48 通过,因为
`_manifest.py:311` 的 `except Exception` 把 `URLError` 吞进 `routeErrors`)。

**判定**:"离线组不联网"这句承诺是**概率性的**——有网就发,没网就静默吞。

**两处 docstring 的错话**:`_net.py:4` 说"全包唯一发起上游请求的地方"**是对的**
(它确是唯一真出口);但 `_upstream.py:105` 说"`_search_upstream` 是全内核唯一的网络出口"
**是错的**——深读侧 5 个 `_get_json` 调用完全不经过它;`_impl/__init__.py:26` 沿用了这条错话。
准确措辞应是"**检索侧**的唯一出口"。

**⚠️ 并发改造的交互**:泄漏点 `_manifest.py:62` 与路由并发改造(改 `:285` 的串行循环)
**同处一个函数区**。故实施顺序必须是:统一出口 → 修泄漏点 → 再做并发。
否则并发化会把这条子进程用例的请求数放大(现在 1 次、并发后仍 1 次,但注入路径会更难拦)。

### 1.2 `cli._guard` 的 `op` 无测试守护

**症状**:工单 #24 的修复(`read` 遇上游 404 时不再误报"text 超 100 字符")靠
调用点手写一行 `op="read"`(`cli.py:125`),**删掉它 48 条离线用例全绿**。

**`op` 的控制面(AST 精确枚举)**:`op` 只决定 `UpstreamError` 分支的
`hint`/`example` 两个字符串,以及 `_ex` 在另外三个异常分支的取值;
`QueryTooLong` 分支完全不受它控制。调用点两处:`cli.py:110`(不传,默认 `"search"`)
与 `cli.py:125`(`op="read"`)。

**复现(变异测试)**:

```
原版    $ kd read 123456789012345678 → exit=1
   hint = 按 id 取全文时上游报错…        example = kd read 402990431979506944
变异版  $ kd read 123456789012345678 → exit=1
   hint = 上游以 HTTP 200 返回错误壳(常见于检索词超 100 字符…)  ← search 语境
   example = kd search --kw "信用额度控制"
```

**为什么测试抓不住**:全仓唯一碰 `read` 的进程级调用是
`tests/kd_regression.py:803`(`cli("read","1","--kind","nope")`,argparse 层拦截、exit 2,
进不到 `_guard`)与联网组 `:3260`(成功读取、无错误体)。
**零测试断言 `read` 错误体的 `hint`/`example`**(`grep -n "hint" tests/` 只有 `:792` 对 search 的断言)。

**已备好的钉子**(双版本验证:原版 PASS、变异版 FAIL,本轮已写并跑通)——要点:
必须走 `cli.main(["read", ...])` 真调用路径(直接调 `_guard(op="read")` 在 `op` 被删后仍会通过,
测不到回归);必须打桩 `cli._out` 而**不能**用 `redirect_stdout`(后者内部调
`sys.stdout.reconfigure`,而 `io.StringIO` 没有该方法)。

## 2. 成立但是自述与实现不符(4 条)

### 2.1 `read` 的两个"旋钮"传不进去,且其中一个值已失去依据

`_question_detail(qid, with_answers=True, max_answer_pages=3, max_detail=5, rate=None)`
(`_detail.py:53`)—— **全仓无任何调用方传值**,两个数字不在 `contract.json` 的 `limits` 里,
`core.read` 公开签名只有 `(kind, oid, rate=True)`(实测:`(kind, oid, rate=None)`)。

**原始设计理由(已查到,提交 `81ee6a6` v1.0)**:当时 `_get_json` **还没有限速器**、
也没有预算机制,这两个数是**当时唯一的成本闸门**——防一个长帖把请求数拉爆。

**现在两个理由都不成立**:

| 数字 | 实测 | 判定 |
|---|---|---|
| `max_answer_pages=3` | 抽 10 个问答帖查回答数,全部 `totalPages=1`;再采 25 条帖子,回答数中位 **2**、90 分位 **4**、最大 **5**;要触发需单帖 >60 回答,**0 条** | **永不可触发** |
| `max_detail=5` | 实测最大值恰为 **5**,故现在恰好不截断 | 卡在边界,但**依据缺失**(是巧合) |

**用户裁定**:`5` 写进声明并加测试钉住;`2` 和 `3` 删掉(永不可触发,留着是误导);
公开签名不变、不加命令行参数(理由:`ADR-0016` 决策 3 删 `--budget` 的先例——
没有调用方可用它,就等于画上去的旋钮)。

### 2.2 丢词通报被两个环节互相遮盖

`dropped` 的实现是「去重后的词数 − 上限」(`_manifest.py:266-276`)。实测:

| 输入 | 发出 | `dropped` | `degraded` | `scanNote` |
|---|---|---|---|---|
| `A B A`(3 词 1 重复) | 2 | 0 | **True** | 报「路数塌缩:3→2 路(调用方给了重复词)」 |
| `A…G A`(8 词 1 重复) | 7 | 0 | **False** | **只字不提** |
| `A…H A`(9 词 1 重复) | 7 | **1** | False | 「收到 **8** 个词,只发前 7 个」 |
| `A…I`(9 词全唯一) | 7 | 2 | False | 「收到 9 个词,只发前 7 个」 |

两个症状:

1. **重复词造成的路数减少报得不一致**:`A B A` 报、`A…G A` 不报。同一原因时而报时而不报。
2. **`scanNote` 在去重后的列表上数**:9 词含 1 重复时报"收到 8 个词",而调用方给的是 9 个。

**用户裁定**:「**重复的就不要提示了,非重复的超上限的提示**」。
按此口径 —— `dropped` 现在的算法(去重后减上限)**恰好就是对的**;
需要撤掉的是**重复词那一支的提示**。实测影响:1 条测试
(`tests/kd_regression.py:2713` 明文钉「同词重复必须报塌缩」)+ `ADR-0016` 决策 4 的措辞。

**⚠️ 本轮报告的错报更正**:架构审查报告把「8 词含重复 → `dropped=0`」列为"少报"。
**那个判断方向错了**——按用户口径它就是对的。真正的问题只有上面两条,且第 1 条与
`dropped` 无关(它由 `routesDegraded` 与 `scanNote` 承担)。

### 2.3 `_manifest_rank` 是恒等函数

`_manifest_rank`(`_manifest.py:138-165`)在 200 组随机构造下
`sorted(order, key=rank) == order` **恒成立**;500 次试验 `first_seen` 取值**恒不相交**
(单射,无 tie-break)。把 `sorted(...)` 换成 `keys = list(order)` 行为不变。

**真正的顺序契约不在这段代码里**,而在一个未命名的隐式不变量上:
`order.append` 与 `first_seen[...]` 在 `:188-192` 被**同处写入**。
`tests/kd_regression.py:1195` 断言的是**签名**,不是行为。

**用户裁定**:删掉 `sorted` 与 `rank`,直接保序(行为等价,少一层伪装;
`ADR-0013` 的零算法排序红线不变,只是把"排完等于没排"变成"明确不排")。

### 2.4 `project_top` 被调用两次 —— **本轮否决**

`project_top` 定义在 `_manifest.py:377`,调用两处:`_manifest.py:374`(返回前)与
`_public.py:144`(`stats` 注入后)。

- **幂等成立**(实测:两次投影键序逐字相同;投影有损、只会减不会增)。
- **删 `_public.py:144`(MUT-A)→ 47 通过 / 1 失败**——它是 `stats` 的声明闸门,**不可删**。
- **删 `_manifest.py:374`(MUT-B)→ 48/48 全绿**。

**但本轮否决这个改动**。理由:它删的是 `_search_manifest` **自己输出的最后一刀**,
只因 `_public` 那次完全覆盖它而显得冗余。删后该函数从"我返回的东西一定符合声明"
退化为"我返回原始字典,谁调谁自己投影"——下一个调用方必须知道这件事。
收益是一次字典遍历(微秒级),代价是一个内部契约从**闭合**变**敞口**。
这是**为测试绿灯而改**,不是真问题。

## 3. 成立但当前零可达(1 条)

### 跨进程限速器失效

`_RATE = _RateLimiter()`(`_config.py:287`)是进程内的。实测并发 N 进程各 6 次调用:

| 进程数 | 总请求 | 窗口 | 聚合速率 | 相对名义 2.5 |
|---|---|---|---|---|
| 1 | 6 | 0.714 s | 8.40 req/s | 3.4x |
| 2 | 12 | 0.873 s | 13.74 req/s | 5.5x |
| 4 | 24 | 0.970 s | 24.73 req/s | 9.9x |
| 6 | 36 | 0.938 s | 38.40 req/s | **15.4x** |

每个进程各自重新计数。

**`ADR-0011:78-80` 判决"必须跨进程共享",`spec/2026-09-16:113` 推迟它,
而 `spec:191` 自己要求"ADR-0011 决策 5 的措辞需在实施时补充这一条件说明"
—— 这句没补**(`grep "不再适用" docs/adr/0011-*.md` 零命中)。文档互相矛盾。

**零可达的确认**:`scripts/` 目录**不存在**;`corpus_fullscan.py` / `discovery_sweep.py` /
`run_eval.py` / `releasenotes_ingest.py` / `releasenotes_probe.py` 五个文件**均不存在**
(`git log --diff-filter=D` 证实同一次提交 `6afa727` 删掉)。

⚠️ **`spec/2026-09-16:113` 的陈述已过期**:它说"**保留**的人工触发脚本
(`releasenotes_ingest.py` / `releasenotes_probe.py`)维持既有频率档位"——这两个也一起被删了。

**唯一让它变成现实风险的场景**:多进程并发调用。用户本机的 **Agent Teams 模式**
(多 agent 并行跑 `kd search`)就会命中。评审这一条时须知道它今天不构成风险。

## 4. 影响面近零(2 条)

### 4.1 `_DEFAULT_PRODUCT_ID` 导入期求值

`_public.py:22` 的 `_DEFAULT_PRODUCT_ID = default_product_id()` 是导入期快照。
注入 `productIds.default=87` 后:`default_product_id()` → 87,但
`_public._DEFAULT_PRODUCT_ID` → 93、`core.search` 签名默认 → 93、上游收到 **93**。

**但"改 `contract.json` 不生效"不成立**——重启进程后三者一致(全 87),
而生产路径**从不重读声明**(实测 `core.search` 执行期间 `default_product_id()` 被调用 **0 次**)。
`_public.py:18-21` 的注释**逐字承认**了这一点。

真问题只有一条:`default_product_id()` 现在**零运行时消费者**。
修法:`_public.py` 的 `None` 分支改为 `return default_product_id()`(一行),
让"显式 None"跟随声明。**签名默认值不能改成动态**——`tests/kd_regression.py:550`
断言 `sig.parameters["product_id"].default == DEFAULT_PRODUCT_ID`。

### 4.2 `_impl` 的 `_detail` 遮蔽子模块

`vars(kd._impl)` 非双下划线名 = **67**(23 公开 + 44 下划线),与架构审查的计数一致。

| 撞车名 | 包属性实际是 | 真遮蔽? |
|---|---|---|
| `_config` `_errors` `_manifest` `_net` `_public` `_routes` `_text` `_upstream` | 就是子模块对象 | ❌ |

```python
import kd._impl._net as m       -> module    (可用)
import kd._impl._detail as m    -> function  (不是模块)
kd._impl._detail._get_json      -> AttributeError
```

**有害处,且已有真实代价**:`tests/kd_regression.py:2215-2236` 专门写了
`_upstream_mod()` 与 `_detail_mod()` 两个 helper 绕道 `sys.modules`,注释写明
"不能写 `import kd._impl._upstream as m`"。生产代码未踩(全仓
`_impl.<子模块>` 形式的属性访问零处)。

`core.__all__` 核实无误:`['search','read','QueryTooLong','UpstreamError','InternalError']`(len=5),

**修法**:`_impl/__init__.py:102` 的 `_detail` 改名(如 `_detail_fn`)或删除该导出
(它不是 `cmd_health` 的依赖,也无测试引用包属性形态)。

## 5. 被本轮证伪的子代理结论(3 条)

| 子代理结论 | 本轮复核 | 真相 |
|---|---|---|
| 「裸 curl 无 UA 被华为 WAF 拦截,一切判死都是假阴性;必须带 UA」 | **证伪** | 6 个新采知识文档 id 做无 UA/带 UA 对照,**结果逐条相同**(5 活 1 死)。该子代理举的反例 `knowledge/248777993710223104` 带 UA 也照样死——那个 id 是它从 302 跳转里读来的,本身不是有效形式。**"第三条陷阱"不存在** |
