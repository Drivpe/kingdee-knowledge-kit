# 调研:kingdee-knowledge-kit 为什么需要拉起服务?能否封装成纯 CLI?(2026-09-16)

> 起因:当前架构 = 长驻本地 HTTP 服务(`http.server`,默认 `127.0.0.1:4097`)+ 薄 CLI(`kd.py`)经 HTTP 调用;
> 安装器用 `nohup ... &`(Linux)/ `Start-Process -WindowStyle Hidden`(Windows)静默拉起后台进程。
> 对比项目 Lingya(`ly`)是纯进程内 CLI,`dependencies = []`,靠 `[project.scripts]` 暴露命令。
> 方法:一手来源优先 = Python 官方文档 / PyPA 规范 / SQLite 官方文档 / POSIX 规范 / 各项目自己的设计文档;
> 每条结论附 URL;找不到一手来源的明确标注**未找到一手来源**,不以推测填充。
> 立场:只列事实与权衡,不替决策。

## 一句话结论

**"检索工具必须拉起服务"不是 Python CLI 的固有约束,而是本项目的一个可选架构选择。**
Python 生态的官方标准做法(`[project.scripts]` + console_scripts)本身**不含任何后台常驻进程**——`pipx install` 之后用户直接拿到一条命令;
而 SQLite 官方文档明确说它**不需要单独的服务进程**(["doesn't require a separate server process"](https://docs.python.org/3/library/sqlite3.html)),多进程并发访问由 WAL + busy_timeout + 锁机制在**文件层**解决,不需要常驻进程串行化。

**更关键的是:业界把它做成服务时给出的理由是可量化的,不是模糊的"更稳"。** `black`/`blackd` 官方原文把服务化收益定义为「避免每次重新启动一个进程的开销」——

> "The main benefit of using it is to avoid the cost of starting up a new *Black* process every time"

这给本项目提供了一个**可实测的判据**:若本工具每次启动要付出昂贵代价(例如加载 embedding/reranker 模型),服务化有正当理由;若启动成本可忽略,则该理由不成立。

**本次调研不做裁决**——不替用户判断"启动成本是否够贵"「实际有几个并发客户端」这类只有实测才能回答的问题。

## 1. Python CLI 打包的现代标准做法

### 1.1 `[project.scripts]` 的机制与规范地位

PyPA 把 entry points 定义为一个**互操作规范**(不只是 setuptools 的私有功能),原文:

> "It is now defined as a PyPA interoperability specification in order to allow build tools other than `setuptools` to publish `importlib.metadata` compatible entry point metadata"

- group `console_scripts` 的名字就是**命令名**,object reference 指向一个**无参函数**;函数返回值当退出码,返回 `None` 等价于 `0`。
- 规范给了等价的 wrapper 语义:

```python
import sys
from mymod import main
sys.exit(main())
```

- 关键边界:**安装工具负责在 scripts 目录建 wrapper,但不负责把该目录加进 `PATH`**——
  > "They are not responsible for putting this directory in the `PATH` environment variable"
- `console_scripts` vs `gui_scripts` **只在 Windows 上有区别**:前者包一层 console 可执行文件(能挂 stdin/stdout/stderr),后者不挂控制台。

来源:[Entry points specification — Python Packaging User Guide](https://packaging.python.org/en/latest/specifications/entry-points/)

setuptools 侧同样以 `[project.scripts]` 为标准写法,并明确"console script 用的函数不应接受参数,用户输入靠函数体内自己解析 `sys.argv`":

来源:[Entry Points — setuptools documentation](https://setuptools.pypa.io/en/latest/userguide/entry_point.html)

### 1.2 安装体验:用户拿到什么

`pip install` / `pipx install` 之后,用户拿到的是**一条可直接执行的命令**,不需要手动拉起任何后台进程——因为 entry point 的语义就是"调用一个函数并以其返回值作为退出码",规范里没有任何守护进程/服务的概念。

Lingya 的 `pyproject.toml` 正是这个形态(实测本机文件 `/mnt/d/03_Work/03_Develop/Lingya/pyproject.toml`):

```toml
[project.scripts]
ly = "ly.cli:main"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

**结论:第 1 问的答案是——console_scripts 机制本身不需要用户拉起任何后台进程。**
(注:一个包**可以**同时暴露多个 entry point,其中某个恰好是服务——见第 4 节的 `black`/`blackd`。)

## 2. pipx 的定位

### 2.1 它解决什么问题

pipx 官方自述:

> "`pipx` installs and runs end-user Python applications in isolated environments. It fills the same role as macOS's `brew`, JavaScript's `npx`, and Linux's `apt`."
> "unlike pip it creates a separate virtual environment for each application, so their dependencies never collide and an uninstall leaves nothing behind."

它对**应用**的定位很明确:只装带 CLI entry point 的包,不装供 import 的库——

> "pipx is a specialized package installer. It can only install packages with CLI entry points."

来源:[pipx 官方首页](https://pipx.pypa.io/stable/) / [Comparisons](https://pipx.pypa.io/stable/explanation/comparisons.html)

### 2.2 pipx vs `pip install`

PyPA 自己的官方指南给出了**权威推荐理由**(不是二手):

> "Usually you want to be able to access these applications from anywhere on your system, but installing packages and their dependencies to the same global environment can cause version conflicts and break dependencies the operating system has on Python packages."
> "pipx solves this by creating a virtual environment for each package, while also ensuring that its applications are accessible through a directory that is on your `$PATH`. This allows each package to be upgraded or uninstalled without causing conflicts with other packages"

pipx 与 pip 的对比要点(官方):
- pipx 依赖 pip 和 venv;
- pipx 替代 pip 的一个**子集**:装 CLI 应用,不装库;
- `pip install --user pipx` 就装好 pipx 本身。

来源:[Installing stand alone command line tools — PyPA](https://packaging.python.org/en/latest/guides/installing-stand-alone-command-line-tools/) / [pipx Comparisons](https://pipx.pypa.io/stable/explanation/comparisons.html)

### 2.3 pipx vs "下载脚本 + 手动拷文件"

一手结论:`pipx install PACKAGE` → 用户拿到「命令在 `$PATH` 上」的结果,官方教程展示的真实输出:
```
$ pipx install httpie
  installed package httpie 3.2.4, Python 3.12.3
  These apps are now globally available
    - http
    - https
```
并且配套 `pipx list` / `upgrade` / `uninstall` / `reinstall` 管理面。

**关于"相对手动拷文件的优劣",官方文档没有做这种对照**——官方对照表里的比较对象是 pip / uv tool / poetry / pipenv / venv / pyenv / pipsi / brew / npx / pip-run / fades / pae。
**未找到一手来源**:任何官方文档对「pipx vs 下载脚本+手动拷文件」的直接比较。能从官方文本**直接推出**的只有事实:手动拷文件不经过 venv 隔离,而隔离与可升级/可卸载是 pipx 的立身之本。

### 2.4 三平台支持情况

PyPA 官方指南**同时给出** Unix/macOS 与 Windows 的安装命令,说明三平台均受支持:

Unix/macOS:
```
python3 -m pip install --user pipx
python3 -m pipx ensurepath
```
Windows:
```
py -m pip install --user pipx
py -m pipx ensurepath
```
其中 `ensurepath` 就是把应用目录写进 `$PATH`(官方提示可能需重开终端才生效)。

pipx 官方另有 Windows 专属文档章节(`how-to/install-pipx.html`)。已知官方限制:pipx **要求 Python 3.10+**("It requires Python 3.10+ and uses the standard-library `venv` package")。
另注:PyPA 指南页脚称 "pipx only works with Python 3.6+",与 pipx 自己文档的 3.10+ 说法**不一致**;以 pipx 官方仓库的 3.10+ 为准更稳。

来源:[PyPA 安装指南](https://packaging.python.org/en/latest/guides/installing-stand-alone-command-line-tools/) / [pipx Comparisons](https://pipx.pypa.io/stable/explanation/comparisons.html)

## 3. 长驻服务 vs 进程内调用的权衡

### 3.1 进程内/无状态进程的一手论据

**12-Factor App 第 VI 条 Processes**——官方原文立场是"无状态 + share-nothing":

> "Twelve-factor processes are stateless and share-nothing. Any data that needs to persist must be stored in a stateful backing service, typically a database."
> "The memory space or filesystem of the process can be used as a brief, single-transaction cache."
> "Session state data is a good candidate for a datastore that offers time-expiration, such as Memcached or Redis."

并且明确点名"进程内缓存不可依赖":

> "The twelve-factor app never assumes that anything cached in memory or on disk will be available on a future request or job"
> "Even when running only one process, a restart ... will usually wipe out all local (e.g. memory and filesystem) state."

来源:[The Twelve-Factor App — VI. Processes](https://12factor.net/processes)

**Python 标准库 `socketserver` 官方文档**给出一条**直接相关的判据**,即"何时该用服务、何时该用进程"——它讨论的是 forking/threading 服务器里内存状态的陷阱:

> "it makes no sense to use a forking server if the service contains state in memory that can be modified by different requests, since the modifications in the child process would never reach the initial state kept in the parent process"
> "In this case, you can use a threading server, but you will probably have to use locks to protect the integrity of the shared data."

来源:[socketserver — Python docs](https://docs.python.org/3/library/socketserver.html)

**LSP 的一手动机论述**——官方给出的理由是**跨工具复用 + 标准化**,不是"性能",也**不是**"进程隔离带来稳定性":

> "The idea behind a *Language Server* is to provide the language-specific smarts inside a server that can communicate with development tooling over a protocol that enables inter-process communication."
> "The idea behind the *Language Server Protocol (LSP)* is to standardize the protocol for how tools and servers communicate, so a single *Language Server* can be re-used in multiple development tools, and tools can support languages with minimal effort."
> "A language server runs as a separate process and development tools communicate with the server using the language protocol over JSON-RPC."

来源:[Language Server Protocol — Overview](https://microsoft.github.io/language-server-protocol/overviews/lsp/overview/)

**⚠️ 两条容易误引的边界(核实后必须写明)**:
1. **"进程隔离 → 编辑器稳定性"这一条,微软官方规范并无明文表述**,不要当作官方理由引用。官方对"跨语言"的表述是**数据类型语言中立**(用 URI/position 而非 AST),也不是隔离理由。
2. 更反直觉的是,LSP 3.17 规范原文明确了**当前协议并不支持一个 server 被多个工具共享**:
   > "The protocol currently assumes that one server serves one tool. There is currently no support in the protocol to share one server between different tools."
   来源:[LSP 3.17 Specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
   也就是说,"一个 server 服务多工具"是 LSP 的**设计意图与生态价值**,而非协议当前提供的机制;两者不能混为一谈。

**MCP 官方规范**把本地场景的默认 transport 定为 **stdio**(客户端把 server 作为子进程拉起,而非长驻 HTTP 服务):

> "Clients **SHOULD** support stdio whenever possible."
> stdio: "The client launches the MCP server as a subprocess."

来源:[MCP Specification — Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)

### 3.2 长驻服务**必要**的场景(有官方一手支撑的)

| 场景 | 一手依据 |
|---|---|
| 需要**被多个客户端共享状态**,且状态在内存中可被并发修改 | `socketserver` 文档:Forking 服务器子进程的内存修改"永远不会回到父进程初始状态";此时要么 threading + 锁,要么把状态外置 |
| 需要**跨请求共享昂贵资源**(连接池、预加载索引、模型权重),且启动开销大到值得让进程长活 | `blackd` 官方文档给出该动机的最清晰表述(§4.2):"The main benefit of using it is to avoid the cost of starting up a new *Black* process every time" |
| 需要**被多工具复用同一份逻辑实例**(编辑器/IDE 场景) | LSP Overview:"a single *Language Server* can be re-used in multiple development tools"(注:这是设计意图;协议当前不支持一个 server 被多工具共享,见 §3.1) |
| 需要**跨进程并发控制**(串行化写、限流、队列) | `socketserver` 文档:"you will probably have to use locks to protect the integrity of the shared data" |

### 3.3 长驻服务**过度设计**的场景

| 场景 | 一手依据 |
|---|---|
| 每次调用的状态完全可以**外置到数据库**,进程本身无状态 | 12-Factor VI:持久状态存 backing service;内存只作"single-transaction cache" |
| 本地工具、单客户端、调用即结束(不存在多客户端共享) | MCP 规范:这样场景的默认建议是 stdio 子进程;LSP 的进程外理由是**多工具复用**,单客户端不成立 |
| 只是想省一次启动开销 | **未找到一手来源**支持"为省启动开销而常驻"是标准做法;12-Factor 反而强调 disposability(第 IX 条,快速启停)。同一规范页 [12factor.net](https://12factor.net) 列出 IX. Disposability: "Maximize robustness with fast startup and graceful shutdown" |

**明确标注**:上表中"过度设计"一栏中,除引用到的官方文本外,其余判断属于**基于官方原则的推论**,非官方直接论断。

## 4. 单文件 CLI 内嵌本地 HTTP 服务的常见模式

### 4.1 为什么有些工具要起本地服务(项目自己的一手说明)

**LSP**:理由是标准化的跨工具复用 + 进程隔离(见 §3.1 原文)。

**Jupyter 官方架构页**给出了"为什么需要 server 居中"的一手表述——理由是**通信拓扑与职责归属**,不是性能:

> "The Jupyter server is a communication hub. The browser, notebook file on disk, and kernel cannot talk to each other directly. They communicate through the Jupyter server."
> "The Jupyter server, not the kernel, is responsible for saving and loading notebooks, so you can edit notebooks even if you don't have the kernel for that language—you just won't be able to run code."
> "The kernel doesn't know anything about the notebook document: it just gets sent cells of code to execute when the user runs them."

kernels 也是**独立进程**,经 ZeroMQ 传 JSON:
> "IPykernel is a separate process which is responsible for running user code ... Frontends, like the notebook or the Qt console, communicate with the IPython Kernel using JSON messages sent over [ZeroMQ] sockets"
> "A kernel process can be connected to more than one frontend simultaneously. In this case, the different frontends will have access to the same variables."
> "This design was intended to allow easy development of different frontends based on the same kernel"

**⚠️ 缺口**:该页说明了"server 作为通信中枢"与"kernel 独立进程",但**没有直接解释"为什么这个 server 必须是长驻 HTTP/WebSocket 服务"**(多客户端、浏览器访问、会话状态)这一层动机。这属**未找到一手来源**。

来源:[Jupyter — Architecture](https://docs.jupyter.org/en/latest/projects/architecture/content-architecture.html)

Jupyter Server 的配置层则直接印证它是面向浏览器的网络服务:
- `ServerApp.ip` 默认 `'localhost'`, `ServerApp.port` 默认 `0`, `ServerApp.port_retries` 默认 `50`;
- `ServerApp.sock` — "The UNIX socket the Jupyter server will listen on";
- `ServerApp.allow_remote_access` 默认 `False`,并说明这是防 **DNS rebinding** 攻击(Host 头校验,非本地域名返回 403);
- 内核端口默认全部为 `0`(= 随机分配):`control_port` / `hb_port` / `iopub_port` / `shell_port` / `stdin_port`,注释为 `[default: random]`。

来源:[Jupyter Server — Config file and command line options](https://jupyter-server.readthedocs.io/en/stable/other/full-config.html)

**MCP**:规范把本地工具默认设成 stdio 子进程,把"独立进程、可处理多客户端连接"留给 Streamable HTTP:

> "In the **Streamable HTTP** transport, the server operates as an independent process that can handle multiple client connections."

同时规范给定**本地监听的安全约束**(对本项目直接相关):

> "Servers **MUST** validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks"
> "When running locally, servers **SHOULD** bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)"

来源:[MCP Specification — Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)

MCP 架构页进一步给出**"传输方式 ↔ 客户端数量"的官方对应关系**,这正是"要不要服务化"的直接判据:
> "Local MCP servers that use the STDIO transport typically serve a single MCP client, whereas remote MCP servers that use the Streamable HTTP transport will typically serve many MCP clients."

来源:[MCP — Architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

### 4.2 "既能一次性命令运行、又能以服务方式运行"的成熟做法

**成熟做法确实存在,且是官方支持的一等模式:`[project.scripts]` 里同时声明两条命令。**

**源码级一手证据——`black` 仓库的 `pyproject.toml`**(经 GitHub API 读取 `main` 分支内容并核实 sha,原始文件见下):
```toml
[project.scripts]
black = "black:patched_main"
blackd = "blackd:patched_main [d]"
```
即:**同一个发行包**同时暴露一次性 CLI(`black`)与 HTTP 服务(`blackd`);服务端的额外依赖走 optional-dependencies 的 `d` extra,所以**默认安装不会引入服务端依赖**。

来源:[psf/black — pyproject.toml](https://github.com/psf/black/blob/main/pyproject.toml)

pipx 官方教程的真实安装输出同样能看到这两个命令并列(注意 `blackd` 出现在"globally available"列表里,**但安装过程并不会替你启动它**):
```
$ pipx install --cooldown 7 black
  installed package black 24.8.0, Python 3.12.3
  These apps are now globally available
    - black
    - blackd
```
来源:[pipx — Installing applications](https://pipx.pypa.io/latest/tutorial/install-applications/)

**`blackd` 官方文档给出的"为什么要做成服务"的理由——这是本次调研里对第 3 问最贴切的一手动机陈述:**

> "`blackd` is a small HTTP server that exposes *Black*'s functionality over a simple protocol. **The main benefit of using it is to avoid the cost of starting up a new *Black* process every time you want to blacken a file.**"

即服务化的收益被明确定义为**摊销进程启动开销**——一个可被验证/否证的量化理由,而非笼统的"更稳定"。

同时 `blackd` 的安全定位与本地工具一致(对本项目有参照价值):
> "Warning: `blackd` should not be run as a publicly accessible server as there are no security precautions in place to prevent abuse. **It is intended for local use only**."

其默认配置同样是"仅绑本机 + 固定端口":
> `--bind-host` "Address to bind the server to. [default: localhost]"
> `--bind-port` "Port to listen on [default: 45484]"

来源:[Black — Black as a server (blackd)](https://black.readthedocs.io/en/stable/usage_and_configuration/black_as_a_server.html)

### 4.3 `runserver` 模式的优缺点(Django 官方定性,三层证据)

**① 部署文档**:
> "The `runserver` command starts a lightweight development server, which is not suitable for production."

来源:[Django — How to deploy](https://docs.djangoproject.com/en/6.1/howto/deployment/)

**② 部署清单**:专设一节标题即 **"Switch away from `manage.py runserver`"**,原文:
> "The `runserver` command is not designed for a production setting. Be sure to switch to a production-ready WSGI or ASGI server."

来源:[Django — Deployment checklist](https://docs.djangoproject.com/en/6.1/howto/deployment/checklist/)

**③ 源码级**(`django/core/management/commands/runserver.py`,`main` 分支):`help` 字符串为 `"Starts a lightweight web server for development."`;启动时会打印 `"WARNING: This is a development server. Do not use it in a production setting. Use a production WSGI or ASGI server instead."`(可用环境变量 `DJANGO_RUNSERVER_HIDE_WARNING` 抑制);并带 `--noreload` 开关与 `autoreload.run_with_reloader` 重载路径。
来源:[django/django — runserver.py](https://github.com/django/django/blob/main/django/core/management/commands/runserver.py)

**⚠️ 一条不可引用的说法**:"runserver 是单线程"在官方文档与上述源码摘录中**均无明文**,**未获一手确认**,本文不引用。

官方对 `runserver` 的描述性定义:
> "Starts a lightweight development web server on the local machine. By default, the server runs on port 8000 on the IP address `127.0.0.1`."

来源:[django-admin and manage.py](https://docs.djangoproject.com/en/6.1/ref/django-admin/)

**Python 标准库自身对 `http.server` 的定性更为直接**,这直接命中本项目所选组件:

> "Warning: `http.server` is not recommended for production. It only implements basic security checks."

并且官方点出两条安全注意:
> "`SimpleHTTPRequestHandler` will follow symbolic links when handling requests which makes it possible for files outside of the specified directory to be served."
> "Methods `BaseHTTPRequestHandler.send_header()` and `BaseHTTPRequestHandler.send_response_only()` assume sanitized input and do not perform input validation such as checking for the presence of CRLF sequences. Untrusted input may result in HTTP header injection attacks."

来源:[http.server — Python docs](https://docs.python.org/3/library/http.server.html)

**"子命令 serve"的已知缺点(一手)**:Django 官方把它归为"非生产设计";标准库把 `http.server` 标为"not recommended for production"。至于"子命令式的 runserver 相比独立部署有哪些具体运维缺点"的**系统性一手清单**,Django 文档未逐条枚举。**未找到一手来源**(系统性缺点清单)。

## 5. SQLite 在 CLI 场景的并发访问

### 5.1 核心事实:SQLite 不需要常驻服务进程

Python 官方 `sqlite3` 文档开篇:

> "SQLite is a C library that provides a lightweight disk-based database that **doesn't require a separate server process** and allows accessing the database using a nonstandard variant of the SQL query language."

来源:[sqlite3 — Python docs](https://docs.python.org/3/library/sqlite3.html)

### 5.2 多进程并发的一手机制:WAL

SQLite 官方 WAL 文档:

> "WAL provides more concurrency as readers do not block writers and a writer does not block readers. Reading and writing can proceed concurrently."

**写者唯一但不需要外部串行化进程**:
> "Since there is only one WAL file, there can only be one writer at a time."

**关键限制(与本项目直接相关)**:
> "All processes using a database must be on the same host computer; WAL does not work over a network filesystem."

**读一致性由快照保证**:
> "each reader can potentially have its own end mark. But for any particular reader, the end mark is unchanged for the duration of the transaction, thus ensuring that a single read transaction only sees the database content as it existed at a single point in time"

**BUSY 的残余场景(官方承认"mostly true,但有例外")**:
> "This is mostly true. But there are some obscure cases where a query against a WAL-mode database can return `SQLITE_BUSY`, so applications should be prepared for that happenstance."
列举的情形包括:另一连接以 exclusive locking mode 打开、最后连接关闭清理 WAL/shm 期间、以及最后连接崩溃后新连接做 recovery(持排他锁)期间。

来源:[SQLite — Write-Ahead Logging](https://sqlite.org/wal.html)

### 5.3 busy_timeout 与阻塞锁

SQLite 官方(WAL 阻塞锁文档):

> "SQLite may be configured to use POSIX blocking locks by: building the library with `SQLITE_ENABLE_SETLK_TIMEOUT` defined, and configuring a timeout in ms using the `sqlite3_busy_timeout()` API."
> "With blocking locks configured, the only cases in which clients should see an SQLITE_BUSY error are: if the OS does not grant a blocking lock before the configured timeout expires, and when an open read-transaction is upgraded to a write-transaction."

Python 侧 `sqlite3.connect(timeout=5.0)` 的官方语义,正是这个 busy timeout:
> "**timeout** (float) – How many seconds the connection should wait before raising an `OperationalError` when a table is locked. If another connection opens a transaction to modify a table, that table will be locked until the transaction is committed. **Default five seconds.**"

来源:[SQLite — Wal-Mode Blocking Locks](https://sqlite.org/src/doc/tip/doc/wal-lock.md) / [sqlite3 — Python docs](https://docs.python.org/3/library/sqlite3.html)

### 5.4 对本问题的直接回答

**如果一个 CLI 每次调用都是独立进程,它能否安全地用 SQLite 做本地缓存?**
**能**,一手依据:
- SQLite 明文"doesn't require a separate server process";
- WAL 模式下读写互不阻塞,且"one writer at a time"由**文件锁**在引擎层保证,不需要外部常驻进程代为串行化;
- 竞争窗口用 `busy_timeout`(`sqlite3.connect(timeout=...)`,默认 5 秒)吸收。

**是否必须有一个常驻进程来串行化访问?**
**官方文档中没有"必须"这一说。** 锁与串行化是 SQLite 引擎自身的职责。需要额外注意的只有:
- 全进程必须同主机(WAL 不支持网络文件系统);
- 需为 `SQLITE_BUSY` 预留重试/busy_timeout;
- WAL 需要 `-wal` / `-shm` 同目录读写权限(SQLite 3.22.0+ 放宽了只读 WAL 库的打开条件)。

**额外的可靠性事实(WAL-reset bug)**:SQLite 官方公告称,3.7.0(2010-07-21)至 3.51.2(2026-01-09)存在一个罕见的 WAL-reset 数据竞争,可在**两个及以上连接跨线程/进程并发写或 checkpoint 的同一瞬间**导致损坏;3.51.3(2026-03-13)修复。
官方同时评估:"the occurrence rate of this problem in the wild appears to be less than or equal to the expected occurrence rate of SSD malfunctions and/or cosmic-ray hits",并给出建议:升级到含修复的版本。

来源:[SQLite — Write-Ahead Logging §11 The WAL-Reset Bug](https://sqlite.org/wal.html)

## 6. 本地 HTTP 服务的安装与生命周期风险

### 6.1 `nohup ... &` 的确切语义(POSIX 规范)

POSIX 对 `nohup` 的定义:

> "The *nohup* utility shall invoke the utility named by the *utility* operand ... At the time the named *utility* is invoked, the **SIGHUP signal shall be set to be ignored**."

因此 `nohup` 只保证**忽略 SIGHUP**这一件事。规范还说明了两条相关行为:
- 若 stdin 关联终端,实现**可以**重定向 stdin(原因见 RATIONALE);
- 若 stdout 是终端,输出追加到 `nohup.out`。

RATIONALE 里给出的历史坑正好对应本项目的场景:
> "Historical versions of *nohup* did not affect standard input, but that causes problems in the common scenario where the user logs into a system, types the command: `nohup make &` at the prompt, and then logs out. If standard input is not affected by *nohup*, the login session may not terminate for quite some time, since standard input remains open until *make* exits. To avoid this problem, POSIX.1-2008 allows implementations to redirect standard input if it is a terminal."

规范明确建议可移植写法:
```
nohup make </dev/null &
```

来源:[nohup(1p) — POSIX Programmer's Manual](https://man7.org/linux/man-pages/man1/nohup.1p.html)

**重启后是否存活?** `nohup` 的语义**只覆盖 SIGHUP**,不涉及重启。
`nohup` 规范全文**无任何"重启后存活"的承诺**;生命周期管理不在其职责范围内。

systemd 官方文档用**反向方式**确立了该点(一手,原文):`systemd-run(1)` 的 Example 5 说明——
> "A `systemd.scope(5)` unit is used instead of a `systemd.service(5)` unit, because **screen** will exit when detaching from the terminal, and a service unit would be terminated."

同页关于用户会话生命周期:
> "The `user@.service` is started automatically when the user first logs in, and stays around as long as at least one login session is open. **After the user logs out of the last session, `user@.service` and all services underneath it are terminated.**"
> "Enabling lingering means that `user@.service` is started automatically during boot, even if the user is not logged in, and that the service is not terminated when the user logs out."

即:**"随登录会话存活/随系统启动"是 service manager 授予的能力**(`loginctl enable-linger`),不是 `nohup` 授予的。手工 `nohup ... &` 起的进程既不注册为 unit、也不在任何 unit 的 cgroup 内,因此既不在 `systemctl list-units` 里,也不被 `WantedBy=` 拉入启动目标。
对照原文(`systemd-run(1)` Description):
> "If a command is run as transient service unit, it will be started and managed by the service manager like any other service, and thus **shows up in the output of `systemctl list-units`** like any other unit."

来源:[systemd-run(1)](https://freedesktop.org/software/systemd/man/latest/systemd-run.html)

**⚠️ 降级表述**:"重启后必然消失"的**正面**原文表述,本次未取得(只有上述反向依据)。因此本文只陈述"它不在任何服务管理器的管辖内,故不享有任何存活保证",不写成"必然消失"。

**关于"手工后台进程不受服务管理、无法自动重启、无法随系统启动"**:systemd 官方文档**未找到**针对"手工 `nohup` 进程"的专门论述段落;上述 `systemd-run(1)` 与 `systemd.service(5)`("a process controlled and supervised by systemd",`Restart=` 仅适用于受管服务)是可得的最接近的一手反向依据。
来源:[systemd.service(5)](https://man7.org/linux/man-pages/man5/systemd.service.5.html)

### 6.2 Windows `Start-Process -WindowStyle Hidden`

本项目 `scripts/start-service.ps1` 用的是:
```powershell
Start-Process -FilePath $pyCmd -ArgumentList ($pyArgs + @($svc, "$Port")) -WindowStyle Hidden
```

关于该 cmdlet 的**权威语义**,一手来源是 Microsoft Learn 上的 `Start-Process` 参考页。**关键原文已取得**(PowerShell 7.6 版):

> "On Windows, `Start-Process` creates an independent process that **remains running independently of the launching shell**. On non-Windows platforms, the newly started process is attached to the shell that launched. If the launching shell is closed, the child process is terminated."

**对本项目的直接含义**:Windows 上 `Start-Process -WindowStyle Hidden` 起的服务**会独立于拉起它的 shell 继续运行**——所以它不会像 Linux 上那样因终端关闭而受 SIGHUP 影响(Windows 无此信号语义)。**但"独立于 shell"≠"受服务管理"**:它同样不注册为 Windows Service,因此不享有 SCM 提供的自动重启、随系统启动、状态查询。

关于 `-WindowStyle` 的确切语义与失效条件,同页原文:
> "You can't use the `WindowStyle` and `NoNewWindow` parameters in the same command. The parameter doesn't apply to non-Windows systems. When using on non-Windows systems, you never get a new window."

参数类型为 `ProcessWindowStyle`,默认值 `None`。

来源:[Start-Process — Microsoft Learn](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-7.6)

**⚠️ 一条不可引用的说法**:"`-WindowStyle Hidden` 对非 GUI 程序无效"这一具体断言,**未取得官方逐字原文**;官方明确写出的只有上面两条(与 `-NoNewWindow` 互斥、非 Windows 无效)。本文不引用前者。

**Windows 上常驻服务应如何做(一手方向与依据)**:Windows 的一等公民是 **Windows Service**,由 SCM 管理。官方定位:
> .NET 框架文档 "Introduction to Windows Service Applications":服务 "must be installed and started",不能像普通程序那样直接运行。

来源:[Introduction to Windows Service Applications — Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/framework/windows-services/introduction-to-windows-service-applications)

另有一条**相关的官方机制证据**——Session 0 隔离,它说明了为什么"桌面会话里悄悄拉起的进程"与"真正的服务"不是一回事:Microsoft 官方答复原文:
> "Additionally, native Windows services marked as 'Allow service to interact with the desktop' via the Services applet (i.e. services.msc) are no longer granted interactive with desktop rights by the Windows Service Control Manager (SCM)."

来源:[Microsoft Q&A — Service 与桌面交互](https://learn.microsoft.com/en-us/answers/questions/27517/is-there-any-workaround-in-win10-to-allow-service)

Win32 服务总览入口:[Services — Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/services/services)
**⚠️ 缺口**:"后台进程在用户登出/重启后被杀"的**正面**官方段落(Job Object / 会话终止视角),本次未取得确切原文;只取得 Session 0 隔离这一相关机制。

### 6.3 已知运维问题(一手可达部分)

**问题一:靠 shell 手工后台拉起的进程,不受任何服务管理器管辖。**
一手依据:`systemd-run(1)` 原文——受管单元 "shows up in the output of `systemctl list-units` like any other unit";`systemd.service(5)` 把 service 定义为 "a process controlled and supervised by systemd",`Restart=` 仅适用于受管服务。反向即:**未注册的进程不在其中,也就没有自动重启。**
来源:[systemd-run(1)](https://freedesktop.org/software/systemd/man/latest/systemd-run.html) / [systemd.service(5)](https://man7.org/linux/man-pages/man5/systemd.service.5.html)

**问题二:无法随系统启动。**
一手依据同 `systemd-run(1)` Example 5:`user@.service` 与系统启动/登出的关系由 "lingering" 控制——**随系统启动是服务管理器的能力,不是 `nohup` 的能力**。

**问题三:端口冲突。** 见第 7 节。Jupyter 的 `port_retries` 默认 50 是"这是行业公认问题"的一手佐证。

**问题四:旧进程占用文件导致无法升级(Windows 文件锁)。**
一手机制证据(共享冲突):Microsoft 官方文档描述文件被以独占方式打开后,后续写/删请求会遭遇共享冲突——
> "Client A opens the file with `FileAccess.Write` and FileShare.Read (denies subsequent Write/Delete while open). ... Result: Client B encounters a sharing violation."
> 错误描述:"Sharing violation: The operation failed because the object is already opened and does not allow the sharing mode that the caller requested."

来源:[Azure Files — Managing file locks](https://learn.microsoft.com/en-us/rest/api/storageservices/managing-file-locks)
**⚠️ 限定**:这是 Azure Files(REST/共享)视角的文档,**不是 Win32 `ERROR_SHARING_VIOLATION` 的规范页**;Win32 侧对应文档本次未取得。
**本项目自身源码亦可作为一手证据**:`install.sh` 用 `fuser -k "$PORT/tcp"`、`install.ps1` 用 `Stop-Process -Id $_ -Force` 来处理"重启前必须杀掉旧进程"——这正是该类问题的直接表征。

**问题五:启动顺序与冲突的"正解"是什么——socket activation 的官方动机。**
systemd 官方把自己的 socket activation 动机表述为简化 daemon 与依赖、统一 socket 配置:
> "Socket activation was one of the early flagship features of systemd ... Motivation included simplification of daemons, simplification of dependencies between them, and uniform configuration of sockets on which daemon..."
(USENIX ;login: 文章,作者为 systemd 维护者)

以及 `systemd.socket(5)` 原文:
> "Socket units may be used to implement on-demand starting of services, as well as parallelized starting of services."

来源:[systemd.socket(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.socket.html) / [USENIX ;login: — systemd socket activation](https://www.usenix.org/system/files/login/articles/login_june_06_jedrzejewski-szmek.pdf)

**问题六:用户不知情(静默拉起 + 日志丢弃)。**
可佐证的一手事实(本项目源码):安装器把服务输出重定向为丢弃——
```bash
nohup python3 "$SVC" "$PORT" >/dev/null 2>&1 &
```
(`scripts/start-service.sh`)意味着服务崩溃/报错时**不留任何用户可见痕迹**;脚本仅以 `/health` 轮询 24 次 × 0.5s 判断就绪,失败时打印 `service not ready` 并 `exit 1`。
**⚠️ 未找到一手来源**:以"运维故障清单"形式讨论"僵尸进程""用户不知情"的官方或权威项目文档。本文只陈述本项目源码可验证的行为事实。

## 7. 端口冲突处理

### 7.1 固定端口被占用时会怎样(标准库层)

Python 官方 `socket` 文档明确:
> "Errors related to socket or address semantics raise `OSError` or one of its subclasses."

`bind` 到已占用端口属于"address semantics"错误,即抛 `OSError`(具体为 `errno.EADDRINUSE` 一族)。**注**:`EADDRINUSE` 常量本身的逐条语义在 Python 文档中为"Many constants of these forms, documented in the Unix documentation on sockets and/or the IP protocol"——即**转发给 Unix 文档**。

来源:[socket — Python docs](https://docs.python.org/3/library/socket.html)

### 7.2 让操作系统分配端口(port=0)

`socketserver` 官方的 Asynchronous Mixins 示例直接演示了"port 0 = 任意空闲端口",并说明如何取回实际端口:
```python
HOST, PORT = "localhost", 0
server = ThreadedTCPServer((HOST, PORT), ThreadedTCPRequestHandler)
with server:
    ip, port = server.server_address
```
注释原文:`# Port 0 means to select an arbitrary unused port`

并且 `BaseServer.server_address` 的官方语义:
> "The address on which the server is listening. The format of addresses varies depending on the protocol family ... For internet protocols, this is a tuple containing a string giving the address, and an integer port number: `('127.0.0.1', 80)`, for example."

来源:[socketserver — Python docs](https://docs.python.org/3/library/socketserver.html)

### 7.3 主流工具如何处理:Jupyter 的 `port_retries`(一手配置证据)

Jupyter Server 官方配置文档中,两项默认值合起来就是一套完整的端口冲突策略:

> `ServerApp.port` (Int) **Default: `0`** — "The port the server will listen on (env: JUPYTER_PORT)."
> `ServerApp.port_retries` (Int) **Default: `50`** — "The number of additional ports to try if the specified port is not available (env: JUPYTER_PORT_RETRIES)."

即:**默认让 OS 分配(`port=0`)+ 端口被占时向上重试最多 50 次**。

同一页还给出**两种替代寻址方式**的一手配置:
- Unix socket:`ServerApp.sock` — "The UNIX socket the Jupyter server will listen on";`ServerApp.sock_mode` — "The permissions mode for UNIX socket creation (default: 0600)."
- 内核连接信息写入**连接文件**(port file 的等价物):`ConnectionFileMixin.connection_file` — "JSON file in which to store connection info [default: kernel-<pid>.json]" — "This file will contain the IP, ports, and authentication key needed to connect clients to this kernel."
- 且内核各端口默认随机:`control_port` / `hb_port` / `iopub_port` / `shell_port` / `stdin_port`,官方注释 `[default: random]`。

来源:[Jupyter Server — Config file and command line options](https://jupyter-server.readthedocs.io/en/stable/other/full-config.html)

### 7.4 LSP / MCP 的 transport 选择

**LSP**:官方 Overview 明确走 JSON-RPC over 进程间通信,示例实现默认 **stdio**(编辑器把 server 当子进程拉起);另有 socket 形态。规范原文:
> "A language server runs as a separate process and development tools communicate with the server using the language protocol over JSON-RPC."

**MCP**:官方规范给出两种标准 transport,并把本地默认指向 **stdio**(无端口、无端口冲突问题):
> "The protocol currently defines two standard transport mechanisms for client/server communication: 1. stdio, communication over standard in and standard out 2. Streamable HTTP"
> "Clients **SHOULD** support stdio whenever possible."

来源:[LSP Overview](https://microsoft.github.io/language-server-protocol/overviews/lsp/overview/) / [MCP Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)

Jupyter 的 `connection_file`(`kernel-<pid>.json`,内含 IP/端口/认证 key)是**功能等价**的一手证据。

### 8.2 与调研结论的对应关系(事实层)

**支持"可以做成纯 CLI"的事实**
- console_scripts 机制不含后台进程概念,`pipx install` 后用户直接得到命令(§1);
- SQLite 官方明确"不需要独立服务进程",WAL 下读写互不阻塞,写者唯一由文件锁保证(§5.1、§5.2);
- MCP 规范把**本地**工具默认设为 stdio 子进程(§4.1、§7.4);
- `black`/`blackd` 证明"同包同时提供一次性命令与服务"是官方支持的成熟模式,且安装不替用户拉服务(§4.2);
- Lingya 已有可对照的纯 CLI 形态(§1.2)。

**支持"保留服务有理由"的事实**
- 若需要在**多次 CLI 调用之间共享内存态**(如预加载的向量索引、reranker 模型权重),进程内方案每次调用都要重新加载;`socketserver` 文档指出内存态跨进程不可传递(§3.1);
- **这正是 `blackd` 官方给出的唯一理由**:「服务化的收益 = 摊销进程启动开销」(§4.2)。本项目若存在**昂贵的启动成本**(加载 embedding/reranker 模型),则该理由**直接适用**;若启动成本可忽略,则该理由**不成立**——这是一个**可实测**的判据,而非立场问题;
- MCP 规范给出的对应关系是:多客户端 → Streamable HTTP;单客户端 → stdio(§4.1)。**本项目实际有几个并发客户端,决定这一条是否成立**;
- 服务化换来的代价已可观测:固定端口、需自建生命周期管理、日志被丢弃、升级需先杀旧进程(§6、§7、§8.1)。

**能力上不构成障碍的事实**
- SQLite 不需要常驻进程来串行化(§5.4);
- WAL 要求"全部进程同主机 + `-wal`/`-shm` 同目录可写",本项目本来就是单机本地工具(§5.2);
- 唯一需要留意的引擎级风险是 WAL-reset bug,官方建议升级到 3.51.3+,并评估实害率极低(§5.4);
- 已有成熟先例:`black`/`blackd` 在同一包内并列提供 CLI 与服务,且**默认安装不引入服务端依赖**(走 `d` extra,§4.2)。

### 8.3 明确的能力缺口(本次调研未取得一手来源的项)

以下为**已核实为缺口**的清单,均不以推测填充:

1. **`-WindowStyle Hidden` 对非 GUI 程序无效**的逐字官方表述 —— 官方只写"与 `-NoNewWindow` 互斥""非 Windows 无效"。
2. **"登出/重启后后台进程被杀"的正面官方段落**(Job Object / 会话终止视角)—— 只取得 Session 0 隔离这一相关机制。
3. **"nohup 进程重启后必然消失"的正面原文** —— 只有 systemd 侧反向依据,已降级表述为"不享有任何存活保证"。
4. **Python 传 `port=0` 让内核分配端口并用 `getsockname()` 取回** —— Python 文档未明写此句(Unix 语义推断);`socketserver` 官方示例可作行为佐证,但非同一条款。
5. **Win32 `ERROR_SHARING_VIOLATION` 的规范页** —— 只取得 Azure Files 视角的共享冲突文档。
6. **Jupyter "为什么必须是长驻 HTTP/WebSocket 服务"的设计动机** —— 官方架构页只说明"server 是通信中枢",无该层明文。
7. **`jupyter_server/serverapp.py` 的 `init_ports` 源码级证据** —— 本环境 `raw.githubusercontent` / GitHub API / jsDelivr 均不可达;Jupyter 端口策略证据级别=**官方配置文档**,非源码。若需源码证据,应在可联网环境补抓。
8. **"pipx vs 下载脚本+手动拷文件"的官方对照** —— 官方对照对象不含此项。
9. **通用 "port file" 传递端口的正式约定** —— 仅取得 Jupyter `connection_file` 这一功能类比。
10. **"僵尸进程""用户不知情"的官方运维讨论** —— 未找到以故障清单形式讨论的一手文档。
11. **Django `runserver` "单线程"** —— 官方文档与源码均无明文,**不可引用**。
12. **LSP "进程隔离带来稳定性"** —— **非**官方理由,不可引用(官方只给复用与标准化)。
