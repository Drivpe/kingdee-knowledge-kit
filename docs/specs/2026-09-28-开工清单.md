## T2　拆词策略：把已写好的判据从文档搬进内核

### 问题

内核的规则拆词器**不知道哪个词稀有、哪个词烂大街**，会把「应用」「状态」这类
几千篇文档共享的泛词也单独拆成一路，导致候选集被撑爆、精确专文被挤到后面。

### 实测（本轮复现，产品线 93，金标 = `knowledge/646787188905978624`）

| 做法 | 实际路序 | 金标位次 | total |
|---|---|---|---|
| 默认（`kd search "<整句>"`，内核规则拆词） | `['应用为禁用状态[网关]', '应用 禁用状态 网关']` | **第 3** | 4303 |
| 手工拆词（`--kw 2510 --kw "<整句>"`） | `['2510', '应用为禁用状态[网关]']` | **第 1** | 1775 |

**同一组词、同一上游，唯一差别是「稀有 token 在第几路」。** 默认路径输给了绕开它的手工路径。

### 用户的要求（本次会话确认）

> 「现在分几路怎么拆词应该是 llm 做的吧？要限制 llm 搜索的关键词不能过于宽泛」

**已核实的现状**：拆词归属**已经是**「LLM 做」的设计——
- LLM 传 `--kw` 时，内核**完全不插手**拆词（`queries` 逐字等于调用方给的词）；
- 只传整句时，内核才用规则拆（这才是泛词的来源）。

所以用户的要求与「把判据挪进内核」是**同一件事的两个入口**：
LLM 自己拆好词就不会有泛词路；而内核的规则拆词是那条会产出泛词的兜底路径。

### 待定决策（开工前必须先定，二者选一）

- **方案 A（推荐）**：把判据挪进内核，让默认路径也能产出「稀有 token 抢第 1 路」；
  文档随之从约 250 行瘦身成一句话。代价：动内核排序相关代码，回归风险高。
- **方案 B**：只把文档写得更硬（强制 LLM 每次必须自己拆词、且稀有 token 必须占第 1 路），
  代码不动。代价：每次搜索都依赖 LLM 自觉执行，漏做即退化为第 3 名。

**决策依据（本次更正的一个事实）**：「检索策略规范」这节是 `c6b6c0f`（**2026-09-27**）
才进 SKILL.md 的，**只跑了 1 天**，不是一个月（工单 #24 虽于 09-18 定票，但判据入文档是 09-27）。
故「文档路线无效」这一判断**证据不足**，不能拿它当支持方案 A 的理由。

### 硬约束（不得违反）

- **ADR-0009**：原句路必须保留（它是工具，不是权重）；
- **ADR-0013 决策 2**：零算法排序**不可动**——调整的是**路序**，不是给条目打分。
  （本轮实测：往排序键注入 `-len(hits)` 会被回归**立刻抓住**，说明这条约束在当前测试下是有效的。）

### 验收

- 金标案例用**默认路径**（不手工拆词）即可排到第 1；
- `python3 tests/kd_regression.py` 全绿；
- `--kw` 入口行为不变（LLM 拆词仍是完全接管）。

### ✅ 完成记录与**验收口径的更正**（2026-09-28 实施后补写）

**实施**:方案 A 落地——`src/kd/_impl/_routes.py` 新增 `_rare_token()` 与 token 路,
配置在 `query_routes.json` 的 `tokenRoute` 段(只认 **≥3 位纯数字串**,拉丁词与中文词一律不前置)。

⚠️ **原验收「金标案例用默认路径即可排到第 1」这句有歧义,须按下面两段读**:

| 「默认路径」指什么 | 实测 | 判定 |
|---|---|---|
| 直接把**含数字 token 的原文整串**交给 search(`kd search "2510 应用为禁用状态[网关]"`) | queries `[2510, 2510 应用…[网关], 应用 禁用状态 网关]` → **第 1** | ✅ 达标 |
| 直接把**不含数字 token 的整句**交给 search(`kd search "应用为禁用状态[网关]"`) | queries `[应用为禁用状态[网关], 应用 禁用状态 网关]`,连测 3 次**恒为第 4** | ❌ **在信息上不可达** |

**为什么第二种不可达**:金标 `646787188905978624` 是靠 `2510` 这个错误码命中的,
而那句整句里**根本没有 `2510`**。内核无从知道用户想问 2510——要求"默认路径排到第 1"
等于要求内核猜出一个输入里不存在的词。故原验收的第二种读法**不成立**,不是实现缺口。

**真正被修的差距**是第一种读法:改前该形态是**第 3**(token 混在原句里、排在第 2 位之后),
改后是**第 1**。同时规格表里那条"手工绕开"(`--kw 2510 --kw "<整句>"`)从"必须"
降级为"可选"——**默认路径已达标**。

**教训(与本文档末尾那条同型)**:验收标准里"默认路径"这个词必须**写清输入是什么**,
否则实施者与验收者会对同一个词读出不同的东西。已按上表把口径钉死。

## T4　防错机制：`contract.json` 的检查当前是空转的重言式

### 用户问「检查有用吗」——分两层答

**这个机制想解决的问题是真的，且发生过**：提交 `d753719` 的原话记录了「删掉 3 个字段后
测试计数没跟上，而没有任何信号」——这是真实漏报。

**但它现在这道检查等于没用**（本轮实测）：

| 注入 | 回归结果 | 真实输出 |
|---|---|---|
| 从 `contract.json` 的 `resultKeys` 删掉 `products` | **35/35 全绿** | `kd search` **真的少了一个字段** |
| 代码侧新增 `productsV2`，声明不动 | **35/35 全绿** | — |

**根因**：`tests/kd_regression.py:902-908` 的 `t_manifest_projection` 拿
`_manifest_project` 的输出键集去比 `RESULT_KEYS`——而 `_manifest_project`
**正是用 `result_keys()` 决定产出哪些键的**。两边同源，恒等成立。
它自称「字段集的双向断言」，实测是**回声与回声自比**，两个方向都抓不住。

**实际危害**：它让后人**以为有保护**。没有检查时人会小心；有一个永远绿的检查，
改配置的人会以为「测试过了，没事」。

### 要做的

把检查的比对对象从「程序自己读的声明」换成**程序真实的输出**
（喂合成上游走完整链路，或直接对 `core.search()` 的结果断言）。一断自环，改配置就会立刻变红。

### 验收

- 从 `resultKeys` 删任一字段 → 回归**变红**并给出准确诊断；
- 代码侧新增未声明字段 → 回归**变红**；
- 正常状态下 35 项（或调整后的项数）全绿。

### ✅ 完成记录（2026-09-28 实施后补写）

**修法**:新增 `tests/kd_regression.py` 的 `t_result_keys_vs_real_output`,三段对账:
① **冻结基线**(`FROZEN_RESULT_KEYS`/`FROZEN_TOP_KEYS`)—— **刻意不派生自 contract.json**,
打断"被测代码读声明、断言也从声明派生"的自环;② **真实输出**——打桩上游走完整链路
(`core.search` → 归一 → 归并 → 投影),对 `results[]` 的实际键集断言,不再借用
`_manifest_project` 的入参/出参同源关系;③ **注入自检**——断言这个对账**真的会红**。

**注入验收(两个方向都实测)**:

| 注入 | 旧形态 | 现形态 |
|---|---|---|
| 从 `resultKeys` 删 `products` | 35/35 **全绿**(漏报) | ✅ 变红,诊断指向冻结基线并给出改法 |
| 代码侧新增 `productsV2`(声明不动) | 35/35 **全绿**(漏报) | ✅ 三处同时变红 |

⚠️ **同批还抓出第二处恒绿的自环**(原计划只点名了 `t_manifest_projection`):
`t_contract_fallback_in_sync` 自称"兜底集与声明的漂移会被抓住",实测**同样恒绿**——
它比的 `cp.result_keys()` 在声明可读时**根本不经过兜底集**。已改为直接比
**兜底常量本身**,并加"模拟声明读不到 → 必须回落兜底集"的反向验证。
实测:注入兜底集漂移(删 `products`)现在会红,修前不会。

**验收结果**:回归 43 项离线 + 58 项联网全绿;两处自环均已断开且有注入证据。
