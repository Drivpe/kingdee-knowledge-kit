## Problem Statement

四个用户可感知的问题,全部有实测背书:

1. **agent 执行检索太慢**。典型工作流(`search` 3 路 + `read` 2 篇)中位 **2372 ms**。
   慢的根因不是限速,是**路由与深读的循环都在串行发请求**——实测"只把串行改并发、
   不碰任何红线数字"即可降到 **976 ms**。
2. **问答帖一律没有链接**,而它其实可点。现行 `linkPolicy` 把 `question` 判为 `no-link`,
   依据是"问答恒不可点"——**该结论已被推翻**:正确形式 `/questions/<帖子号>/answers/<回答号>`
   实测 22/22 可点,内核当前拼的 `/question/<帖子号>` 才是 22/22 不可点。
   调用方因此拿不到任何问答来源的跳转。
3. **搜到了却不给,而且不报错**。搜「微课」返回 `total: 212`,而 `results` 只有 **2 条**,
   `routeErrors: []`、`scanNote` 写"1/1 路完成"。真相是上游给了 8 条 `LearningCourse`,
   内核认不出该类型、**静默丢弃**。调用方看到"212 条命中、无匹配",会告诉用户"官方没这类资料"
   ——而库里其实有。
4. **离线测试组会真发上游请求**。用钩子跑完整 48 条离线用例,**抓到 1 次真实上游请求
   且 48/48 全绿**。承重点是装机自检(`install.sh` / `install.ps1`)——**跑在用户机器上**,
   有网就发,没网就静默吞进 `routeErrors`。根因是网络出口分裂成两个,没有任何单一注入点
   能拦住全部请求。

另有三项影响面较小的缺陷(测试守护缺口、导入期快照、子模块被遮蔽),一并收口。

## Solution

**先立防线、再做提速、最后补能力**,顺序不可重排(依赖关系已定):

1. **出口统一**:让"唯一网络出口"这句话变成真的——两处 import 期快照改为属性访问,
   于是替换 `_net._get_json` 能拦住全部请求;离线泄漏点一并修掉。
2. **补两个测试钉子**先立防线(低成本,且后续改动都要靠它们兜底)。
3. **红线数值上调**到 `burst 7 / rps 5`(唯一真源 `contract.json`),并新增一条钉住新数值的用例
   ——否则它又会变回"匿名常量"。
4. **并发改造**(收益最大的零红线代价项):路由循环与深读循环改并发池,
   典型工作流 2372 → 约 976 ms。
5. **问答帖链接**补回答号并改 `linkPolicy.question`——**同批做,不可拆**,
   否则是"政策允许但内核给不出链接"的空承诺。
6. **`read` 深度收进声明**:`5` 写进 `contract.json` 并加钉子;永不可触发的翻页上限删除。
7. **标签宽容层**:一行 `strip`,容忍空白/尾换行/全角/NBSP。
8. **新增 `other` 档**:收容 3 个已知值之外的 `entity-type`,**默认隐藏 + 新增开关 +
   告知跳过了多少条**;四处同步,漏一处就是"用一处静默换另一处静默"。
9. **零散两项**:导入期快照改为跟随声明、被遮蔽的子模块改名。

**对用户的效果**:同样的检索快一倍多;问答帖能给链接;不再出现"搜到了却说不存在";
装机自检不再偷偷联网;上游类型词表变了不会再静默丢数据。

## User Stories

1. 作为调用方 agent,我希望 `kd search` 的墙上时间显著下降,以便在同样的预算内多读几篇资料。
2. 作为调用方 agent,我希望慢的根因被修在**免费的那一侧**(并发)而不是靠放宽上游礼貌,
   以便提速不以"更容易被上游限流"为代价。
3. 作为调用方 agent,我希望 `search` 与 `read` 的耗时对路数近似线性,以便我能预估一次检索的成本。
4. 作为调用方 agent,我希望问答帖条目也带可点链接,以便在答案里给用户一个能打开的出处。
5. 作为调用方 agent,我希望问答帖链接**带回答号**,以便点开直接落在被引用的那条回答上,
   而不是只看到帖子而找不到依据。
6. 作为调用方 agent,我希望同帖合并时**优先取采纳回答**的回答号,以便链接指向的解就是答案依据。
7. 作为调用方 agent,我希望 `linkPolicy` 对 `question` 改为给链接,以便政策与内核能力一致。
8. 作为调用方 agent,我希望上游给的**每一种**实体类型都被收容,以便不再出现"total 很大、
   results 很小"而没有任何解释的情况。

16. 作为调用方 agent,我希望重复词仍然被**去重**(不发两次同样的上游请求),以便不浪费请求数。
17. 作为调用方 agent,我希望 `read` 的深读深度**写在声明里**,以便它是可追溯的契约而不是代码里的魔数。
18. 作为调用方 agent,我希望 `read` 遇到上游错误与"资料就这么多"时给出**不同的**截断原因,
    以便我知道该重试还是该接受现状。

22. 作为维护者,我希望"唯一网络出口"这句话是**真的**,以便测试能用一个开关拦住全部网络。
23. 作为维护者,我希望离线测试组**真的不联网**,以便它在任何机器上都是确定的。

## Implementation Decisions

### 接缝(已确认)

**双层接缝**,两层各司其职:

- **网络层接缝** `_net._get_json` —— 拦住**全部**上游请求的唯一开关。
  出口统一后,替换它即可让整内核零网络。这是"离线组真的不联网"的实现基础。
- **业务层接缝** `_upstream._search_upstream` —— 保留。测试用它注入"上游会返回什么",
  不必自己造响应结构。现有回归辅助函数(`_patched_search` / `_manifest_via_full_chain`)
  与联网组均依赖它,保留可避免大面积重写。

两层都不新建。出口统一的本质是**修掉两处 import 期快照**(`_upstream` 与 `_detail`
各有一处 `from ._net import _get_json`),改为属性访问;`_manifest` 已经是属性访问,
不动。同一函数区内另有一处**限速器快照**要一并处理。

`_net._get_json` 的替换点必须与"限速器可注入"一起考虑:`_net._RATE is _config._RATE`
当前为真——同因。限速器的注入路径要与网络出口统一同批确定,否则"拦住网络但拦不住限速"
会让并发改造的测试失去控制手段。

### D1 出口统一(前置,必须在并发之前)

两处 import 期快照改为**模块属性访问**,使替换模块属性即生效:

| 位置 | 现状 | 改为 |
|---|---|---|
| `_upstream` 顶部 | `from ._net import _get_json` | `from . import _net` + 调用点 `_net._get_json(...)` |
| `_detail` 顶部 | `from ._net import _get_json` | 同上 |
| `_upstream` / `_detail` 的限速器 | 经 `_config` 的快照进入 `_net` | 与网络出口一并走属性访问 |

`_upstream._search_upstream` **不改为属性访问自己的调用者**——`_manifest` 已经是属性访问,
保持原样。

**两处过大的 docstring 一并改掉**(`_upstream` 说"`_search_upstream` 是全内核唯一的网络出口"
**是错的**——深读侧 5 个调用完全不经过它;`_impl/__init__` 沿用了这条错话)。
准确措辞:「**检索侧**的唯一出口」。

**离线泄漏点**:`tests/kd_regression.py` 中那条用 `cli("search", ...)` 起**子进程**的用例
(`cli()` 用 `subprocess.run`,进程内桩不继承)。处置:**改为进程内调用** `core.search`
(它本来只断言 `effectiveProductId`,进程内同样能断言),不留任何真发请求的路径。

### D2 两个测试钉子(先立防线)

- **`cli._guard` 的 `op`**:`read` 遇上游 404 时的 hint 靠调用点手写 `op="read"`,`删掉它
  48 条离线用例全绿`。钉子要点(已双版本验证):必须走 `cli.main(["read", ...])` **真调用路径**
  (直接调 `_guard(op="read")` 在 `op` 被删后仍会通过,测不到回归);必须打桩 `cli._out`,
  **不能**用 `redirect_stdout`(后者内部调 `sys.stdout.reconfigure`,而 `io.StringIO` 没有该方法)。
- **`ANSWER-SPEC` 措辞**:文档里的措辞没有回归守护,同批补一条。

### D3 红线数值与钉子

`contract.json` 的 `limits.rate.interactive`:`{burst: 3, rps: 2.5}` → `{burst: 7, rps: 5}`。
`jitterMs` 不动。

依据(ADR-0017 决策 2):`burst` 对齐"单次操作最大请求数"(`maxKeywords = 7`);
`rps` 翻倍仍在"人类手动操作密度"内;**放宽只对 ≥4 路生效,3 路及以下行为完全不变**
(`delay` 恒为 0)。

必须**新增一条钉住新数值的用例**:现有回归只断言档名 `"interactive"`,没有任何用例引用
`burst` / `rps` 的具体数值,故数字改动不触及测试——**这正是它当初变成"匿名常量"的原因**。

### D4 并发改造(零红线代价,收益最大)

**路由并发**:`_manifest` 里的路由执行循环改并发池。约束:

- **保持路序**:`route_lists` 与 `route_errors` 的最终顺序必须仍按路号,不得由完成先后决定。
  排序契约不变——仍是 `(首次出现的路序号, 该路内上游名次)`。
- **失败隔离不变**:单路失败仍走 `routeErrors`,不拖垮整轮。
- `done` / `total` 的累加要并发安全(`total` 取 max)。
- 用**标准库**并发池(Python 3.8+ 可用),不引入依赖。

**深读并发**:`_detail` 的问答深读有两处循环——翻页循环与逐条详情循环。
逐条详情循环(最多 5 条)可并发;翻页循环受 `totalPages` 依赖,须先取首页再决定。

**回归要求**:ADR-0017 明确要求把 `_RateLimiter` 的**并发安全**纳入回归——
现实现的 sleep 在锁外、`_next` 在锁内,结构本身是线程安全的(20 轮 × 7 并发压测无异常、
`_next` 单调性保持),但它**从未在并发场景下被真正使用过**。

⚠️ **未实测边界**:并发只测到 **7 路**(`maxKeywords` 上限),**10+ 路服务端行为未测**;
分钟级长窗口限流未测。不得外推。

### D5 问答帖链接(同批,不可拆)

**形式**:`/questions/<帖子号>/answers/<回答号>`。实测 22/22 可点;
`/question/<帖子号>`(单数)22/22 死;`/questions/<帖子号>`(复数无 aid 段)4/4 死。
回答号**必须精确**(`+1`、`1`、`0` 均落 `/error/404`)。

**回答号来源**:`_upstream._norm_item` 的 answer 分支**原本就拿得到**(`x["id"]`,
当前被丢弃)。帖级合并时应**取采纳优先**(`isAdopt`),无采纳时回落上游首条。

**同批改 `linkPolicy.question`**(`no-link` → `link`),否则是"政策允许但内核给不出链接"的空承诺。

**`contract.json` 的 forbidden 备注要修正**:现写「不要把 `question/` 改写成 `questions/`
(复数)——实测该路径同样不存在(15/15 全 302)」。该备注**仍有效但理由错了**:
复数路径并非"不存在",而是**必须带 `answers/<aid>` 段**。

⚠️ **遗留未测**:带回答号的长形式在**登录态**下的行为未测(全部证据为匿名侧)。

### D6 `read` 深度收进声明

- `max_detail = 5`:实测最大值恰为 5,现在恰好不截断但**依据缺失**(是巧合)。
  **写进 `contract.json` 的 `limits`** 并加测试钉住。
- 翻页上限(`max_answer_pages`)与配套机制**删除**:实测抽 10 个问答帖全部 `totalPages=1`,
  再采 25 条帖子回答数中位 2、90 分位 4、最大 5;要触发需单帖 >60 回答,**0 条**。**永不可触发**。
- **公开签名不变、不加命令行参数**。理由:`ADR-0016` 决策 3 删 `--budget` 的先例——
  没有调用方可用它,就等于画上去的旋钮。

⚠️ **释义留证**:handoff 原文写「`5` 写进声明、`2` 和 `3` 删掉」。复核文档表格里可控的数字
只有 `max_answer_pages=3` 与 `max_detail=5` 两个,故执行口径为 **5 保留并声明、3 删除**。
(删掉翻页上限后,理论上一个超长帖会发更多请求——当前零下达,若将来出现须重新评估。)

### D7 标签宽容层

`_manifest._norm` 的 `(x.get("entity-type") or "").lower()` 改为加 `strip`,
容忍空白/尾换行/全角/NBSP。

**为什么这不是小事**:`_norm_item` 的形参契约写着「`et` 已小写」,**完全依赖唯一调用方遵守**、
函数内部零防御。把调用点的 `.lower()` 去掉,`_norm_item` 会退化为大小写敏感、
**全量静默丢弃**——而 48 条离线用例**测不出来**(直调 `_norm_item` 的用例自己传小写,
绕过了 `_norm` 这一层)。

### D8 `other` 档(最大改动面)

**动机**:上游至少 6 种 `entity-type`,内核只认 3 种,认不出的一律 `return None` 静默丢弃。

**对外类型名**:`other`。默认**隐藏**,新增开关放出,并在隐藏时**告知跳过了多少条**。

**四处同步**(漏一处就是"用一处静默换另一处静默"):

1. `ENTITY_KINDS`(对外类型白名单);
2. `contract.json` 的 `resultKeysByType`(新增 `other` 一档)与 `linkPolicy`(新增 `other`);
3. `read` 的 `_DETAIL_FN` 白名单。

⚠️ **2026-09-29 更正:原第 4 项「`_URL_OF` 模板」已撤销** —— `other` 恒 `no-link`,
该模板被实测确认为生产死键(哨兵实验 + 删键后 results 逐字段相同),已删除。

**链接政策**:`other` 落 **`no-link`**。依据是**本轮复验**(`docs/research/2026-09-29-额外类型链接形式复验.md`):

| 类型 | 网页形式 | 判定 |
|---|---|---|
| `LearningCourse` | `/school/detail/<id>` | **死**(推翻上一份文档的"200 可点"——那是 `/error/404` 页本身返回 200) |
| `LearningCourse` | 另 8 种候选形式 | 全部死 |
| `LearningPath` | 未确认 | 未确认 |
| `KnowledgeSpecial` | `/knowledge/specialDetail/<id>` | **依 id 而异**(1 活 3 死,严格交替复验 6 轮排除限流) |
| `LearningBroadcast` | 上游自带 `url` → `live.vhall.com` | **第三方域**,与 vip 域政策不是一回事 |

即**额外类型没有任何一个网页形式被多轮次确认为活的**。按 `linkPolicy` 的保守方向
(少给一个链接,不误导读者),落 `no-link`。

**`read` 侧**:`other` 档**不进** `_DETAIL_FN`。`read(kind="other")` 必须给出**准确的**
错误提示——区分"非法 kind"与"合法但本档没有全文端点",不得沿用 `bad_kind` 那条会把人
引到"我传错了"方向的 hint。

**fixture 要求**:验收须含**一条真实上游响应 fixture**。当前仓库一条都没有,
回归样本是合成的、只造 `Answer`/`Article`/`Knowledge` 三个值——**这正是本缺陷长期未被发现的原因**。
课程样本可用仓库内既有的 `docs/research/2026-09-06-school-course-sample.json`(全部 `LearningCourse`×10)
作真实数据来源,但注入路径须经真实出口,不得只调内部函数。

**附带事实(实现时须知道)**:课程条目的 `id` 有**两种形状**——小整数(`"6898"`)与雪花串
(`"200641239941605888"`)混排,上游另给 `xId` 形如 `"LearningCourse-6898"`。
**不得**按长度或字符集判 id 形状。

### D9 零散两项

- **导入期快照**:`_public` 的 `_DEFAULT_PRODUCT_ID = default_product_id()` 在 import 期求值,
  注入声明默认值后不跟随。修法:显式 `None` 分支改为 `return default_product_id()`(一行),
  让"显式 None"跟随声明。**签名默认值不能改成动态**——回归用例断言
  `sig.parameters["product_id"].default == DEFAULT_PRODUCT_ID`。
  (`default_product_id()` 现在**零运行时消费者**,这是修它的原因。)
- **子模块被遮蔽**:`_impl` 包属性 `_detail` 被 `from ._detail import _detail` 覆盖成**函数**,
  于是 `import kd._impl._detail` 拿到函数、`kd._impl._detail._get_json` 抛 `AttributeError`。
  测试已为此写了绕道 `sys.modules` 的 helper。修法:改名为 `_detail_fn` 或删除该导出
  (它不是 `cmd_health` 的依赖,也无测试引用包属性形态)。

### D10 丢词口径(执行用户裁定,非重新裁定)

用户原话:「**重复的就不要提示了,非重复的超上限的提示**」。

- `keywordsDropped` 现有算法(去重后词数 − 上限,下界 0)**恰好符合该口径**,保留。
- **撤掉"重复词那一支的提示"**:即 `routesDegraded` 顶层键、`degraded` 计算、
  `scanNote` 的「路数塌缩」句、以及 CLI 的 stderr 对应句。
  删除而非置恒 false——留一个恒 false 的键是"死机制",与本仓"不留占位/不承诺不存在的能力"冲突。
- **去重本身保留**:不得对同一 query 发两次上游请求。
- 影响:`tests/kd_regression.py` 中明文钉「同词重复必须报塌缩」的那条用例须改;
  `ADR-0016` 决策 4 的措辞须更新。

### D11 排序(执行用户裁定)

`_manifest_rank` 是**恒等函数**(200 组随机构造下 `sorted(order, key=rank) == order` 恒成立)。
用户裁定:**删掉 `sorted` 与 `rank`,直接保序**。行为等价,少一层伪装;
`ADR-0013` 的零算法排序红线不变——只是把"排完等于没排"变成"明确不排"。

**真正的顺序契约不在那段代码里**,而在一个未命名的隐式不变量上:`order.append` 与
`first_seen[...]` 被**同处写入**。删 `rank` 时须把这条不变量写成注释,否则下一个人会以为
"顺序不重要"。

### 不做的事(明确划出)

- **不删 `project_top` 的第二次调用**(`_public` 那处):它是 `stats` 的声明闸门,
  删了 → 47 通过 / 1 失败。另一处(`_manifest` 返回前)删掉确实 48/48 全绿,
  但**已否决**——它删的是本函数自己输出的最后一刀,收益是一次字典遍历(微秒级),
  代价是内部契约从**闭合**变**敞口**。这是"为测试绿灯而改",不是真问题。
- **不动 `_PER_ROUTE_WANT = 10`**:实测 `pageSize` 10→3 只省 9 ms,收益可忽略。
- **不实现跨进程共享限速**(SQLite + WAL + `busy_timeout`):`ADR-0011` 决策 5 的原案前提
  (自动循环脚本)已随 `scripts/` 目录删除而消失,当前无消费者。
  ⚠️ 但须知道:多进程并发(用户本机的 Agent Teams 模式)会真实命中此缺口,
  上游看到的是聚合 13+ req/s 而非名义值。这一点已写进 ADR-0017 决策 3 留证。
- **不碰 `ADR-0004` 的 `1 请求/秒 / ≤200`**:那组数字约束的是已删除的发现层脚本。
- **不改 `spec/2026-09-28-开工清单.md:497` 的「无并发」**:它是施工期实验纪律,`spec` 不回改。

## Testing Decisions

**好的测试在这里长什么样**:

- 只测**外部行为**,不测实现细节。断言的对象是"用户真的会拿到的东西"
  (`core.search` / `core.read` 的返回体、CLI 的 stdout/exit code),
  而不是内部函数的入参/出参对。
- **验证用测试是三段对账**:`冻结基线 + 真实输出 + 注入自检`。
  字段集期望值**不得**派生自 `contract.json`——那样是回声与回声自比,**两个方向都静默通过**。
- **新增用例必须用变异测试验证它抓得住各自钉的病**,不是"看着绿就行"。
  现有先例:两条测试钉子均已双版本跑通(原版 PASS、变异版 FAIL)。

**测哪些模块**:

- `_net` / `_upstream` / `_detail` 的**出口统一**:用 `_net._get_json` 层接缝断言
  "替换它之后零真实请求"。
- `_manifest` 的**并发改造**:断言路序不变、失败隔离不变、请求集合与串行版相同。
- `_config` 的**限速**:钉住 `burst=7 / rps=5` 的具体数值;
  并把 `_RateLimiter` 的并发安全纳入回归(ADR-0017 决策 4 的前置要求)。
- `cli` 的 **`_guard(op=...)`**:走 `cli.main` 真调用路径。
- `_upstream._norm_item` 的 **`other` 分支**与**标签宽容**。
- `contract.json` ↔ 兜底键集的**交叉核对**(两边同源不得漂移)。

**同型先例(可照抄的形态)**:

- 出口注入:`_manifest_via_full_chain` / `_patched_search`(打桩 `_search_upstream` 后跑完整链路)。
- 三段对账:字段集检查(`_frozen_keys_of` + 真实输出 + `_assert_type_partition_has_teeth`)。
- 变异自检:`_assert_declared_mismatch_fails` / `_assert_code_side_new_key_fails`。
- 文档一致性钉子:`t_link_policy_docs_in_sync` / `t_docs_no_dead_mechanisms`。

**回归基线**:离线 `python3 tests/kd_regression.py` → **48/48 全绿**(Python 3.14.4)。
联网组 `--online`(15 条)本规格不强制要求跑通,但 `kd health` 必须 OK、
且须跑通一条真实搜索端到端。**本轮上一轮未跑联网组。**

## Out of Scope

- **`other` 档的 `read` 全文获取**。`LearningCourse` 的接口端点(`/schoolapi/rest/course/<id>`)
  实测可用且含逐字稿(样本 3135 / 6542 / 17935 字符),但那是**另一档工作**:
  需要 kind → 端点的映射,而 `LearningPath` 无端点、`LearningBroadcast` 的 url 在第三方域。
  本轮只做"不再静默丢弃",不做"收进来还能全读"。
- **`LearningBroadcast` 的第三方域链接政策**。它的 `url` 指向 `live.vhall.com`(实测可点),
  但本政策的全部证据都建立在 vip 域上,不能套用。
- **`KnowledgeSpecial` 依 id 而异的可点性**。1 活 3 死的分布与 `linkPolicy`
  按 kind 一刀切的形状不兼容,不据此给链接。
- **登录态下的链接行为**。全部证据为匿名侧;带回答号的长形式在登录态下未测。
- **10+ 路并发与分钟级长窗口限流**。未实测,不外推。
- **采集/评测脚本与跨进程限速**。见"不做的事"。

**判定纪律(血泪,务必遵守)**:

判定可点性已累计**四个坑**,任一都会得出错结论:
1. 只看首跳状态码 → 两个方向都判错(`question/` 失效页最终状态码恰为 **200**;
   `article/248777993676668672` 首跳 302 但**迁移成功**、最终页可点);
2. 单次观测不排除限流 → 把限流期表现推广成路径级常量;
3. 误把偶发的一次通过归因成"请求头差异" → 会得出一个**不存在的规则**;
4. 必须跟随重定向看最终 URL(`url_effective`),落 `/error/404` 判死。

⚠️ 本轮复验又添一条:**`/error/404` 页本身返回 200**——`/school/detail/<id>` 因此被上一份
文档误判为"可点"。任何"某路径可点/不可点"的结论**必须多轮次重复 + 各形式对照**。

**上游纪律**:匿名链路,**零账号 / 零 cookie / 零点数**是红线;探测间隔 ≥1.05 s;

(上一轮有一个子代理要求 ≤40 次请求、实际约 66 次)。

本轮红线争议正是反例(README 声明了约束却不写数字)。新增任何声明字段前,先确认它有消费者。
