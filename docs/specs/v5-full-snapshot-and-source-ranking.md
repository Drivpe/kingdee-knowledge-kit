# Spec:v5.1 corpus 全量快照 + 信源排序链

> 产出自 2026-09-06 grill 会话(三轮定案,全记录见交接文档 17 执行记录与本次会话)。
> 状态:ready-for-agent(仓库暂无 issue tracker 配置,发布于 docs/specs/,装好 gh CLI 后可补发 GitHub issue)。
> 术语遵循 CONTEXT.md(corpus 语料目录/发现层/上游缓存/时间网格/匿名链路);决策依据见 docs/adr/0004。

## Problem Statement

用户提问时希望**一次检索就找到答案**,不依赖"越用越厚"的语料积累。当前 corpus(1209 篇 stub)是 42 个词的时间网格首轮产物,覆盖偏科:高频域文档标题可搜,冷门域与正文级细节(报错文案/字段/步骤)第一次检索大概率搜不到,必须退回在线多轮检索。

另外两处与预期不符:①图游走(recommendArray)是永远不触发的死代码(匿名不可达),误导后续维护者;②"问答/官方文档/课程/更新日志"四类资料的检索入口没有明确的优先级顺序,agent 每次自行临场发挥。

## Solution

1. **corpus 升级为全量快照**:一次性枚举搜索索引内全部文档(实测宽词「金蝶」totalElements≈117,854),只落标题+摘要 stub(约 60MB),保证 rg 首次检索的全面性;全文仍按需深读写穿,不做正文预抓。
2. **信源排序链落策略层**:SKILL.md 写死每类资料(问答/官方文档/文章/发版说明/课程)的固定检索顺序,rg corpus → kd search 分类型 → 站外 websearch 兜底;服务端 /ask 不动。
3. **剔除图游走死代码**,发现层收敛为:全量快照(一次性)+ 时间网格增量 + share 引用 + usage 沉淀。
4. **发版说明半墙**单独立项跟踪(ID 可读、搜索不可达);课程(school)信源逆向单独立项(交接文档 18)。

## User Stories

1. 作为金蝶用户,我第一次提出一个冷门域问题时,agent 用 rg 在本地 corpus 就能找到候选文档,所以我不必等待多轮在线检索。
2. 作为金蝶用户,我提出一个正文级细节问题(报错文案/字段名)时,agent 能通过标题/摘要定位文档并一次深读写穿,所以第二轮检索即得全文。
3. 作为金蝶用户,我问"某个版本更新了什么"时,agent 知道发版说明的检索链和它的边界(索引外),所以得到诚实的结果或明确的"暂不可达"。
4. 作为金蝶用户,我问课程相关问题时,agent 走课程检索链(websearch 兜底)并标注"站外/课程信源",所以不把课程内容与社区文档混淆。
5. 作为 agent,我先 rg corpus 再决定是否打上游,所以上游请求只花在本地没有的文档上。
6. 作为 agent,我拿到一份每类资料固定的检索顺序,所以不再临场发挥、结果可复现。
7. 作为 agent,我深读一篇 stub 后它自动升级为全文,所以 corpus 的深度随真实使用自动增长。
8. 作为维护者,我看到发现层只有四条明确的腿(快照/时间网格/share/usage),所以不需要理解一段永不执行的图游走代码。
9. 作为维护者,我跑一轮 verify 就能确认全量快照脚本的幂等性(重复摄入=unchanged),所以重跑/断点续跑无副作用。
10. 作为维护者,我在 ADR 里能查到红线豁免的完整记录(谁豁免、豁免多少、为何),所以红线历史可审计。
11. 作为用户,全量枚举期间我随时可以 Ctrl-C,重跑脚本从断点继续,所以一次失败不浪费已抓取的部分。
12. 作为用户,我想知道全量快照后 corpus 的覆盖率(占索引全量的百分比、金标命中数),所以"全面性"有数字可验。
13. 作为 agent,回答里引用 corpus 文档时给出原链接(front-matter url),所以用户可以直接跳转官方页面核对。
14. 作为用户,课程与帮助中心的内容被明确标注为"站外语源",所以我能区分官方社区文档与站外结果的权威差异。

## Implementation Decisions

- **全量枚举通道**:复用现有 /api/search(关键词+分页),宽词集合×实体类型切片(global=true,不按产品线切),每查询最多 50 页×25 条(实测深分页被服务端静默钳制),全量去重后经 POST /corpus 摄入为 stub。
- **频率豁免**:用户拍板豁免一次——1 请求/秒,预计 ~7500 请求(约 2-2.5 小时);红线原文(时间网格单轮 ≤200)不变,本次豁免单独记录在 ADR-0004 与红线节。
- **不换通道的前提(已定)**:后台调研(docs/research/2026-09-06-bulk-ingest-channels.md)确认社区侧无更优批量通道——sitemap 冻结在 2018、无 RSS、开放平台 API 全是需授权的业务 WebAPI、无可用 WAP 端;关键词切片枚举方案维持。**补充通道**:帮助中心 help.open.kingdee.com 实测为 DokuWiki,`?do=index` 一次返回 1077 个页面 URL 且每页支持 `export_raw` 原文导出、robots 对索引友好——作为「官方文档」类的低成本批量补充通道单列小任务,不与社区三类实体枚举混流。
- 调研中「图游走省请求量」的建议不采纳:与本项目一手探测矛盾(匿名拿不到 recommendArray,见 ADR-0004)。
- **stub 与全文的边界不变**:全量快照只含标题+摘要+原链接;正文仍只在上游被请求(深读)时写穿覆盖 stub——"上游被请求,语料才更新"的不变量不动。
- **图游走剔除**:删除 recommendArray 提取与 recommendations 字段及对应 stub 写入;share 引用落盘(discovered_by=share)保留;ADR-0004 增补剔除记录与探测结论。
- **信源排序在策略层**:SKILL.md 固化每类资料的检索链(问答:rg corpus/answer → kd search --type answer;官方文档:rg corpus/knowledge → kd search --type knowledge → help.open.kingdee.com 站外兜底;文章:rg corpus/article → kd search --type article;发版说明:rg corpus → 待探测 ID 通道 → site:vip.kingdee.com 站外兜底;课程:站外检索,标注信源);服务端不融合多信源(延续信号重排被评测否决的教训,语义编排交 agent)。
- **增量机制保留**:时间网格脚本与词表保留,全量快照完成后角色转为时间增量(只翻新页)。
- **断点续跑**:全量脚本以(查询词,页码)为进度单元落盘进度文件,中断重跑跳过已完成单元。
- **发版说明通道探测**:本会话试 2-3 个匿名候选(发版说明专题页 SSR 数据/知识分类目录/knowledgeSpecial 专题接口);探到则接入时间网格词表,探不到记录在案,不阻塞其余工作。
- **课程逆向**:单独立项(交接文档 18),本 spec 只负责 SKILL 里的站外兜底段。

## Testing Decisions

- **唯一测试缝 = 本地 HTTP 服务 API**(现有 verify_ksearch.py 的调用方式),不为全量脚本开新缝:脚本只消费 /search 与 /corpus,与 verify 同缝。
- 只测外部行为:verify 已有 v5 检查(corpus 写穿/文件规范/摄入幂等/deprecate 标注)全部保留;新增"全量脚本幂等"检查——对同一批 items 重复摄入,第二次必须全部 unchanged(复用 verify 中假 OpenAI 端点的同款手法,起一个假 /search 服务喂固定分页,全量脚本对假服务跑通去重与断点逻辑,不打真上游)。
- 图游走剔除的回归:现有 31 项 verify 全绿即视为无破坏;`recommendations` 字段从详情响应消失是预期行为,verify 不断言它的存在。
- 全量完成后的验收报告(对齐 docs/discovery-report-v5.md 体例):索引覆盖率(去重文档数/117,854)、评测集金标在 corpus 的命中率变化(usage/reference 两层)、rg 冒烟(关上游解一道历史 usage 题)。

## Out of Scope

- 课程(school)接口逆向与接入(交接文档 18 立项)
- 发版说明 ID 通道的正式实现(本轮只探测;实现视探测结果另行立项)
- 全文/正文预抓、后台定时任务、常驻进程(红线:上游没被请求,语料才更新)
- 服务端多信源融合排序(/ask 改造)
- 向量语义召回(ADR-0004:冻结待墙)
- 登录态任何通道(零账号红线)

## Further Notes

- 后台调研 agent 的结论(批量通道是否存在更优解)是启动全量跑前的最后一个输入;若其发现低成本通道,Implementation Decisions 第 1、2 条随之修订。
- 全量快照与"发版说明 ID 通道探测"相互独立,可并行推进。
- 红线豁免是一次性的:下一次全量刷新(若有)需重新拍板;日常增量仍走 ≤200 请求/轮的时间网格。
