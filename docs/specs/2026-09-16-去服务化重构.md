# Spec:去服务化重构 —— 检索内核改为库 + 纯 CLI

> 产出自 2026-09-16 grill 会话(一轮定案;交接上下文见 `docs/handoff/灵基模型切换-交接文档21` 与 `/tmp/handoff-2026-09-16-去服务化spec与开工.md`)。
> 状态:ready-for-agent。决策依据见 `docs/adr/0011-decommission-http-service.md`(勿重开)。
> 术语遵循 `CONTEXT.md`(kd / 检索内核 / 资料包 / 多路关键词 / chunk 切片 / 匿名链路);
> 已按 ADR-0011 标废除的词条:检索服务、落地缓存、索引语料、查询内语义重排。

## Problem Statement

用户(实际第一用户是 agent)要问一个金蝶问题时,当前必须先有一个常驻后台服务在跑,`kd` 才连得上:

- **装完即埋雷**。安装器会把一个 1351 行的 HTTP 服务静默拉起为后台进程(`nohup ... &` / `Start-Process -WindowStyle Hidden`),占着固定端口 4097。服务挂了、端口被占、升级时忘了 `fuser -k`,表现都是 `kd` 全命令不可用,而崩溃日志被丢进 `/dev/null`,用户无从诊断。
- **代价没有换来收益**。服务化唯一站得住的技术理由是"避免每次重新加载昂贵资源"。本项目里那是 `semantic_rerank` 的 96MB ONNX 模型,而它**默认关、模型从未下载、`tokenizers` 未装、评测未过门**——这个理由从未被激活。实测对照:CLI 冷启动 0.09–0.15 秒,服务常驻占 37.4MB 内存。
- **发行方式是孤例**。本仓当前是"无元数据 + 拷文件 + 手写 shim + 安装阶段自动拉起服务"。15 个主流 CLI 样本中带服务的 4 个(`blackd`/`jupyter lab`/`streamlit run`/`label-studio`)**无一在安装阶段自动拉起服务**;15/15 都发 PyPI,12/15 有 `pyproject.toml`。
- **装不上是真问题**。本机 `~/.kingdee-kit`、`~/.agents/skills` **均为空**——本套件从未真正安装过,一直在仓库内运行。上一轮真机实测还发现两个装机阻断缺陷(`install.sh` 漏拷 `semantic_rerank.py` 与 `query_routes.json`;`install.ps1` 无 UTF-8 BOM 却含 41 行中文,PowerShell 5.1 在中文 Windows 上按 GBK 解码直接 ParserError 退出)。

## Solution

把 HTTP 服务整个撤掉,检索内核变成可 `import` 的库,`kd` 是唯一的执行入口:

1. **服务层消失**。十个端点(`/search` `/ask` `/health` `/corpus` `/karticle` `/question` `/answer` `/article` `/share` `/manifest`)与 `docs/API.md` 一并删除,**不留兼容层、不做双路径并存**。
2. **装上就有命令**。用户 `pipx install kd`(或跑一键脚本)之后直接可用,不再有后台进程、端口、生命周期管理。
3. **本地落盘缓存整体取消**。`corpus/`、`~/.lingeebuild/landing`、`data/ksearch.db` 三处全撤;连带 `SKILL.md` 第 2 步(rg 字段名级精查)整节作废,v6 的"三级回退"退化为两级。接受代价:重复问同一件事要重新请求上游。
4. **`semantic_rerank` 删除**。它要解决的问题(关键词搜不到但语义相关)已由 ADR-0009 的原句路解决——后者零依赖、已上线、有实测背书(原句排第 1 vs 片段融合第 23)。
5. **上游纪律不能松**。去服务后限速状态不再天然共享,而采集类脚本是自动循环,必须改成跨进程共享,否则成倍放大请求速率、触碰"保持人类调用频率"红线。
6. **发行与安装对齐主流**。建 `pyproject.toml` 发 PyPI,保留一键脚本(去掉服务拉起段),支持 `pipx`;技能部署对齐 `ly` 的多 harness 方式。
7. **命名保留 `kd`**。否决改 `ly` 前缀:`~/.kd/` 已被 `ly` 占用且存 ERP 凭据,改名会造成配置目录碰撞。
8. **先建新路径并验证,再删旧代码**。避免一次性跨两仓大改导致问题无法定位。

## User Stories

1. 作为用户,我 `pipx install kd` 之后直接就能跑 `kd ask`,所以不需要理解"后台服务要活着"这个前提。
2. 作为用户,我不再遇到端口 4097 被占用导致的 `kd` 全命令不可用,所以不需要 `fuser -k` 这种操作。
3. 作为用户,`kd` 崩了会有正常的报错输出,而不是日志被丢进 `/dev/null`、什么都看不到,所以我至少知道发生了什么。
4. 作为用户,升级版本时我直接重装即可,不需要先杀旧进程,所以升级路径是可预期的。
5. 作为用户,我停止使用后 `kd` 不留下任何常驻进程在后台占内存,所以我的机器状态可解释。
6. 作为用户,我在 Windows 上双击一键脚本(或无 Python 环境时)也能装上,所以低门槛路径仍在。
7. 作为用户,我已有的 `kd search / read / ask / share / health` 调用方式**一个字都不用改**,所以升级不破坏我的既有用法。
8. 作为 agent,我调 `kd ask` 拿到的资料包结构(多路命中 + topK 全文 + 预算摘要 + 召回信号)与之前完全一致,所以我的合成流程不受影响。
9. 作为 agent,`kd ask` 的"100 字符硬闸"行为不变(超限压回并显式报错),所以我不必重新适配上游限制。
10. 作为 agent,我拿到的错误仍是带 `hint` 的 JSON、退出码仍是 0/1/2,所以我的判错逻辑不需要改。
11. 作为 agent,`kd read --chunk` 仍能按官方 chunkId 匿名还原块全文,所以 ADR-0007 的溯源端不受重构影响。
12. 作为 agent,命令面新增的 `--global`(原 `--global_`)可直接写,所以我不必再绕过下划线这个实现细节。
13. 作为 agent,`--size` 与 `--topk` 的命名不再让人在两处语义相近的参数间猜,所以我调用时不再需要回查文档确认。
14. 作为 agent,我不再依赖"服务活着"这个前置条件,所以被调起时少一层失败模式。
15. 作为维护者,我改上游适配只需改 `kd.core` 一处,CLI 与测试都跟着,所以改动面是可预期的。
16. 作为维护者,我能在 REPL 里直接 `import kd.core` 调 `ask/search/read`,所以定位检索问题不必先起服务再手工拼 JSON。
17. 作为维护者,`kd.core` 的公开面只有 `ask`/`search`/`read` 三个高阶函数,所以内部实现可以自由重构而不构成破坏性变更。
18. 作为维护者,我删掉 HTTP 层后代码少了一层编解码,所以检索链路的阅读路径变短。
19. 作为维护者,我不再需要维护"端点契约文档"(`docs/API.md`),所以文档漂移源少一个。
20. 作为维护者,`semantic_rerank` 及其两个额外依赖被删除,所以安装体积与依赖面同时下降。
21. 作为维护者,`corpus/`、`landing/`、`ksearch.db` 三处落盘体系撤掉后,我不再需要处理它们的写穿、幂等、并发一致性问题,所以维护负担显著下降。
22. 作为维护者,我删掉了 `run_eval.py` 全套,所以"去服务后跨进程限速怎么实现"这个隐藏风险直接消失。
23. 作为维护者,我删掉了 `corpus_fullscan.py` 与 `discovery_sweep.py`,所以自动循环类脚本不再存在、不再触碰上游频率红线。
24. 作为维护者,`scripts/` 下只剩人工触发的少量脚本,所以"哪些东西会自动打上游"一眼可查。
25. 作为维护者,我删掉 `run_eval` 之后不再需要为它保留 SQLite 共享限速,所以迁移范围收敛。
26. 作为维护者,数据的删除是可核验的——我跑一遍仓库审计能确认没有残留对已删模块的引用,所以不会留下"永不亮的路"。
27. 作为维护者,安装器不再拷 `service/` 四个文件,所以"漏拷导致服务静默退回默认值"这类装机缺陷从根上消失。
28. 作为维护者,装机自检从"验服务 `/health` 报的配置是不是真配置"改为"验 `kd` 可执行且能跑通一条命令",所以验证的是用户真正会用的东西。
29. 作为维护者,技能部署与 `ly` 对齐(canonical 目录 + 软链、失败回退拷贝),所以两个套件的安装心智一致。
30. 作为维护者,README 与 `SKILL.md` 里指向已删能力的描述(`kd manifest`、`rg` 精查、落地缓存)被同步清理,所以文档不再承诺不存在的能力。
31. 作为维护者,`CONTEXT.md` 的词条与代码现实一致(四条已标废除),所以下一个会话不会按旧地图行动。
32. 作为维护者,我知道 `~/.lingeebuild/releasenotes` 是空库这件事被诚实记录,所以不会误以为它是可用的终审依据。
33. 作为维护者,我按本 spec 实施时每一步都有可回滚点,所以出问题能定位到具体一段改动。
34. 作为维护者,我保留了 `kd` 这个名字,所以 `~/.kd/` 与 `ly` 的凭据路径不发生碰撞。
35. 作为维护者,我把 `#3`/`#2` 两个依赖已废除体系的 issue 明确关闭,所以 triage 队列不再被失效工单污染。

## Implementation Decisions

### 模块布局

```
src/kd/
  core.py      # 检索编排:plan_routes / knowledge_search / _rrf_fuse / _select_top /
               # ask_bundle / chunk_text / top_chunks / Budget / RateLimiter / clamp_query
  docstore.py  # 落盘模块(取消缓存后仅保留上游请求所需部分)
  cli.py       # argparse 入口(原 cli/kd.py 的命令面)
  __main__.py  # python -m kd
```

可行性依据:`cli/kd.py` 与服务之间**只有 HTTP、零 import**;服务本身是 `docstore`(114 行)+ `semantic_rerank` 加一层 HTTP 包装。旁证:`releasenotes_ingest.py` 早已直接 `import docstore` 不走服务;`kd read --chunk` 也已在 CLI 内直连上游。

### `kd.core` 公开 API 边界

**只暴露 `ask` / `search` / `read` 三个高阶函数。** `plan_routes`、`_rrf_fuse`、`_select_top`、`Budget`、`RateLimiter`、`chunk_text` 等全部作为内部实现,上游接口变更全部封在 `core` 内,CLI 只负责参数解析与 JSON 输出。理由:把内部实现变成事实上的接口会让后续每次重构都成为破坏性变更。

### CLI 命令面

**命令名全部保留**:`search` / `read` / `ask` / `share` / `health`,功能与参数语义不变。借迁移顺手修两处参数命名:

- `--global_` 改为 `--global`(下划线是 argparse 规避关键字的痕迹,内部 `dest` 可自行处理);
- `--size`(search)与 `--topk`(ask)命名统一——两者语义相近,统一后可减少调用时的回查。

契约不变:stdout 只出 JSON、进度走 stderr、错误是带 `hint` 的 JSON、退出码 0=成功 / 1=上游或内部错误 / 2=用法错误、永不交互、永无 ANSI 色码、强制 UTF-8。

### `kd manifest` 删除

**删除 `kd manifest` 子命令,与主流对齐。** 已核实:black / ruff / aws / poetry 这类主流 CLI 只有 `--help`(人读长文),不做机器可读的能力清单 JSON;`pipx manifest` 存在,但它导出的是"已装应用清单",不是能力自发现,两者不是同一回事。

连带必须同步清理的引用点(共 10 处,漏改会让文档指向不存在的命令):

- `skills/kingdee-knowledge/skills/kingdee-knowledge/SKILL.md` 第 29 行;
- `README.md` 的第 13、24、43、72、73、97、111 行;
- `install.sh` 第 86 行、`install.ps1` 第 125 行;
- `CONTEXT.md` 中如涉及该命令的描述。

**该 JSON 里指向服务的字段(端点、参数、URL)在服务删除后即为死数据**——它们描述的接收方不复存在,既无人读也无法验证。这是删除的实质理由,不只是"主流不做"。

### 上游纪律:跨进程限速

**`run_eval.py` 全套删除**。它当前依赖服务的共享限速器;ADR-0011 已定评测体系因精度不足搁置、验收以手工用例为主,删掉它可让"跨进程限速"这条隐藏风险直接消失,同时与 `corpus_fullscan.py`、`discovery_sweep.py` 一起清空 `scripts/` 下的自动循环脚本。

因此**本轮不实现 SQLite 跨进程共享限速**(ADR-0011 决策 5 中"必须补 WAL 与 `busy_timeout`"的前置条件随之**不再适用**)。保留的人工触发脚本(`releasenotes_ingest.py` / `releasenotes_probe.py`)维持既有频率档位(交互会话短突发 2-3 请求/秒 + 随机抖动,后台/摄取任务 1 请求/秒)。

**若将来重新引入自动循环脚本**,SQLite 共享限速必须重新评估——届时 `journal_mode=WAL` 与显式 `busy_timeout` 是硬前置,不是可选项。

### 数据目录与落盘

`corpus/`、`~/.lingeebuild/landing`、`data/ksearch.db` 三处缓存取消。`docstore` 模块保留但收缩到"上游请求所需"的最小面。`data/eval/` 随 `run_eval` 一并处置(评测集与用例池不再保留)。

`~/.lingeebuild/releasenotes/` **不在取消范围内**——它是 ADR-0005 下唯一保留的预囤语料,是"官方已修复"类问题的终审依据。⚠️ 但它**当前是空库(0 篇)**,而 `SKILL.md` 已把它写成可用的终审依据,这一"文档承诺了不存在的能力"作为独立待办跟踪,不在本 spec 范围。

### 打包与安装

- 建 `pyproject.toml`,`[project.scripts] kd = "kd.cli:main"`,发布到 PyPI;
- **主推 `pipx install kd`**(PyPI 官方为"安装命令行应用"场景给出的指引方案;注意其措辞是 "consider",PyPA 明示不做全局唯一推荐);
- **保留一键脚本**(`install.sh` / `install.ps1`)作为无 Python 环境或 Windows 双击场景的兜底路径,删掉其中三段:拷贝 `service/` 四个文件、拉起服务、验 `/health` 配置;
- 装机自检从"验服务配置"改为"验 `kd` 可执行且能跑通一条命令";
- 技能部署对齐 `ly`:canonical 目录 + 软链(失败回退拷贝),覆盖 `workbuddy` / `zcode` / `opencode` / `pi` / `agents`。

**必须守住的既有约束(已踩过坑)**:`kd.cmd` 保持 **ASCII-only**(cmd.exe 按 OEM 码页读 `.cmd`,非 ASCII 注释会吃掉后续命令);`install.ps1` 保留 **UTF-8 BOM**(否则中文 Windows 上 PowerShell 5.1 解析崩溃)。

**`scripts/start-service.ps1` / `start-service.sh` 一并删除**——服务不存在后,这两个脚本没有服务可起。

### `ly` 转发入口

**本轮先不做。** 去服务化重构本身已跨两仓,`ly` 转发作为独立工单另行处置(ADR-0011 决策 6 已定形态:`ly` 侧新增转发入口,用 `shutil.which("kd")` 定位并转发子进程,6 个命令全部转发,保持 `kd` 的 stdout=JSON / stderr=进度 / 退出码契约;两包独立发布、不互相依赖)。

### 存量 issue 处置

- **`#3`** Spec:v5.2 全量快照覆盖度估计与枚举效率升级 —— **关闭**。依赖已废除的 corpus 体系。
- **`#2`** 帮助中心(help.open.kingdee.com,DokuWiki)批量通道接入 corpus —— **关闭**。同上,其目标是往 corpus 灌数据,而 corpus 已取消。
- **`#17`** Spec:M 探针——官方向量库实际覆盖度测量(A/B 双通道) —— **保留**。它测的是官方向量库的覆盖度,与去服务化无依赖关系。

关闭时在 issue 里注明原因并指向本 spec,避免后续会话重新捡起。

### 实施顺序(硬要求)

**先建新路径并验证,再删旧代码。** 具体分段:

1. 建 `src/kd/`,把纯逻辑函数从服务文件搬进来,`cli.py` 改为直接调用;
2. 用代码级回归用例验证新路径与旧行为一致(见 Testing Decisions);
3. 确认一致后,删服务文件、删十个端点、删 `docs/API.md`、删 `semantic_rerank`、删落盘缓存、删 `run_eval` 全套、删 `manifest` 及其 10 处引用、删 `start-service.*`;
4. 改安装器与 `pyproject.toml`;
5. 全仓审计残留引用。

**跨仓注意**:`verify_ksearch.py`(33 项断言,大多打 HTTP 端点)按下面 Testing Decisions 处理。

## Testing Decisions

**什么算好测试**:只测外部行为,不测实现细节。对本次重构而言,"外部行为"指的是**用户与 agent 实际会用的东西**——`kd` 命令的输入输出契约、资料包的结构、错误形状与退出码、上游硬闸行为。测"HTTP 端点返回 200"这类断言在服务删除后失去对象,也没有迁移价值。

**测试范围(已确认)**:

- **要**:代码级回归测试——"拆完之后,以前能干的事现在还能干"。例如把一个长问句交给 `kd ask` 仍能跑通;超过 100 字符的查询仍会被压回并显式报错。
- **不要**:**统计精度类评测**——对同一问题反复跑多次、算命中率 / 置信区间 / recall@k 这类指标,本套件不做。这是 `run_eval.py` 与 `data/eval/` 一并删除的原因,也是"评测体系因精度不足搁置"的落地。

**旧测试处置**:`verify_ksearch.py` 的 33 项断言**删掉**,用新的代码级用例集替代。理由是其断言大多直接针对 HTTP 端点(状态码、JSON 形状、协议细节),换成内部调用后测的东西已经不同,逐条改写不如重写。

**测试位置与形态**:放在 `tests/`,以 `kd.core` 的公开面(`ask`/`search`/`read`)与 `kd` 命令的进程级调用为观测点。上游相关断言需可在无网络时降级(标记为需上游的用例单独归组,默认不跑)。

**先 TDD 再删旧代码**:新用例集在删旧代码**之前**建立,与实施顺序第 2 步一致——这是 ADR-0011「先建新路径并验证,再删旧代码」的具体执行手段。

**既定手工验收(ADR-0011 决策 8)**:以手工用例为主,重点两条——BOM 金标、长问句 100 字硬闸逐条验。环境侧注意:Linux 上 `cmd.exe` 可用但输出是 GBK(显示问题,不代表程序错);`kd.cmd` 与 `install.ps1` 必须在真机 PowerShell 上实跑,不做静态推断。
