# 单入口检索链路重构(2026-09-18)

> 状态:**已冻结**,作为本轮全部并行改造的**唯一契约输入**。改代码、改测试、改守卫、改文档一律以本文件为准。
> 上游依据:`/tmp/handoff-2026-09-18-refactor-per-target-shape.md`(走查结论)+ 2026-09-18 用户三项拍板。

## 0. 一句话

把检索链路收敛成**一条**:`kd search` 出清单 → LLM 挑 → `kd read` 取全文。
**删除 `ask` 及其全部专属件**(RRF 融合、深读 topK、chunks、synthesisBrief、displayOrder)。
**排序不再引入任何算法评分**:上游综合排序已经排好,内核只做**去重**,顺序由「路序 + 路内上游原生序」决定。

## 1. 三项拍板(用户 2026-09-18 明确指令,不得重开)

| # | 决策 | 原文要点 |
|---|---|---|
| 1 | **保留 `search`,`ask` 全删** | 「留 search, ask 全删」 |
| 2 | **不使用算法排分** | 「你是用官方的综合排序用不同关键词搜索的,所以结果已经排过序了,因此我们要做的就是删除重复的内容,让 llm 自行判断需要阅读哪篇」 |
| 3 | **允许狠改** | 「狠狠地改,只要更好用」;上传纪律不变:**本地攒提交,禁推远端** |

### 决策 2 的推论(重要,勿误读)

- **不得**按「命中路数」排序——那也是一种算法评分。`hitRoutes` **降级为纯信息字段**,供 LLM 参考,不参与排序键。
- **不得**恢复 RRF / 加权 / 任何形式的分数。
- 排序键只剩 `(路序, 路内上游名次)`——两者都**不是算出来的**:路序来自 `_plan_routes` 的路定义顺序(原句路恒为第 1 路),路内名次直接来自上游返回顺序。
- 清单里**不出现任何 score 字段**(`fusedScore` 随 ask 一并删除)。

## 2. 公开面契约(kd.core)

### 2.1 白名单(工单 #26 机制的延续)

```python
__all__ = ["search", "read", "QueryTooLong", "UpstreamError", "InternalError"]
```

`kd.core` 顶层可属性访问的非双下划线名字 **恰好**为上述 5 个。`ask` 从白名单移除后**必须不可属性访问**(`hasattr(kd.core, "ask") is False`)。

### 2.2 签名基线(逐字,守卫逐字比对)

```python
search(text=None, keywords=None, product_id=93, page=1, page_size=10,
       global_=False, sorts_type=1, type_=None, max_routes=None, budget=None,
       rate=None) -> dict

read(kind, oid, budget=None, rate=None) -> dict
```

**相对旧签名的每一处改动及理由**:

| 改动 | 理由 |
|---|---|
| `ask` 整条删除 | 用户拍板 |
| `search` 新增 `keywords=None` | 打通「LLM 拆词」缺口:`_plan_routes` 早已支持 `keywords`,只是 `search` 没接出来。LLM 在**调用层**拆好词后传进来,**内核永不含 LLM 调用** |
| `search` 的 `text` 由必填改 `None` | `text` 与 `keywords` 二选一:只给关键词时不需 text。**两者并用是推荐用法**:`text` 放整句/完整报错串并充任原句路(见缺陷 D) |
| `search` 的 `routes` 改名 `max_routes` | 旧名与返回结构的 `results[].routes[]`(该条来自哪几路)**同名不同义**,是真实混淆源 |
| `search` 删除 `rerank` | 死形参:多路清单路径下无任何行为(旧 docstring 自述) |
| `read` 删除 `refresh` | 死形参:内核恒在线,`refresh` 恒无效 |
| `rate` 保留(两函数) | 上游纪律的可执行出口;档名从 `query_routes.json` 读,传不存在档名回落 `interactive`(**不再有任何 `background` 档承诺**) |

### 2.3 修的既有缺陷(随本轮一并修净)

**缺陷 A——`global_` 是假参数(真 bug)。** 旧 `_search_manifest(global_=…)` 收到该参数后**从未下传**,`_route_search_once` 内部把 `global_` 硬编码为 `False`。后果:CLI 的 `--global`(跨全部产品)**静默无效**。
修法:`global_` 必须透传到每一路的 `_search_upstream`。

**缺陷 B——`sorts_type` 是幽灵参数。** 旧 `_search_manifest(sorts_type=…)` 收到后从未使用,实际排序由每路路由自带的 `sortsType` 决定,缺省靠 `.get("sortsType") or 1` 兜底。
修法:保留为**默认值**,仅当某路未自带 `sortsType` 时生效;原句路仍固定 `sorts=1`(ADR-0009 定案,不改)。

**缺陷 B2——`sortsType=0` 被 `or` 链吞掉。** 见下方**缺陷 H**。

**缺陷 C——多路塌缩无表达。** `信用额度控制` 等输入上原句路与产品路的 terms **逐字相同**,去重后只剩 1 路,而返回结构不表达这一事实。
修法:新增顶层字段 `routesDegraded: bool`——`queries[]` 去重后的实际路数 < 计划路数时置 `true`,并在 `scanNote` 写明「路数塌缩 N→M」。**这是表达事实,不是评分**。
⚠️ 该字段的假阳性见下方**缺陷 G**。

**缺陷 D——`keywords` 分支整条丢掉原句路(2026-09-27 修)。** 旧 `_plan_routes` 的 `keywords` 分支直接 `return`,**从不构造原句路**(原句路只在自动拆解分支里 `insert(0, …)`)。后果:调用方采用"我给整句 + 我给拆好的词"这一最自然的用法时,反而丢失了 ADR-0009 实测最值钱的那一路,且返回体不表达这一丢失。
修法(用户 2026-09-27 裁决:**默认就是要原句的**,不留开关):

| 场景 | 原句路来源 | 其余关键词 |
|---|---|---|
| `text` 非空 + `keywords` | `text` 充第 1 路(`kind="raw:question"`,`sortsType=1`) | 依次成 `explicit` 路 |
| `text` 为空 + `keywords` | **第 1 个 `keywords`** 充第 1 路(`kind="raw:question"`,`sortsType=1`) | 第 2 个起成 `explicit` 路 |

两条分支的路数与 `queries` 内容**相对旧实现完全不变**(只给 `keywords` 时第 1 词不再另占一路,而是升格为原句路),变的只是第 1 路的 `kind` 与 `sortsType`——即它从"片段路"精确为"相关性排序的原句路"。`text` 与某关键词逐字相同时由上层的 `_dedupe_routes` 兜住,不产生同词两路。

**缺陷 E——`keywords` 分支绕过产品线推导(2026-09-27 修)。** `_plan_routes` 的 `keywords` 分支**提前 `return`**,而产品线别名推导只写在规则分支里。后果:问「苍穹 …」并同时把词拆好递进来时,产品线回落成默认 `93`(旗舰版),**拿苍穹的问题去搜旗舰版资料,再当苍穹答案输出**(2026-09-06 串线事故的形态)。而这条分支恰是"调用层 LLM 拆好词后传进来"的入口——即本轮新方向要走的那条路。
修法:把推导抽成**两条分支共用的公共出口** `_derive_product_id(sources, product_id)`,两边都必须经过它。改动不新增对外参数、不改签名,`effectiveProductId` 的回显口径不变。

⚠️ **推导源与优先级**(同日二次补修,由独立验证发现——第一次修法只覆盖了一半通道):

`_derive_product_id` 接的是**有序**来源序列,靠前者更权威。调用方按"这句话是谁说的"排:

| 序 | 来源 | 理由 |
|---|---|---|
| 1 | `text` | 调用方明确给的整句,最权威 |
| 2 | 全部 `keywords` | 产品词可能出现在任意一个关键词里;**且 `text` 为空时第 1 个关键词会升格为原句路**(缺陷 D),它恰好是"整句",最可能含产品词 |

三条实测事实支撑这个设计(每一条都有回归钉子,均经变异测试确认会红):

- **只改"两分支共用"是不够的**:修前 `search --kw "苍穹 XXX"`(text 为空)推出 `93`,而 `search "苍穹 XXX"` 推出 `87`——同一个整句、两条命令行、产品线不同,两者第 1 路 `terms` 逐字相同。故推导源必须包含 `keywords`。
- **不能只看 `keywords[0]`**:`plan(text=None, keywords=["生产单位数量","苍穹"])` 必须推出 `87`。SKILL.md 同时要求"稀有 token 抢第 1 路"与"产品词可能在任意词里",两者只能靠"扫全部关键词"并存。
- **不能把各源拼成一维串**:`plan(text="苍穹 A", keywords=["A","旗舰版"])` 若拼串会因别名表的 dict 序让「旗舰版」压掉 text 说的「苍穹」,推出 `93`。分优先级即保住"`text` 里说的话 > 拆出的片段"。

⚠️ **为何这层优先级有实际后果**(实测):同一问句下 `--product 87` 与 `93` 的 **top10 零交集**(total 943 vs 2702,两次复采逐字全等,排除抖动)。**产品线判定错误 = 拿完全不同的语料作答**,故这不是内部洁癖。
⚠️ **另:推导源必须在 `kws.pop(0)` **之前**捕获**,否则 `text` 为空时升格为原句路的那个关键词恰好从推导源里消失。

**多产品别名同现的裁决规则(2026-09-27 定义)。** 一个源里可能同时出现多个别名(如「苍穹 旗舰版」),而原实现取的是**别名表的第一个命中**——别名表顺序来自 `query_routes.json` 里 dict 的**字面量书写顺序**,那不是任何人承诺过的契约。实测把遍历序反转,`"苍穹 旗舰版"` 的结果即从 `93` 变 `87`,而**全部回归仍全绿**(无钉子守着)。考虑到产品线判定直接决定召回语料(实测 87 与 93 同问句下 top10 零交集),靠配置顺序偶然固定是不可接受的。

**规则**:取**在文本中出现位置最靠前**的别名;位置相同则取更长者。
选它的理由:不受别名长度偏置,且**完全不依赖配置顺序**(有专门用例反转别名表后重跑断言结果不变)。
⚠️ 这是**新定义的规则**,会改变少数组合的既有行为(如 `"苍穹 旗舰版"` 原按表序得 `93`,现得 `87`)。跨产品线同现的问句本身罕见,两个方向都可辩护;此处选"先出现优先"以求可解释性。

**`_derive_product_id` 的入参契约:必须传序列。** 签名从 `(text, product_id)` 改为 `(sources, product_id)`。误传字符串时 `for src in sources` 会**逐字符**迭代,每个字符都不含多字别名 → **静默返回原值、无异常无日志**。故函数开头就地归一(`isinstance(sources, str)` 时包成单元素列表),并有专门用例钉住该契约。这是迁移期最容易踩的形态,因为旧签名 `(text, …)` 传的正是字符串。

**已知边界(非本轮引入,记录在此)。** `_derive_product_id` 是**纯子串匹配、无否定处理**:`'不要搜企业版'` 会推出 `1`、`'与苍穹无关'` 会推出 `87`。这是字面匹配的固有缺陷。本轮方向是"把判定交给调用层"(显式传参即不被字面改写),故该缺陷的影响面被收窄,但**不传参时的自动推导仍会中招**。彻底解决需替换整个字面匹配机制,不在本轮范围——**本段列的三条(否定词、多别名裁决、sources 契约)同属该机制范畴,不要以为边界只有否定词一条**。

**缺陷 F——显式传入的产品线被问句字面覆盖(2026-09-27 修)。** 原实现无条件用问句别名改写 `product_id`,不分"调用方显式指定"与"默认兜底"。最严重的一例:显式 `--product 0`(本节明文规定的"真不过滤")+ 问句含「苍穹」→ 被改写成 `87`,该语义**静默消失**;同理显式 `87`/`1` 也会被问句改写成别的值。
根因(经 `git log -S` 核实):`de0afea` 时代 `search()` 的默认值是 `None`,推导覆盖的是"无兜底"语义;**`22f8e35` 把默认值改成 `93` 后,同一条推导变成了覆盖"用户的真实输入"**。
修法:`_derive_product_id` 只在 `product_id` 为 `None` / `93`(默认兜底)时推导;任何其他显式值一律尊重调用方。
语义后果(本轮定案):**产品线由调用层(LLM)判定**,内核不做字面二次改写——这是"用语义替换字面匹配"在契约层的落点。ADR-0012「问句产品词优先于默认」的本意(默认是兜底、不是覆盖用户所说)由此被真正贯彻。

**缺陷 G——`routesDegraded` 假阳性(2026-09-27 修)。** 实现直接沿用了 `_dedupe_routes` 的"是否发生重复"布尔值,而该布尔与 `planned` 的截断是两件事。反例:`max_routes=1` + 拆出两路同词 → `planned=1`、去重后实际 `=1`,却回显 `routesDegraded=true`,且 `scanNote` 写出「计划 1 路,去重后实际 1 路」——两个数字相同却说塌缩,自相矛盾。
修法:严格按缺陷 C 的公式判定 `degraded = (去重后实际路数 < planned)`。**截断不是塌缩**——`max_routes` 主动砍掉的路不属于"拆解产出被去重收敛"。两个方向都要保住:正常塌缩仍报 `true`。`routesPlanned` 的口径**不变**(见第 3 节:去重前、受 `max_routes` 截断后)。

**缺陷 H——`sortsType=0` 被 `or` 链吞掉(2026-09-27 修)。** 缺陷 B 的兜底写法 `.get("sortsType") or sorts_type or 1` 用 `or` 链取值,而 **`0` 是 falsy**——某路或调用方明确指定 `sortsType=0`(相关性排序)时会被静默折成 `1`,无任何信号。
修法:新增 `_route_sorts_type(route, fallback)` 显式判空(只把 `None` 当"未给"),保住 `0`。
⚠️ 性质(2026-09-27 实测):上游当前 `sortsType=0` 与 `=1` **等价**(都是相关性排序,`2` 才是时间倒序),故这是**潜伏 bug** 而非已发生的错误召回——现配置恒为 `1` 恰好遮盖了它。仍修:"显式值被静默改写"本身即契约缺陷。

**缺陷 I——`read` 路径的错误提示张冠李戴(2026-09-27 修)。** `cli._guard` 的 hint 全部写死成 `search` 语境,于是 `kd read <错id>` 拿到上游 404 时提示会说"text 超 100 字符"——与 `read` 毫无关系,把排查方向直接带偏。
修法:`_guard(fn, op=…)` 按调用方区分 hint 与 `example`;`read` 的上游错误提示改为指向真实原因(传的 id 与 kind 不匹配 / 实体已被上游删除或迁移)。

**缺陷 J——假 seam 与说瞎话的注释(2026-09-27 修)。**
- `_impl/_detail.py` 的 `_DETAIL_WORKERS = 4` 注释称"详情并发度",实测回答展开是**纯串行 for 循环**,全仓无并发池;该常量被 `scripts/check_core_surface.py` 当"活钉子"保护。→ 删除常量并从钉子清单移除。
- `_impl/_config.py` 的 `_Budget` docstring 称"深读路径经 `ThreadPoolExecutor` 并发进入",实测全仓无 `ThreadPoolExecutor`/`concurrent` 引用(随 `ask` 下线)。→ 更正归因,锁本身保留(仍必要)。
- `_impl/__init__.py` 注释引 `_manifest._indirect`,实际函数名是 `_resolve`。→ 同步。
- `kd/cli.py` 的 `_VALID_KINDS` / `_VALID_TYPES` 是同一集合的两个名字。→ 合并为 `_VALID_KINDS`。

## 3. `search` 返回结构(逐字段冻结)

```
{
  "ok":               bool,     # 恒 true(失败走异常)
  "text":             str|None, # 回显;仅给 keywords 时为 None
  "keywords":         list|None,# 回显调用方给的显式关键词;未给则 None
  "total":            int,      # 各路 totalElements 的最大值
  "queries":          [str],    # 去重后实际检索词,顺序即路序
  "routesPlanned":    int,      # 计划路数(去重前,受 max_routes 截断后)
  "routesDegraded":   bool,     # 见缺陷 C
  "effectiveProductId": int|None,  # 本次**实际生效**的产品过滤(见 3.3;None=未带过滤)
  "page":             int,
  "pageSize":         int,
  "totalPages":       int,      # 清单总页数
  "results":          [entry],
  "routeErrors":      [err],    # 失败路,形状不变:{route,kind,terms,error,code,message}
  "budget_exhausted": bool,
  "scanNote":         str,
  "stats":            {"upstreamCalls": int, "elapsedMs": float}
}
```

### 3.1 `results[]` 条目(清单投影,逐字段冻结)

```
{
  "type":       "knowledge"|"answer"|"article",
  "id":         str,          # 清单单位=条目;answer 用**回答 id**
  "title":      str,          # 清单核心交付物
  "url":        str|None,     # 可访问链接;knowledge/article 可点,answer 可能失效
  "hitRoutes":  int,          # 被几路命中(纯信息,**不参与排序**)
  "routes":     [int],        # 来自哪几路(升序)
  "questionId": str|None,     # answer 专有,仅进展示字段
  "snippet":    str|None,
  "products":   [str],
  "views":      int|None,
  "updatedAt":  str|None,
  "adopted":    bool|None,    # answer 专有
  "answersCount": int|None,   # answer 专有
  "comments":   int|None,     # answer 专有
  "supports":   int|None,     # article 专有
  "questionBody": str|None    # answer 专有
}
```

**不得出现** `contentText`、`fusedScore`、`chunks`、`contentLen`、`useful`(历史残留,出现即 FAIL)。

> 注:`adopted`/`answersCount`/`comments`/`supports`/`questionBody` 由 `_norm_item` 已算出,投影时**透传**——它们是上游原生信号,不是内核算的分。

### 3.3 `effectiveProductId` 必须保留(裁决记录,2026-09-18)

本源设计漏列该键,**执行期由契约走查发现它是真实功能回退,故补入**:

- 该键原为 `ask` 返回体顶层独有(旧 `search` 亦无),`ask` 删除后**调用方失去唯一可执行的产品线判据**——`ANSWER-SPEC.md` 第 8 条要求"引用与合成前核对 `effectiveProductId` 是否等于预期产品线 ID",而它是与 `--product` **同值域**的整数(None=未带任何过滤 / 93 / 87 / 1),可直接比对;`results[].products` 装的是上游中文类目名,**值域不可比**,不能替代。
- `_plan_routes` 早已算出该值(问句出现「苍穹」等别名时覆盖默认 93),只是未外露——**补回零额外成本**。
- 语义:必须回显**推导后实际生效**的值,**不得**回显调用方传入的原始值(否则别名覆盖不可见)。
- 实测三态:默认→`93`;问句含「苍穹」→`87`(别名覆盖);显式 `--product 0`→`0`(真不过滤)。
- ⚠️ **回显值域 ≠ 上游参数值域,二者由一条显式映射相连**(不要用"相等"去断言它):
  `effectiveProductId` 用**调用方词汇**(与 `--product` 同值域,`0` 表示"我显式要求不过滤"),
  而上游只认两种状态——带过滤或**省略该参数**。故 `0` 必须映射为**省略参数**:
  传 `productIds[0]=0` 上游会当真值过滤(实测会把 Knowledge 挤出前排)。
  映射:`None`→省略 / `0`→省略 / `93|87|1`→`productIds[0]=<n>`。
  这条映射本身就是契约:`effectiveProductId` 是"调用方意图的回显",不是"上游参数的转储"。

### 3.2 展示顺序(逐条,无歧义)

1. 路内:严格保持**上游返回顺序**(pageSize=10,page=1 为主,`want` 补齐才翻页)。
2. 路间:按**路序**——清单里任意两条,先取「首次出现的路序号」小者;同路序取「该路内名次」小者。
3. 去重键:`"{type}:{id}"`。answer **用回答 id**(同一帖的不同回答各自成条,不合并)——保持旧 `_manifest_key` 语义不变。
4. **排序键绝不包含** `hitRoutes` 长度、任何分数、任何时间衰减、任何 views 权重。

即排序键为 `(first_route_no, first_pos_in_route)`,旧实现里的 `-len(hits)` 第一维**必须删除**。
