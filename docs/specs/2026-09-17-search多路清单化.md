# Spec: search 升级为多路只出清单 —— 检索从「替你决定」改为「给你挑」

> 产出自 2026-09-17 会话（设计定稿见 `/tmp/handoff-2026-09-17e-search-多路清单.md`，本轮按该文档落地实现）。
> 状态: ready-for-agent。
> 决策依据：交接文档第 2 节四项已定设计（**勿重开**）；本 spec 补充裁决第 4 节五个未决项 + 补全第 3 节实现细节中未钉死的部分。
> 术语遵循 `CONTEXT.md`。本 spec **不重新审议 ADR-0012**（默认产品线 93、不开子代理、答案形态）。

## Problem Statement

`ask` 是当前常规入口，它把「召回 → 融合 → 挑出 topK → 深读」这一整条链路一次做完。这个设计在**报错码类问题**上被实测证伪：

用户拿上游返回的报错原文去检索，`ask` 召回不到目标文档，而 `search` 能。实测对照（检索词 `应用为禁用状态[网关]`，产品线 93，同一时刻）：

| 路径 | 目标文档排名 | 能否读到 |
|---|---|---|
| 上游 `/api/search` 原生排序 | 第 5 | — |
| `kd search` | 第 5 | ✅ |
| `kd ask --topk 4`（RRF 融合后） | **第 8** | ❌ 在 topK 之外 |
| `kd ask --topk 8` | 第 8 | ✅ |

根因在 `_rrf_fuse`。它的评分是 `1/(60+名次)`，这是一个**有损压缩**：它把每一路的绝对排名压成一个按名次倒数的分，再求和。后果有两个方向：

- **奖励泛泛文档**。一篇被多路各自排到第 20 名的文档，四路都得 `1/80`，总分 `0.05`；而一篇被原句路精确命中排第 1 的文档只有 `1/61 ≈ 0.0164`。真正精确的那篇**必然输给四路都不精确的那篇**。
- **惩罚单路精确命中**。目标文档恰好只在原句路命中（这正是词汇鸿沟场景的定义），它在融合里拿不到任何"多路加成"，被压到 topK 之外。

这不是调参能修的——**融合本身在消灭"哪一路命中的"这个信息**。用户要的恰恰是这个信息：先给我标题，我自己看语义相关性，别替我决定。

现有三类使用者因此都受损：agent 拿到的是被融合后的 4 篇，看不到真正相关的第 5 篇；用户无法介入筛选；维护者无法解释"为什么这篇没被召回"——因为决策发生在融合公式里，不可追溯。

## Solution

把 `search` 从**单路精确检索**升级为**多路拆词 + 只出标题清单**，取代 `ask` 成为常规入口。核心是**去掉融合、保留路数信息**：

1. **`search` 变成多路的**。复用已有的 `_plan_routes` 拆词能力（当前只被 `ask` 调用），同样拆出 ≤7 路，每路各发一次上游检索。
2. **丢弃 RRF**。多路结果去重后**按"命中路数"降序排**，只数出现过几路，不做任何加权。路数相同时按上游原生序（保留上游自己的相关性判断）。
3. **只出清单，不返回正文**。每条给 `type` / `id` / `title` / `hitRoutes` / `routes[]`，**不返回 `contentText`**。标题列表交给 LLM 目视筛选——LLM 看到标题的语义判断强于任何公式。
4. **需要全文时走 `read`**。`kd read <id> --kind <t>` 不变，链路不重叠。
5. **`ask` 保留但降级为次要入口**。签名与行为不动（已有调用方与守卫签名），仅不再作为推荐入口。
6. **每路 10 条，总量封顶**。每路 `pageSize=10`，最多 7 路 → 去重前 ≤70 条。实测本次目标在第 5 位，一页足够覆盖。

**这个设计的本质**：把"哪一路命中"从被融合抹掉的中间量，提升为排序的主键——即把决策权交还给调用方（LLM/人），而不是在 CLI 内部用公式裁决。

## User Stories

1. 作为 agent，我用报错原文调 `kd search` 时，能在清单里看到那篇精确命中的文档（它单独占一路），所以我不再因为融合被剥夺目标文档。
2. 作为 agent，我能看到每条结果的 `hitRoutes`（命中几路），所以我可以据此判断"多路都命中的泛文"与"单路精确命中的专文"的区别，而不是被动接受一个总分。
3. 作为 agent，我能看到每条结果来自哪几路，所以当清单里没有目标文档时，我能反推是哪一路没召回到，而不是面对一个黑箱。
4. 作为 agent，我拿到的是标题清单而非 4 篇全文，所以我的上下文开销可控、且由我自己决定读哪篇。
5. 作为 agent，我筛出候选后用 `kd read <id> --kind <t>` 取全文，所以"筛选"与"深读"两步是解耦的、各自可重试。
6. 作为 agent，`search` 三件套的字段仍与旧版兼容（新增字段是增量），所以我既有的解析逻辑不会因为升级而崩。
7. 作为 agent，我显式指定 `--type` 过滤时，路由仍尊重这个过滤，所以我不必为了类型过滤而绕回 `ask`。
8. 作为用户，我拿到的不再是"系统替我挑的 4 篇"，而是一份可扫的标题列表，所以筛选取回了我自己手里。
9. 作为用户，我在报错码、症状描述这类"我知道原文、但不知道官方怎么命名"的问题上，终于能搜到目标文档。
10. 作为用户，如果我确实想要一站式资料包，`ask` 仍然在，所以我的旧用法没有断。
11. 作为维护者，`_rrf_fuse` 从 `search` 链路移除后，检索行为变得**可解释**——排序完全由"命中几路 + 上游原生序"决定，没有隐藏的加权。
12. 作为维护者，融合公式这个"不可追溯的决策点"消失，所以"为什么这篇没召回"这类问题可以被回答（看 routes 的命中情况即可）。
13. 作为维护者，去重键被统一为单一定义（见 Implementation Decisions），所以同一文档不再可能因 id 空间不同被拆成两条或误合。
14. 作为维护者，`answer` 条目的两个 id 空间（回答 `id` / 问题 `questionId`）有明确的主键选择与理由留档，所以下一个会话不会重新踩这个坑。
15. 作为维护者，`search` 的签名变更与守卫 `SIGNATURE_BASELINE` 同步更新，所以判据 5 不 FAIL。
16. 作为维护者，回归用例的白名单字段随返回结构同步更新，所以 `t_search_contract` 反映的是新契约而不是阻碍它。
17. 作为维护者，`_rrf_fuse` 若被删除，`FORBIDDEN_NAMES` 判据仍 PASS（禁用名只需不存在），且删前已确认无外部引用，所以判据 7 不受影响。
18. 作为维护者，上游请求数上升到原本 2-7 倍这件事被显式纳入预算体系，所以批量调用不会失控。
19. 作为维护者，本轮**不改变** `ask` 的融合路径，所以改动面收敛、风险可控，`ask` 的去 RRF 可作为独立后续决策。
20. 作为维护者，安装器与技能文档的同步清单被列出，所以收尾不会漏改（含 `install.ps1` 的 UTF-8 BOM 纪律）。

## Implementation Decisions

### 已定设计（交接文档第 2 节，勿重开）

四项设计原样承接：多路+只出清单、丢弃 RRF、输出标题清单、每路 10 条。本节以下内容为**未决项裁决**与**实现细节补全**。

### 未决项裁决（交接文档第 4 节的五个问题）

**① `search` 的拆词默认开启还是加开关？**

**默认开启，不设 `--multi` 开关。**

理由：加开关意味着两条代码路径长期并存，"多路"与"单路"行为分叉会被测试与文档双重维护，而旧路径的存在意义仅是向后兼容一个**本就只在仓库内运行、调用方是 agent 的**命令（见去服务化 spec：本套件从未真正安装过）。若保留单路，agent 会在两种语义间猜。

代价被显式接受：结果数、请求数、耗时都变（见「预算」）。**需要单路精确行为的场景，用 `--routes 1` 表达**，而不是保留一条并行实现——同一个实现、参数收敛，而不是两套代码。

`--routes N`：显式指定最多用几路（默认 `maxRoutes` = 7，取自 `query_routes.json`）。`--routes 1` 即旧单路语义（但排序仍是"命中路数"退化为"上游原生序"）。

**② `type_` 过滤在多路下怎么算？**

**每路都带该过滤，且每路独立跨页扫描。**

理由：`type_` 过滤是调用方的显式意图（"我只要 knowledge"），不是路由策略。若只在某一路扫，会导致"同一意图下不同路召回能力不同"这种不可解释的行为——正是本 spec 要消除的东西。

复用现有 `_knowledge_search` 的扫描补齐逻辑（`max_scan_pages=5`），但**每路的扫描独立计数**。代价是 `type_` + 多路时上游请求数最坏为 `routes × max_scan_pages`；该组合由**预算**硬卡（见下）。

`scanNote` 在多路下改为**汇总口径**：报告实际扫描页数与请求数，不再声称"跨上游 N 页扫描"这种单路语义。

**③ 预算怎么计？**

**`search` 纳入同一套 `_Budget`，但默认上限与 `ask` 不同。**

- `ask` 的默认 `budget.maxUpstreamPerAsk`（64）**不动**——它含深读请求，语义是"一次完整资料包"。
- `search` 新增独立默认档 `budget.maxUpstreamPerSearch`（`query_routes.json`，**默认 24**）：7 路 × 1 页 = 7 次基础请求，加 `type_` 扫描与重试的余量。
- 二者共用 `_Budget` 类与 `acquire()` 硬闸（去服务化后已是单进程，无跨进程问题），但**上限各自取默认**；调用方显式传 `budget=` 时以传入值为准。
- 预算耗尽时**不静默**：`budget_exhausted: true` + `scanNote` 记录"实际完成 N 路 / 计划 M 路"，让调用方知道清单不完整。

这是对"多路 → 上游请求升到 2-7 倍"的直接回应：**升倍是设计代价，必须被计量而非被忽略**。

**④ `--page` 分页与多路的关系？**

**多路下 `page` 语义改为"清单分页"，`page_size` 作用于融合后的清单。**

理由：上游分页在多路下没有意义——"第 2 页"是哪一路的第 2 页？融合后清单是一个新的有序集合，只能对它分页。

具体：每路上游固定 `pageSize=10`（每路 10 条，见已定设计 ④），去重排序得到融合清单，再按 `(page-1)*page_size : page*page_size` 切片。**去掉 `--page` 参数**会破坏既有调用方，故保留参数名但**重新定义语义**并在 docstring 与 `scanNote` 中写明。

⚠️ 这意味着 `--page 2` 的**内容**与旧版截然不同。这是**破坏性语义变更**，必须写进 commit message 与技能文档。

**⑤ 是否保留 `ask` 的 RRF 路径？**

**本轮保留，`ask` 一行不改。**

理由：`ask` 是另一个调用面（一站式资料包，含深读）。本轮改动应聚焦 `search`，避免一次跨两个调用面的大改导致问题无法定位——与去服务化 spec"先建新路径并验证，再删旧代码"同一纪律。

**但 `ask` 的融合路径已在本 spec 中留有明确后续**：若 `search` 多路清单在实践中确实优于 `ask`，则应新开一张票决策 `ask` 的去留/改造（可能是"`ask` 内部改为调 `search` + 深读"），而不是在本轮顺带改。

### 去重键（交接文档 3.2 的陷阱）

**统一为 `(type, id)`，`questionId` 仅作展示。**

现状是**三处键不一致**，这是必须一并修的隐患：

| 位置 | 现用键 | 问题 |
|---|---|---|
| `_rrf_fuse` | `answer:questionId` / `type:id` | answer 按 questionId 归并 |
| `_fused_key` | `answer:questionId` / `type:id` | 与 `_rrf_fuse` 一致 |
| `_knowledge_search.collect()` | `(et, id)` | **answer 用回答 id，与前两者不同** |

后果：同一问答帖的**不同回答**在 `_rrf_fuse` 里被归并成一条（丢回答），在 `collect()` 里被当成两条。`search` 多路后要走去重，这个不一致会直接造成"同一帖多回答被误合"或"同一回答被拆两条"。

**新定义**：去重键 `f"{type}:{id}"`，其中 `answer` 的 `id` 取**回答 id**（`x["id"]`），`questionId` 只出现在展示字段里。

理由：`search` 的清单单位是**条目**，而回答是独立条目（一个帖子可以有采纳回答 + 多条普通回答，语义不同、应可分别筛）。`read("answer", ...)` 只认 `questionId` 是**读取路径**的约束，不影响**列表路径**的条目粒度——两者本来就该分开。这条区别写进代码注释。

⚠️ 该变更**只作用于新的 `search` 多路清单**；`ask` 的融合路径本轮不动（仍用 `answer:questionId` 归并，保持既有行为）。

### 实现要点

**`_plan_routes` 接入 `search` 执行链。** 它返回 `(routes, product_id)`，每条 route 形如 `{"kind", "terms", "why", "productIds"?, "sortsType"?}`。`terms` 是**空格拼接的字符串**（已由拆解器决定组合方式），直接作为 `_search_upstream` 的 `text` 传入即可——`ask` 现就这么用（`_knowledge_search(r["terms"], ...)`），无需二次处理。

### 上游是 OR 宽召回（实测，多路设计的地基）

实测同一问句加词后的 `totalElements` 变化（产品线 93，同一时刻）：

| 检索词 | total | 前 3 条标题 |
|---|---|---|
| `应用为禁用状态` | 1727 | 三条一致 |
| `应用为禁用状态 网关` | 1750 | **与上行完全相同** |
| `应用为禁用状态[网关]` | 1750 | **与上行完全相同** |

**结论：上游是 OR 语义（宽召回），不是 AND。** 加词只会让结果集**变大**（1727 → 1750），不会收窄。所以：

- route 的 `terms` 里空格拼接的多个词，**不是"必须同时满足"**，而是"命中任一即召回"。
- 这正是多路设计成立的前提：既然每一路都是宽召回，那"多路各自独立搜、用**命中路数**排序"就是在多个宽召回里提取**交叉信号**——命中路数越多 = 越多独立拆解角度都认为它相关。这个信号在 OR 语义下才有意义（若是 AND，多路会几乎全部收敛到同一批结果，路数无区分度）。
- 也解释了为何 RRF 有害：它把"多路都泛泛命中"当成强信号。

⚠️ **副产品证据**：上表前 3 条标题中**第三条为空字符串**——这是本 spec「冒烟前必做」那节所述 answer 标题解析坑的**现场复现**（该条为 answer 类条目）。修它时可用这个查询作为最小复现用例。

**每路独立失败不拖垮整轮。** 复用 `ask` 的异常分档：`_BudgetExhausted` → 停止后续路；`UpstreamError` → 记日志、跳过该路、继续；其他 `Exception` → 记日志、跳过该路、继续。**但 `search` 必须在输出里暴露"哪几路失败了"**（新增 `routeErrors[]`），否则调用方会把"某路被上游拒绝"读成"官方没这类文档"——这正是 `ask` 现有注释里警告过的错误。

**单路空结果与整体空结果要区分。** `总命中 0` 时，若 `routeErrors` 非空，应提示"部分路失败，召回不完整"，而不是直接说"无匹配"。

### 冒烟前必做：复现交接文档 3.3 的解析坑

交接文档记录：直接调上游 `/api/search` 时，`answer` 条目标题取不到（`highlight.title` 为空），但 `kd search` 输出里标题正常。

**修前先复现**，命令：

```bash
python3 src/kd_run.py search "应用为禁用状态[网关]" --product 93 --size 10
```

观察 answer 条目（第 3、4 条）的 `title` 是否为空。

**`_norm_item` 对 answer 的取值顺序是 `hl.get("question.title") or q.get("title") or ""`**——注意 `highlight` 里带的键是**含点号的 `question.title`**（不是嵌套对象）。需核实上游 answer 条目的 `highlight` 里到底有没有这个带点的键，以及为何同一条在不同调用路径下表现不同。

**此坑不修不算完成**：多路清单的核心交付物是标题，标题缺失会直接摧毁清单的可用性。

### 守卫与契约（交接文档 3.4）

- `search` 签名被 `SIGNATURE_BASELINE` **逐字钉死**：
  `(text, product_id=None, page=1, page_size=10, global_=False, sorts_type=1, type_=None, rerank=None, budget=None, rate=None)`
- **本 spec 新增两个参数**：`routes=None`（最多几路）、`multi=None`（暂停用；见下）。签名字符串必须与守卫基线**同步更新**，差一个空格即判据 5 FAIL。
- `_rrf_fuse` 在守卫 `FORBIDDEN_NAMES` 里（不得成为 `kd.core` 属性）。**本轮不删该函数**（`ask` 仍在用），故该钉子自然 PASS。
- **判据 7 注意**：它从 `cmd_health` 的 `_cp.` 引用动态提取依赖。删任何内部件前先查 `cli.py` 有无引用。
- 公开面仍必须是 `ask`/`search`/`read` + 三个异常类（判据 1/3/4/6）。

> 注：`multi` 参数在裁决①中被否决（默认开启、不加开关）。**若实现期为省事引入 `--multi`，即为违反本 spec**——应改用 `--routes`。

### 回归基线要改的用例（交接文档 3.5）

| 用例 | 现状 | 需要 |
|---|---|---|
| `t_search_contract` | 断言 search 顶层 10 键 + 结果项字段 | 同步白名单（新增 `hitRoutes`/`routes`/`routeErrors`，`page` 语义变更） |
| `t_search_all_types` | 断言三种 type 都返回 | 多路后应更稳，确认不回归 |
| `t_ask_*` 系列 | 断言 ask 的 routes/sources/budget | `ask` 保留且未改，不动 |

`SEARCH_KEYS` / `RESULT_BASE_KEYS` / `RESULT_ALLOWED_KEYS` 在 `tests/kd_regression.py` 顶部。

**必须新增的用例**（当前无覆盖）：
1. 多路去重：构造同一 `answer` 条目被两路命中，断言清单里**只出现一条**且 `hitRoutes=2`。
2. answer 双 id 空间：断言 `(type, id)` 键下**同一帖的不同回答不被合并**。
3. `routeErrors`：模拟某路 `UpstreamError`，断言该路被记录、其余路结果仍返回。
4. 预算耗尽：断言 `budget_exhausted=true` 且 `scanNote` 反映实际完成路数。

### 三件套验证（改 `src/` 后必跑）

## Testing Decisions

**测行为，不测结构。** 断言"清单里有什么、排成什么样"，不断言内部函数调用次数——多路的实现细节（串行/并发、请求合并）应可自由调整而不惊动测试。

**去重与排序的测试用构造数据，不打上游。** `_norm_item` / 去重 / 排序应是纯函数，喂合成条目即可覆盖；只有 `--online` 组打真上游。
