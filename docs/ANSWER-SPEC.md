# ANSWER-SPEC —— kd 回答规范(v2.4)

本文是合成回答格式的**单一事实源**。三处引用它、不各写一份:`SKILL.md`「第 3 步:合成」节、README 的「进阶 → 合成与置信度 / 回答规范」两节、以及任何调用方 agent 的合成实现。规范对齐官方 AI 分享对话样例。

> **v6.2 起合成权在调用方**(ADR-0008):kd 不再合成回答(原 `kd ai` 已删除),只产检索产物。
> **v2.4(2026-09-18,ADR-0013)**:检索产物由「资料包」改为「清单」——`kd ask` 已删除,
> 唯一入口是 `kd search`。

## 适用者

- **调用方 agent**:自己驱动三步链路并作答——`kd search` 出清单 → 你按标题挑 → `kd read` 取全文 → 按本规范合成。
  **默认直接作答,不开子代理**(ADR-0012 决策 2:子代理看不到主对话、交付常不完整、会错判置信度);
  仅当清单明显超长或一次要合成多份时才考虑开,且要求它**返回完整正文**;
- **回答语言**:中文。

## 规范

1. **结构化 Markdown,三段式**:
   - `## 问题原因分析` —— 先说清为什么(机制/字段/流程层面的原因);
   - `## 解决方案` —— 编号步骤(### 第一步/第二步…),每步给可直接执行的操作路径(菜单路径/字段名/参数值);
   - `## 操作边界` —— 适用版本/前提/隐藏字段位置/不覆盖的情况,主动交代边界。
2. **表格**:并列信息(字段对照、路径说明、参数含义)用 Markdown 表格,不堆长列表。
3. **引用**:官方文档结论**做成可点击角标** `[标题](https://vip.kingdee.com/knowledge/<id>)`
   —— 2026-09-17 实测该路径**匿名可访问**(HTTP 200 且含正文)。可点性**按路径而异**:
   `article/<id>` → 302 到 `knowledge/<新id>`(**路径迁移**,最终 200);`question/<id>` →
   302 到 `/error/404`(**帖子被删**)。故**引用优先用 `knowledge/` 链接**;
   `question/`、`article/` 的 URL 会因删除/迁移失效,只写标题或注明可能失效。
   清单条目的 `url` 字段就是按此口径给出的:`knowledge` 可点、`answer` 可能失效。
   - **不要求**文末独立的 `## 参考来源` 节,正文里也**不要**写"源N"这类自用编号;
   - **网页 URL 更正(2026-09-17)**:早前"匿名一律 302 登录墙、禁止作为溯源依赖"的说法
     实测不成立——三条路径**没有一条是登录墙**(`article/` 是路径迁移、`question/` 是帖子被删)。
     ADR-0007 决策 3 的适用范围据此收窄(详见 ADR-0012);
   - ⚠️ `kd read --chunk` 的 chunk 溯源端**从未落地**(官方无「按文档列全部 chunk」端点,
     chunkId 只能来自登录态),故**不得**依赖 entityId+chunkId 的离线重取路径。
     原资料包的 `chunks` 字段已随 `kd ask` 一并删除(ADR-0013),不再存在该依赖。
4. **诚实声明**:资料未覆盖的部分明确写「现有资料未覆盖…」,给不出结论就说给不出——**不编造菜单路径、字段名、接口名**。
5. **召回置信度(2026-09-18 修订,ADR-0010 后续更正)**:三档枚举(`answerable`/`partial`/`uncovered`)
   **保留为内部判断依据**,但**不再输出为正文前的 JSON 头** —— 答案直接给定性结论,
   不展示任何元信息。三档含义:

   - `answerable` —— 召回文档中有段落直接说明了机制/字段/步骤;
   - `partial` —— 有相关材料,但未覆盖用户问的那个点;
   - `uncovered` —— 召回内容与问题不匹配,或检索本身未命中。

   **禁止用 0-1 数值分数**:LLM 自报概率无校准(同一事换问法可得 0.5 或 0.9),
   且与清单里的客观量不同量纲,反而污染判断;
   分数还会诱导中间偏高取值,使**该说"不确定"时给出 0.7**,破坏本规范第 4 条的诚实要求。
   判定须参考**清单信号**(原 `synthesisBrief` 已随 `kd ask` 删除,ADR-0013):
   - `hitRoutes` / `routes[]` —— 该条目被几路命中、来自哪几路。**仅是参照,不是分数**:多路命中的
     通常更泛,单路精确命中的往往更专(实测:目标文档 `hitRoutes=1` 排在 5 篇 `hitRoutes=2` 的泛文之后);
   - `routeErrors[]` —— 哪些路检索失败。有失败路即意味着**召回不完整**,判定应更保守;
   - `budget_exhausted` —— 预算耗尽,剩余路未检索,判定应更保守;
   - `routesDegraded` —— 路数塌缩(多路拆出同一串检索词),实际路数少于计划路数;
   - 条目上上游原生的旁证:`adopted`(采纳)/`answersCount`/`comments`/`supports`/`questionBody`。

   `routeErrors` 非空或 `budget_exhausted:true` 时,检索不完整,判定应更保守;
   清单里只剩泛词路命中、没有原句路/症状路的精确命中时,多半应落 `partial`/`uncovered`。
   判定为 `partial`/`uncovered` 时正文必须写明缺什么,**并反问一句关键澄清**(照官方 AI 的做法),
   不堆缺口声明,**不硬凑步骤**。
6. **区分权威级**:官方文档确认的结论直接陈述;社区问答/文章得出的标注「来自社区经验」。
7. **根因引用规则**(v6,对齐评测硬指标「根因可解释率」):
   - **answer(社区问答)引用用于症状对齐**——证明你理解了用户遇到的症状与社区案例同款;
   - **根因解释必须优先引用 knowledge(官方文档)或发版说明**——「问题原因分析」段的机制/字段/流程
     结论要落到 knowledge 或发版说明的根因段落,**只引 answer 不算根因可解释**;
   - **「官方已修复」类问题以发版说明为终审依据**——某行为是否为已知问题、在哪个版本修复,
     结论引发版说明的「模块-问题-修复」条目;发版说明与社区说法冲突时,以发版说明为准;
   - 根因确实拿不到时,按第 4 条诚实声明「现有资料未覆盖根因」,不要用 answer 的推测充当根因。
8. **产品线甄别(2026-09-17 修订:硬规则撤销,改为默认值 + 判断)**:
   - **`search` 默认 `product_id=93`(星空旗舰版)**,常规提问不必显式带 `--product`;
   - **问句产品词优先于默认**:问句含「苍穹」「企业版」等别名时按别名推导并覆盖 93;
     要**真正的不过滤**必须**显式**传 `--product 0`——默认 93 已使"不带参数"不再等于不过滤;
   - **不要因为检索不顺手就把 `--product` 切来切去**:问句确实指向其他产品线时,
     让产品词推导去做,或先向用户确认。这是判断,不再是硬规则;
   - **单点核对 `effectiveProductId`**(2026-09-18 修订,ADR-0013):引用与合成前核对它是否等于预期产品线 ID。
     它是 **`kd search` 清单返回体的顶层键**(整数,与 `--product` 同值域,可直接比对),
     语义是**经推导后实际生效**的产品过滤:

     | 值 | 含义 |
     |---|---|
     | `None` | 本次未携带任何产品过滤 |
     | `93` | 星空旗舰版(默认) |
     | `87` | 苍穹 |
     | `1` | 企业版标准版 |
     | `0` | 显式不过滤(`--product 0`) |

     它是唯一可执行的产品线判据:精确整数,与 `--product` 同值域,直接比对。
     ⚠️ **问句里的产品词会覆盖默认**——问「苍穹 XX」时该键为 `87` 而非默认的 `93`,
     故**核对时以该键为准,不要用你自己传入的 `--product` 值代替**(传进去的是原始输入,
     该键才是推导后的结果)。
     **为 `None` 表示本次未携带任何产品过滤**——此时**不得**把结果当作某条产品线的答案引用:
     必须在正文标注「本次检索未按产品线筛选,结论可能混入其他产品线内容」;
   - **`results[].products` 仅作提示,不得作为判据**:该字段装的是**上游中文类目名**
     (`["金蝶AI套件"]`、`["企业版","标准版","成本管理"]`),与 `effectiveProductId` 的整数
     **值域不可比**(中文词 vs 整数 ID),全无可执行的相等判断。它只能用于人工阅读时判断
     "这份资料大概属于哪个范畴",**不得**作为"产品线不符故排除该源"的依据——那会把判断
     退化成猜测。

   > **历史**:本节原名「产品线粘性(硬规则)」,源于 2026-09-06 旗舰版串线事故
   > (agent 把 `--product 93` 变道为 0,召回了企业版 ENG_BOM/T_ENG_BOM 内容并当作旗舰版输出)。
   > 事故后立的三条硬规则于 2026-09-17 全部撤销——默认 93 落地后第一条失去对象,
   > 后两条被判定可由默认值自然规避。事故事实保留在 ADR-0012。

## 反例(禁止)

- 大段平铺文字无小标题;
- 编造具体字段标识或菜单路径;
- 把社区推测说成官方结论;
- **正文里带元信息**:JSON 置信度头、"源N"自用编号、结尾审计披露/复盘段;
- 引用**明知**与目标产品线不符的源(如旗舰版问题却引企业版 ENG_BOM/T_ENG_BOM 内容而不加甄别);
- 拿 `results[].products` 的中文类目名硬当作产品线判据(值域不可比,见第 8 条);
- **只读清单就作答**:清单只有标题,机制/字段/步骤必须经 `kd read` 取全文核实;凭标题猜内容即等于编造。
