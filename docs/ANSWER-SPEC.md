# ANSWER-SPEC —— kd 回答规范(v2.3)

本文是合成回答格式的**单一事实源**。三处引用它、不各写一份:`SKILL.md` 的子代理提示词模板、README 进阶章、以及任何调用方 agent 的合成实现。规范对齐官方 AI 分享对话样例(样例:官方分享短链 clzL8,可用 `kd share` 匿名读取)。

> **v6.2 起合成权在调用方**(ADR-0008):kd 不再合成回答(原 `kd ai` 已删除),只产资料包。
> 本规范由**调用方**在合成时遵循;提示词模板见 `SKILL.md`「合成与置信度」节。

## 适用者

- **调用方 agent**:拿 `kd ask` 资料包合成时,按本规范写回答(建议开子代理隔离上下文);
- **回答语言**:中文。

## 规范

1. **结构化 Markdown,三段式**:
   - `## 问题原因分析` —— 先说清为什么(机制/字段/流程层面的原因);
   - `## 解决方案` —— 编号步骤(### 第一步/第二步…),每步给可直接执行的操作路径(菜单路径/字段名/参数值);
   - `## 操作边界` —— 适用版本/前提/隐藏字段位置/不覆盖的情况,主动交代边界。
2. **表格**:并列信息(字段对照、路径说明、参数含义)用 Markdown 表格,不堆长列表。
3. **引用**:正文关键结论后标 `[n]`;文末 `## 参考来源` 列出 `[n] 标题 —— 类型`(类型取实体 type:官方文档/社区问答/社区文章)。没有可用来源就不列。资料包中 knowledge/article 源带 `chunks`(标题感知切片,形如 `[chunk#2 【操作步骤】]`):合成时应优先依据命中段落,关键结论可标注到段(`[n](chunk#m)`),不引用与结论无关的全文内容。
   - **引用标准形态(ADR-0007)**:每条引用 = `标题 + entityId + chunkId`;需要全文时匿名调官方溯源端解析:`kd read <chunkId> --chunk`(匿名 GET `/aisapi/document-chunks/{chunkId}`,返回块全文及 entityId/entityType/documentId/title 映射)。引用永不 404,离线也可凭 entityId+chunkId 重取原文。
   - **网页 URL 只作记录**:vip.kingdee.com 网页路由(/question、/article、/knowledge)匿名一律 302 登录墙,凡附 URL 必须标注「(需登录)」,且**禁止作为溯源依赖**——核对来源一律走 entityId+chunkId,不靠点链接。
4. **诚实声明**:资料未覆盖的部分明确写「现有资料未覆盖…」,给不出结论就说给不出——**不编造菜单路径、字段名、接口名**。
5. **召回置信度(v6.2,ADR-0010)**:合成方在正文之前输出一行 JSON 头 `{"confidence":…,"basis":…}`,三档之一:
   - `answerable` —— 召回文档中有段落直接说明了机制/字段/步骤;
   - `partial` —— 有相关材料,但未覆盖用户问的那个点;
   - `uncovered` —— 召回内容与问题不匹配,或检索本身未命中。

   **禁止用 0-1 数值分数**:LLM 自报概率无校准(同一事换问法可得 0.5 或 0.9),
   且与资料包的客观量(`synthesisBrief.topScores`)不同量纲,反而污染判断;
   分数还会诱导中间偏高取值,使**该说"不确定"时给出 0.7**,破坏本规范第 4 条的诚实要求。
   判定须参考 `synthesisBrief`(`sourceCount`/`routeKinds`/`budgetExhausted`/`recallHint`):
   `budgetExhausted:true` 时检索不完整,判定应更保守;`routeKinds` 只剩 `product` 而无症状路命中时,
   多半应落 `partial`/`uncovered`。判定为 `partial`/`uncovered` 时正文必须写明缺什么,**不硬凑步骤**。
6. **区分权威级**:官方文档确认的结论直接陈述;社区问答/文章得出的标注「来自社区经验」。
7. **根因引用规则**(v6,对齐评测硬指标「根因可解释率」):
   - **answer(社区问答)引用用于症状对齐**——证明你理解了用户遇到的症状与社区案例同款;
   - **根因解释必须优先引用 knowledge(官方文档)或发版说明**——「问题原因分析」段的机制/字段/流程
     结论要落到 knowledge 或发版说明的根因段落(可细到 `[n](chunk#m)`),**只引 answer 不算根因可解释**;
   - **「官方已修复」类问题以发版说明为终审依据**——某行为是否为已知问题、在哪个版本修复,
     结论引发版说明的「模块-问题-修复」条目;发版说明与社区说法冲突时,以发版说明为准;
   - 根因确实拿不到时,按第 4 条诚实声明「现有资料未覆盖根因」,不要用 answer 的推测充当根因。
8. **产品线甄别(硬规则,v6,票 #19,对齐 2026-09-06 旗舰版串线事故)**:
   - **产品路由粘性**:同一问题会话内,首次 `kd ask` 确定的 product 路由(如 `--product 93`
     旗舰版)**必须贯穿该会话后续所有 search/read/ask 调用**;**禁止中途变道
     `--product 0`(不过滤)、禁止换用其他产品线过滤**;若用户追问中出现了新的产品线线索
     (如明确提到另一产品),**必须先向用户确认后再切换**,不得自行判断或静默切换;
   - **单点核对 `effectiveProductId`**:引用与合成前,**必须核对资料包顶层
     `effectiveProductId` 是否等于本次预期的产品线 ID**。它是唯一可执行的产品线判据:
     精确整数(93/87/1),与调用时传入的 `--product` 同值域,直接比对即可。
     **`effectiveProductId` 为 `null` 表示本次未携带任何产品过滤**——此时**不得**把结果当作
     某条产品线的答案引用:必须在正文标注「本次检索未按产品线筛选,结论可能混入其他产品线内容」,
     并在结论不确定时按第 4 条声明未覆盖;
   - **`sources[].products` 仅作提示,不得作为判据**:该字段装的是**上游中文类目名**
     (`["金蝶AI套件"]`、`["企业版","标准版","成本管理"]`),与 `effectiveProductId` 的整数
     **值域不可比**(中文词 vs 整数 ID),全无可执行的相等判断。它只能用于人工阅读时判断
     "这份资料大概属于哪个范畴",**不得**作为"产品线不符故排除该源"的依据——那会把判断
     退化成猜测。要排除异产品线内容,靠的是 `effectiveProductId` 与正文内容核对,不是这个字段;
   - **过滤回显不符即停**:`effectiveProductId` 与预期不符(如要旗舰版 93 却回显 `null` 或别的值)时,
     **必须停止检索并向用户报告,禁止带着错误过滤继续作答**。

## 反例(禁止)

- 大段平铺文字无小标题;
- 编造具体字段标识或菜单路径;
- 把社区推测说成官方结论;
- 列了一堆来源但正文没有任何 `[n]` 标注;
- 引用**明知**与目标产品线不符的源(如旗舰版问题却引企业版 ENG_BOM/T_ENG_BOM 内容而不加甄别),
  或中途把已确定的 `--product` 路由变道为 0(2026-09-06 事故反例,见第 8 条);
- 拿 `sources[].products` 的中文类目名硬当作产品线判据(值域不可比,见第 8 条)。
